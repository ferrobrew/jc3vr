# The learned body estimator

The `body-estimator` crate runs EgoPoser (Jiang et al., ECCV 2024), a learned estimator that reads a window of head and hand poses and estimates an SMPL body: the pelvis's global orientation and the other 21 joints' rotations. It tells the rig where the pelvis and chest face when the head and hands alone leave it ambiguous ([rig.md](rig.md#the-yaw)), and gives the IK body its joint rotations ([ik-body.md](ik-body.md)). The crate has no game dependencies, so `tools/tracking-synth` runs it on Linux and the payload runs it in the game.

## The weights

The checkpoint is trained on AMASS, whose licence is non-commercial, so it must never be committed; `.gitignore` keeps `.pth` and `.safetensors` files out, except the golden fixture, which holds only inputs and outputs. To set it up, download `egoposer.pth` (the base model) from the folder the [EgoPoser repository](https://github.com/eth-siplab/EgoPoser) links, then run `scripts/egoposer_weights.sh path/to/egoposer.pth`. That converts the state dict to `.egoposer/egoposer.safetensors` in a throwaway `uv` environment and copies it next to `jc3vr_payload.dll` in every built target directory; run it again after a clean build. The payload reads `controllers.body.estimator.weights_path` if set, otherwise `egoposer.safetensors` beside the DLL. Tests and tools take `JC3VR_EGOPOSER_WEIGHTS` (or `tracking-synth --weights`), and tests that need weights skip when it is unset.

## The network and the CPU reference

Each input frame is EgoPoser's 54-value sparse feature vector for the head and both wrists, plus six window-start deltas; an untracked hand is zeroed. A window is 80 frames at 60 Hz, split into a slow stream (every second frame) and a fast stream (the last 40), embedded and summed into 40 tokens, then a three-layer transformer encoder (width 256, eight heads) and two small decoders on the last token, one for the root orientation and one for the body pose, both in 6D.

`EgoPoser::infer` is the network in plain Rust, written for clarity, and golden tests hold it to the PyTorch model's outputs on recorded windows to a relative error of about 1e-6 (`crates/body-estimator/tests/fixtures/egoposer_golden.safetensors`). Since only the last token reaches the decoders, the last encoder layer computes only that token's row, which is exact. A CPU pass costs a few milliseconds of a core, too much for every frame, so it serves as the reference the GPU executor is tested against.

## The GPU executor

`egoposer::gpu::GpuEgoPoser` runs the same pass through Direct3D 11 compute shaders on any device, including the game's. It is Windows-only, behind the default `d3d11` feature. The weight matrices are stored as 32- or 16-bit floats (`WeightPrecision`); everything else stays 32-bit. A device without compute shaders panics, since no machine that runs the game lacks them; other failures are `GpuError`.

An inference never waits on the GPU: `submit` builds the token inputs on the CPU, records the pass on the given context, and copies the estimate into a ring of three staging buffers; `poll` later maps the oldest without waiting. An estimate uncollected when its buffer comes round again is dropped. `infer_blocking` waits, for tests and tools. The executor saves and restores the compute state it touches, so it can record onto the engine's context. The shaders are in `crates/body-estimator/src/shaders/` (a linear layer in 32- and 16-bit variants, the residual layer norm, and the attention), compiled by `shadergen`, and the network runs as 25 dependent dispatches with a buffer per activation so tests can read any stage.

The pass costs about 120 µs of GPU and 7 µs of CPU to record on an RTX 5090 through DXVK, and its readback lands the next frame. It is bound by dispatch count, not arithmetic, so 16-bit weights barely change the time; they halve the weights' memory with no measurable loss (at most 0.016 degrees of pelvis or chest yaw on the fixture), so they are what the game uses. `crates/body-estimator/examples/egoposer_bench.rs` measures it.

The GPU tests compare each kernel in isolation, the whole pass stage by stage, and the final estimate against the CPU reference. They need a Direct3D 11 device: `./scripts/xwin_test.sh -p body-estimator` uses wine's own Direct3D, and setting `CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_RUNNER` to `scripts/dxvk_run.sh` runs them on Proton's DXVK, as the game does.

## In the game

The payload's producer (`crates/jc3vr-body/src/controllers/body/estimator/`) runs whenever the controller scheme is in effect and the head is tracked, in every mode, and publishes the latest estimate through `estimator::latest`. Under the gamepad scheme nothing runs. The grounded rig consumes the headings while Rico is on the ground and the player owns his root, and the IK body takes the spine, neck, hip, and knee rotations on foot and in jumps; elsewhere the estimate is only drawn.

Each rendered frame, `roomscale::compose_cockpit` hands the eyes and tracked grips in the rig's room frame to `body_estimator::window::WindowBuilder`, which does what `tracking-synth estimate-body` does to a recording. Seated, the eyes are remapped to standing height as the rig does ([rig.md](rig.md#posture)), so a seated window looks standing. The window keeps its own room frame that no recenter moves (a recenter's turn arrives through `roomscale::on_recenter`), resamples to 60 Hz, marks a lost controller's hand as hidden, and restarts after a gap over a quarter of a second, a posture change, or a lost head; a full window takes 1.35 s to refill.

At `estimator.submit_hz` the producer posts the window to a mailbox that a newer window replaces. The render thread's post-draw hook, holding the engine's context lock, submits and polls, and publishes each finished estimate to a second mailbox. An estimate is a frame or two old. The weights load on their own thread when the first window arrives, so a gamepad player never reads them. A missing weights file with the estimator on is a panic naming the path and how to produce it: the weights are part of the installation.

`estimator::latest` returns the estimate in the cockpit frame as it stands when read, so a recenter in flight changes nothing: the pelvis's and upper chest's headings in `body-rig`'s yaw convention, every joint's global rotation, the age, and the posture. The rig's confidence in it falls from one to none between `yaw.estimate.fresh_s` and `yaw.estimate.stale_s` of age, so a stalled estimator eases out of the yaw.

The debug UI's Body fit feature has the switch (`controllers.body.estimator.enabled`, on), the weights path, the executor's stage and counters, and the latest headings, age, and posture. The floor arrows (`Body estimate` in the visualisation drawer, off by default because they crowd the view) draw the estimate's pelvis and chest in green and, while the rig runs, the rig's legs and chest in magenta. The estimate is not recorded; `tracking-synth estimate-body` and `rig-eval --weights` recompute it from a take.
