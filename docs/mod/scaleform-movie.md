# A mod-owned Scaleform movie

Status: researched; not built.

A movie the mod authors and hosts itself, alongside the game's root movie, would give the mod a surface in the game's own look for content no shipped movie can show, such as the [weapon selector](weapon-selector.md) at the hand or a controls summary. The engine facts it rests on (the loader, the file opener, standalone movies, fonts, widgets, and building a movie the loader accepts) are in [scaleform.md](../engine/scaleform.md).

## Why the VR settings do not use one

The VR settings went into the pause menu instead ([pause-menu.md](pause-menu.md)). Rows on the game's own settings screen reuse its widgets, layout, focus, gamepad navigation, sounds, localisation, and the controller pointer that already drives that movie, and toggles, sliders, readouts, and buttons cover what the settings need. A mod movie would have to rebuild all of that, and first needs the whole hosting project below before it shows anything. Patching the shipped `.gfx` files was rejected outright: the injector attaches to a running game and does not control its command line, so the loose-file mount is a development convenience only, and shipping would mean repacking patch archives, a heavier and more fragile pipeline than anything else the mod does (shaders, for comparison, are patched in memory; see [shader-patching.md](rendering/shader-patching.md)).

## Hosting, ranked

1. A separate movie the mod creates, advances, and draws itself. It is loaded through [`UIManager::m_Loader`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_Loader), so it inherits the file opener, fonts, translator, and task manager, and instantiated the way `CRenderToTextureUI::InitMovie` does it. It is advanced and captured on the game thread from the existing `PreRender` seam under the deferred render lock, and drawn inside the UI render with the off-screen pattern the parked split already implements (`payload/src/hud/split/roots.rs`) into a texture the mod owns, shown as its own panel the way `payload/src/hud/egui_panel.rs` shows egui. Its bytes come from memory through a detour on [`ScaleformFileOpener::OpenFile`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::ScaleformFileOpener##func-OpenFile). No game movie is touched and no game object is forged. This is the recommended route.
2. Reusing `CRenderToTextureUI` itself, so the engine advances and draws the movie. Less rendering code, but the mod would allocate an object whose layout is not bound (its constructor is inlined), pull the texture out of a shared pointer, and live with `root.ActivateDyn`'s state machine and the engine's teardown. A fallback if route 1's render integration misbehaves.
3. A child clip loaded into the root movie. It gets the root's mouse delivery for free, but renders into the HUD texture, shares the root's display list with every game screen, and competes with `root.gfx`'s activation logic.
4. A new registered screen with an entry injected into `root.gfx`'s class table. The only route with real engine input priority, and the most invasive: a forged screen object and an untested table injection. A minimal registered screen with no movie, used only to claim input priority, can be paired with route 1 if gameplay input must be blocked.

## Binding and input

Values go in on the game thread before `Advance`, as invokes on the movie or member writes on an AS3 controller object, since direct ActionScript calls are safe only on the movie's capture thread. Changes come back through native handlers made with [`MovieImpl::CreateFunction`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::MovieImpl##func-CreateFunction) and handed to the movie, which needs no global hook; ExternalInterface would need a detour, because a movie with no screen behind it has its calls dropped. A thin authored movie with a small AS3 API built from Rust data is a better split than a purely procedural one built with `CreateObject` and invokes, which works mechanically but puts every widget's layout and focus logic in Rust.

The controller pointer drives the movie through its own [`NotifyMouseState`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::MovieImpl##vfunc-NotifyMouseState) and [`HandleEvent`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::MovieImpl##vfunc-HandleEvent), as a third destination for the router in `payload/src/hud/pointer/route.rs`; the engine never sends this movie mouse or gamepad events, so nothing conflicts. Gamepad navigation inside it is the mod's job. With route 1 the game keeps reading input, so the movie either opens only while the game is paused or pairs with the priority-only screen.

## Risks and unknowns

Beyond the format questions in [scaleform.md](../engine/scaleform.md#building-a-movie-the-loader-accepts): whether advancing, capturing, and drawing a second movie inside the UI render causes stalls, flicker, or HAL state leaking into the root draw; releasing the movie on eject while the render thread may still hold it (the engine defers this through its dying-movie list); whether `NotifyMouseState` drives an authored slider's mouse handlers; and whether `CreateFunction` round-trips its reference count, user data, and return value correctly.
