# Grenades

## Safe items

Taking a grenade from the chest pouch creates an independent loadout item and an engine model instance. It does not create an explosive, start a fuse, consume ammunition, or add ammunition. Either hand can hold one. Drawing another grenade while one is stowed creates a different item; drawing a stowed grenade keeps the original item and model identity.

A safe grenade can move between hands and the supported hip and chest holsters. Holstered models follow the resolved holster transform. The loadout table checks the expected item view before every move, so an occupied destination or stale move leaves the item unchanged.

Opening the grip without a tracked throwing motion leaves an inert model at its last tracked world pose. It has no native physics body, fuse, collision handler, or detonation callback. A free hand can pick it up again. Losing input or tracking does not arm it. The current inert-drop representation remains suspended where it was released rather than simulating a fall.

## Locker sources

A free hand can draw a safe grenade from a registered native weapon display or a verified static collection display. Both source paths are enabled by default. Each hand receives its nearest qualifying display within reach. Completion checks the same source registration and distance before calling the safe-item draw used by the pouch. A missing or changed source refuses the grab instead of selecting another source. The draw leaves the display, native ammunition, the other hand, and holstered items unchanged, so either hand can draw repeatedly from the same display. A nearby gun rack, the player position, and the body pouch do not create a locker target.

Native weapon displays use read-only observations after [`WeaponBase::SetState`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-SetState), [`ThrownGrenadeWeapon::UpdateAttachmentTransforms`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::ThrownGrenadeWeapon##func-UpdateAttachmentTransforms), and the world weapon render pass. The interaction-entry walk can seed the same registry. Registration requires the hand-grenade slot and a dropped or rack state. It never calls a native pickup predicate, starts native pickup, or changes native eligibility. The bounded registry retains weak references rather than keeping native weapons alive. Each input tick locks registered weapons briefly, prunes freed or changed world sources, and reads each visible [`WeaponData::m_BaseModelInstance`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##field-m_BaseModelInstance) at its current weapon-data transform. Completion checks the weapon and control block, weapon-data record, visible model, and registration. Native ammunition capacity does not suppress this path.

The upper-shelf grenade bodies in the inspected Massos locations are static model-collection instances. They are separate from the finite native grenade placement rule. The static adapter observes [`Location::LoadModelCollection`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/location::Location##func-LoadModelCollection), validates the bounded dictionary against an explicit allowlist of the inspected Massos collection paths and their instance counts, and finds the grenade body by its exact model filename. The parser validates the names, model indices, transforms, LOD data, bounds, alignment, and complete buffer length. It does not assume a fixed grenade index across collections. A model hash near a rack is insufficient to register a source.

After native loading succeeds, the adapter checks [`ModelCollection::m_NumInstances`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::model_instance::ModelCollection##field-m_NumInstances) and reads the corresponding entries in [`ModelCollection::m_ModelInstances`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::model_instance::ModelCollection##field-m_ModelInstances). Each accepted entry is enabled, visible, static, not deleted, in the world, and backed by a non-fail model resource. [`ModelInstance::GetMatrix`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::model_instance::ModelInstance##func-GetMatrix) supplies its live world matrix. The adapter copies that matrix and its source identity while the loader keeps the collection live. Asset coordinates and the player's pose do not supply static source positions.

The static registry owns copied records only. It does not retain native pointers for later dereference or keep a collection alive. Its bounded entries have a collection address, a monotonic generation, an exact file-order instance index, and the captured instance and model-resource identities. The [`ModelCollection::Destruct`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::model_instance::ModelCollection##func-Destruct) detour removes the collection's records before native destruction. Target publication, completion, and retirement use the same lock; completion holds it through the safe draw. Address reuse, eviction, or unload therefore invalidates an old offer. Static poses remain the captured static transforms until their collection retires. There is no per-frame scan or input-thread native collection dereference.

Leaving gameplay or losing input clears hand offers. It does not discard live static records, because a loaded location need not load again when gameplay resumes. Shutdown closes and clears both registries. The locker hook scopes expose an active-entry count to the shared image-retention check. Source registration and acquisition logs distinguish static collection records from weak native weapon displays.

The source family covers the inspected Massos collections. It does not claim coverage for every static grenade decoration or cabinet. The localized location title does not establish an internal collection number, so the adapter includes the complete inspected family rather than guessing that mapping. The adapter accepts each inspected full location path and its model-dictionary member path, with case and slash normalization. The native loader's resource-name spelling still needs runtime observation: an unrecognized name refuses registration rather than falling back to a global model search. A location loaded before the hooks were installed must unload and load again before the static adapter can capture it. For late injection, the runtime check must stream the location out and return, or reload the save after hook installation. There is no mapped enumeration of already loaded collections in this adapter. These paths implement source acquisition but do not establish game/headset acceptance of the recorded locker.

## Deliberate throws

Opening the grip during a tracked throwing motion automatically arms and throws the grenade. A separate pin action is not required. Pulling the configured pin input does not create a live grenade while the item is held. Safe grenades cannot be cooked in the hand.

The release captures the item's world transform and its hand-estimated velocity. The controller then calls the existing [`ThrownGrenadeWeapon::PrimeGrenade`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::ThrownGrenadeWeapon##func-PrimeGrenade), which supplies the engine's ammunition-pool allocation, grenade constructor parameters, ownership, and update registration. Only the ammunition deduction in that specific call is suppressed, on the same thread and for that weapon. Inventory values are never topped up or refunded.

Once the native grenade's physics body exists, the controller invokes [`WeaponBase::Fire_Projectile`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##vfunc-Fire_Projectile) on the grenade weapon. The native launch handles its effects and ownership metadata. The existing launch hook supplies the captured hand transform and velocity, including the character velocity recorded by the engine. The safe model and table item retire only after that native launch succeeds.

If the pool is full, the character cannot throw, or activation cannot complete promptly, the item stays an inert, re-grabbable model. Cancellation removes only the grenade created by this activation attempt, through the native pool-removal operation; it does not use the ammunition-refunding cancellation wrapper.

## Live grenades

Catching an existing live grenade retains the native grenade and its running fuse. It remains dangerous in the hand, and the existing warning ring and haptics continue to reflect its fuse. Throwing it on does not create a replacement. The actor-free guarantees apply to grenades drawn from the pouch, not to captured explosives.

## Runtime checks

In the game, draw a grenade with no native grenade ammunition, move it into a hip or chest holster, draw another into each free hand, and re-draw the stowed item. Verify that the models remain independent and ammunition does not change. Open a hand slowly or stop controller input: its model must remain inert and be available to re-grab. Then release one with a deliberate throw and verify that only that item becomes a live grenade and leaves its hand. Repeat with both hands, with a native grenade caught in the other hand, and after a gameplay transition.

At the locker, repeat the draw with native grenade stock at zero, below capacity, and full. Test both free hands independently and together, with an occupied opposite hand and with stored safe items. Confirm that the visible grenade display is the target, that stock and existing items do not change, and that leaving the source or resetting gameplay cannot reuse a stale offer. Check slow release, re-grab, deliberate throw, and repeated draws. Native grenade displays must remain available at full stock even when the native pickup prompt is absent. Correlate the static collection registration and successful acquisition with the upper-shelf grenade bodies separately from any native grenade weapon. Stream the location out and back in, and confirm that the new registration cannot complete an old hand offer. Repeat across a gameplay transition and after injection into an already loaded location. Confirm the loader's resource-name spelling before claiming coverage of the recorded location. A missing target remains a source-coverage failure, not evidence of successful locker acquisition.

The native creation and launch paths are verified against the game database. The locker adapter's mapped provider and exact-source completion have unit tests, but this change has not run those tests or compiled independently; the coordinator performs the integrated checks. Rendering, source publication, physical feel, pool-pressure behavior, and transition timing still require live gameplay testing.
