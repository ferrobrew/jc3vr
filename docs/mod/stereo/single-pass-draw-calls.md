# Single-pass draw calls

Single-pass stereo ([single-pass-stereo.md](single-pass-stereo.md)) exists to cut the submissions multipass makes. A patched geometry draw is one instance-doubled submission for both eyes, but several kinds of draw are still submitted once per eye: render blocks that bake their own transform, GPU-indirect draws, unpatched draws, already-instanced draws, and the second masked run of a split fullscreen pass. The draw census counts the submissions, and the conversions below draw several of these kinds once for both eyes. [frame-budget.md](../performance/frame-budget.md) has what the remaining per-eye submissions cost.

## Naming the draws in a pass range

A capture can carry a census of the draw calls its frame made (`crates/jc3vr-capture/src/harness/draw_census.rs`), requested by `draw_census = true` under an experiment's `[diagnostics]` alongside `shader_identity = true`, which it needs to name the shaders; `tools/rendering/experiments/cliff_view_dusk_draw_census.toml` is the dusk cliff view with it on, and the `*_census.toml` configs beside it cover the other coverage scenes. For every draw call made inside a render pass on the capture's frame it records the pass, the render-block type running, the bound vertex shader (by name, and whether the single-pass rewrite patched it) and pixel shader (by the hash of its pristine bytecode), the device-context entry point, and the treatment the draw path gave the call: `instance_doubled`, `per_eye` (submitted once per eye), `once`, `suppressed`, or `repeated`, plus the eye when the call was made inside a render block's per-eye re-issue (`reissue_eye`) or inside one run of a fullscreen pass split per eye (`split_eye`). Calls that agree on all of that are folded into one entry with call and submission counts, which keeps a frame to about two hundred entries.

The census only observes. It hangs off the draw detours, which the harness also installs in a multipass capture, so a multipass capture records both eyes' walks as dispatches 0 and 1. A multipass capture's vertex shader names are not reliable: they come from a registry keyed by the shader object, and the shader reload between modes can leave them stale. The pass, the block, and the pixel shader hashes are unaffected.

`python -m tools.rendering census <capture.json> --bundle <Shaders_F.shader_bundle> --passes FIRST:LAST --totals` prints the entries for a pass range with the pixel shaders named from the bundle, and the call and submission totals per treatment.

## Accounting for the draw calls

`python -m tools.rendering census <single-pass capture.json> --bundle <bundle> --accounting --multipass <multipass capture.json>` (`tools/rendering/comparison/draw_accounting.py`) counts, for each render pass, each render-block type, and each block and vertex shader:

- the game's calls: every call the census recorded, leaving out the collapse's own repeats, the second eye of a render block re-driven per eye (`reissue_eye` 1), and the second run of a split fullscreen pass (`split_eye` 1). Within the routed range this agrees with the multipass capture's first dispatch to within a few calls, which checks that it is one walk of the render-pass list;
- the single-pass submissions;
- the multipass submissions for the same pass or block, from both of its dispatches;
- the submissions single-pass spends beyond one per game call, which is what instance-doubling the group would save.

The vertex shader key is compared against single-pass only, since a multipass capture's vertex shader names can be stale.

The prepasses (everything before [`RP_RAIN_OCCLUDER`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine::RenderPassId##variant-RP_RAIN_OCCLUDER)) change from frame to frame, because the engine amortises its shadow cascade updates over frames, so compare their mean over several frames in each mode; the routed range repeats within a few submissions between frames. Multipass submits about one walk of the prepasses (its second eye skips the view-independent ones; see "Why `PreDraw` is outside the collapse" in [single-pass-stereo.md](single-pass-stereo.md)) and two of the routed range. Single-pass submits one walk of the prepasses and one walk of the routed range plus the per-eye extras. With the conversions below in place, the census scenes (the town, the tunnel, the capital, the shore lake, the dusk cliff, and the meadow) measured about a third fewer routed-range submissions than multipass.

## Drawing patched non-indexed geometry once

The geometry passes on the non-indexed entry point (`GEOMETRY_SLOT13_PASSES`) route their draws through the per-eye re-issue. A patched vertex shader picks its eye from the instance parity and writes the viewport index, so for it one two-instance `DrawInstanced` with the viewport split is enough, the promotion the static light sprites, the moon, the stars, and the water reflection planes take ([single-pass-per-eye-inputs.md](single-pass-per-eye-inputs.md)). The collapse promotes such a draw, and leaves it to the per-eye re-issue when a domain or geometry shader is bound: only the last stage before the rasteriser routes a draw, and the tessellated particles (`particleeffecttess*`), whose vertex shader the `cb0` remap patches, build clip in an unpatched domain shader that writes no viewport index, so both instances of a promoted draw would land in the left eye's half. What the promotion serves beyond the named promotions is untessellated patched geometry drawn without an index buffer, such as the skidmarks, a few submissions per scene at most.

## Drawing the hardware-instanced buildings once

The buildings' hardware-instanced draws take their per-instance data from vertex-buffer elements, so doubling the instance count alone reads past the batch's data. Doubling every per-instance element's `InstanceDataStepRate` as well keeps instances 2k and 2k+1 on element k: D3D11 fetches a per-instance element at `StartInstanceLocation + SV_InstanceID / InstanceDataStepRate` with `SV_InstanceID` counted from zero, which a standalone check of the DXVK Proton ships confirmed at several start instances and buffer offsets. With the eye in the instance parity, one draw through a twin of the layout with doubled step rates serves both eyes.

D3D11 cannot read a layout's elements back, and the engine builds them on the stack inside [`RenderBlockTypeGeneralMkIII::Create`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_block::RenderBlockTypeGeneralMkIII##func-Create) at registration, before the payload is injected. The handle [`CreateVertexDeclarationInstanced`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::graphics_engine##func-CreateVertexDeclarationInstanced) returns keeps only the layout and the streams' byte sizes. So the payload runs that `Create` again, on a scratch copy of the live type object (the `RenderBlockTypeGeneralMkIII` singleton), with every other effect suppressed for that one call. `Create` calls nothing but [`TextureCacheGetTexture`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine##func-TextureCacheGetTexture) for the wind noise texture, the video card query, [`LoadShaders`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_block::RenderBlockTypeGeneralMkIII##func-LoadShaders), the two declaration creators, [`CreateSamplerStates`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_block::RenderBlockTypeGeneralMkIII##func-CreateSamplerStates), and [`CreateConstantBuffer`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::graphics_engine##func-CreateConstantBuffer), and stores every result in the object. The detours in `jc3vr_render::hooks::graphics_engine::declaration_replay` check a thread-local flag the replay raises: inside it the texture, shader-holder, sampler, and constant-buffer calls and [`CreateVertexDeclaration`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::graphics_engine##func-CreateVertexDeclaration) return without acquiring anything, and `CreateVertexDeclarationInstanced` is called through with a copy of its element array whose step rates are doubled. The copy already holds the live object's shader holders, which is all the declaration code reads, and the engine creates every twin itself, so the mod holds no element table. Each twin lands in the field the live object keeps the original in, so pairing the copy's declaration fields (`m_VertexDeclaration`, `m_VertexDeclarationHWInstancingVelocity`, `m_VertexDeclarationDepth`, and `m_VertexDeclarationDepthAlphaTest`) with the live object's maps each live `ID3D11InputLayout` to its twin. The pairing refuses a twin in a field the live object leaves empty, one twin in fields with different live declarations, and a twin in no field, and then destroys what it created.

The replay (`jc3vr_render::stereo::single_pass::hw_instanced`) runs on the draw thread at the start of a dispatch (`begin_dispatch`), once single-pass is active, and runs again if the live declarations change; a failed build is not retried until they do. The twins are destroyed through [`DestroyVertexDeclaration`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::graphics_engine##func-DestroyVertexDeclaration) on eject, after the draw detours are removed, and a draw still finishing holds its own reference to the layout it bound. Because nothing depends on the payload being present at registration, a late injection and each re-injection build their own twins; an eject and re-injection within one game process has not been exercised. The replay detours stay installed for the session and forward unchanged outside the replay. The debug UI's single-pass section shows how many layouts were twinned.

At an already-instanced draw in the routed range with a patched vertex shader bound, `single_pass.hw_instanced_once` looks the bound layout up; with a twin it binds the twin, splits the viewport, submits the draw once with its instance count doubled, and binds the engine's layout again. It declines without a recorded full viewport, with a domain or geometry shader bound, or when the doubled count overflows, and a layout with no twin is logged once and left to `instanced_per_eye`. The shadow and other unrouted passes are untouched. The occluder's instanced depth prime has no twin and stays on the re-issue, one call per frame.

## Drawing the vegetation once

The bark and foliage blocks bake the centred camera's view-projection into a vertex constant buffer inside their own `Draw` and `DrawZ`, so the fallback re-issues the whole block once per eye with that constant reprojected (see [single-pass-render-blocks.md](single-pass-render-blocks.md)). `single_pass.vegetation_once` draws such a block once instead (`crates/jc3vr-render/src/stereo/single_pass/vegetation_once/`).

What a single draw has to cover, from the shader bundle and the blocks' code:

- Which shader a draw uses. The per-block setup, [`RenderBlockBark::Setup`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_block::RenderBlockBark##func-Setup) and the foliage block's `Setup` (unverified, so not bound), and their `SetupZ` for the depth and velocity passes, binds the vertex shader and input layout by the block's draw kind (plain, GPU-indirect, or hardware-instanced) before `Draw` runs; `Draw` stages the constants and issues the draw. The only exception is the billboard path, which `Draw` selects from [`RENDERSTATUS_BILLBOARD_ARRAY`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_pass::RenderStatus##flag-RENDERSTATUS_BILLBOARD_ARRAY) and which binds its own vertex and geometry shaders. The vertex shader bound when `Draw` begins is therefore the one its draws use. No hull, domain, or geometry stage is bound outside the billboard path.
- The eye-pass shaders. Per family, a colour, depth (`prez`), and velocity permutation of each draw kind: `vegetationbark`, `vegetationbarkhwinstanced`, `vegetationbarkinstanced`, their `prez` and `velocity` counterparts, and the same for `vegetationfoliage` plus the `_osnormalmap` colour permutations. The shadow, reflective-shadow, and billboard permutations draw outside the eye split. Every one builds clip as a multiply-add chain over the baked matrix, so the reprojection applies.
- How each kind fetches its instance. The plain permutations have no instance. The hardware-instanced ones read the instance's transform from `INST_TEXCOORD0..2` and `INST_NORMAL` on a per-instance vertex stream, like the buildings. The GPU-indirect (`*instanced`) ones read it from structured buffers by `SV_InstanceID` plus an instance offset staged in the baked constant buffer, either directly or as an index into the per-pass offset buffer the vegetation update fills. Each reads `SV_InstanceID` exactly once, in the `iadd` that forms the index.
- Where the indirect arguments live. Both block types draw from one argument buffer of the vegetation update, `veg_draw_indirect` per pass: five dwords per draw for every mesh type and every vegetation pass, filled from compute in the vegetation update prepass, which runs before any routed pass. Each draw passes its own offset into it. The buffer has no CPU copy.
- What stays shared. The wind, the per-instance fades and LOD, the foliage's wind-noise lookup origin, and the bark's camera-relative offset all read the engine's single computation from the centred camera, as they do under the re-issue. The pixel shaders take the eye from the pixel position: the camera position, the local lights, and the screen-door pattern are covered by the pixel-shader rewrites in [single-pass-per-eye-inputs.md](single-pass-per-eye-inputs.md).

The single draw:

- Each eye-pass permutation gets a variant, built from its bytecode when the engine creates it (`vegetation_once/variants.rs`) and attached to the engine's shader as private data. The plain and hardware-instanced permutations take `dxbc_stereo::reproject_vertex_shader`. The GPU-indirect ones take `dxbc_stereo::reproject_instanced_vertex_shader`, which reuses the shader's own `SV_InstanceID` for the eye parity and renames its one other read to `SV_InstanceID >> 1`. The engine's shaders stay pristine, so the shadow passes and the re-issue are unchanged, and the variants are built whenever single-pass is enabled, so the switch applies at once.
- The block's `Draw` runs once inside a scope the draw detours consult. Each draw binds the variant of the bound shader and puts the engine's back after it. A plain draw becomes one two-instance draw with the viewport split. A GPU-indirect draw is issued against a copy of the argument buffer at the draw's own offset (`vegetation_once/indirect_args.rs`): a compute pass of the mod's (`crates/jc3vr-render/shaders/indirect_args_double_cs.hlsl`) copies the engine's buffer with every record's instance count doubled, once per routed pass of each dispatch at the first draw that needs it, putting back the compute bindings it touched. A hardware-instanced draw takes a layout twin when its layout has one and otherwise is re-issued per eye with `cb13` pinned to each eye (the `instanced_per_eye` re-issue, with the variant bound).
- A block takes the whole-block re-issue instead when the switch is off, outside the eye split, while drawing billboards, when the shader its setup bound has no variant, or once the argument copy has failed. A draw inside a single-drawn block that turns out not to be convertible is re-issued per eye without parallax and logged once.

The single draw's velocity permutations reproject only `SV_Position`, so the clip positions they hand their pixel shader are the centre camera's. That does not reach the velocity buffer, because the velocity pixel shaders rebuild both positions per eye ("The motion vectors, in each eye's screen space" in [single-pass-per-eye-inputs.md](single-pass-per-eye-inputs.md)).

## What is still drawn twice

- The vegetation's hardware-instanced draws (`vegetation*hwinstanced`). Inside a block drawn once, each is re-issued per eye, because their layouts have no step-rate-doubled twin. The bark and foliage types create theirs in their own `Create` through `CreateVertexDeclarationInstanced`, but their `Create`s do more than the buildings' (the bark type's registers a callback with the environment graphics manager and console variables), so the declaration replay does not cover them.
- The screen-space decals, re-issued as a block because each eye needs its own reconstruction basis and depth-UV offset staged on fragment `cb1`, and the box's baked matrix reprojected.
- The terrain patch system: the tessellated far and colour passes and the GPU-indirect near passes, per-eye re-issues with the eye pinned in `cb13`. The tessellated permutations' vertex shaders write all four lanes of `TEXCOORD3`, so the eye cannot ride the free lane the base terrain uses, and the near passes are `DrawInstancedIndirect` with a vertex shader that already reads `SV_InstanceID`.
- The tessellated particles (`particleeffecttess*`), which build clip in an unpatched domain shader and so cannot take the non-indexed promotion.
- The fullscreen passes split per eye: the screen-space subsurface skin's blurs and lighting capture, the deferred lighting's light assignment and clustered resolve, the atmospheric scattering, and the fog volume's blur, a second masked run each.
- The WaveWorks water and the terrain detail, re-issued as blocks.

Nothing in the prepasses is issued twice: under the collapse `PreDraw` runs once, and the per-dispatch passes that multipass runs twice (the vegetation interaction volumes and the rain occluder) run once.
