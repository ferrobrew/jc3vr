# The animation graph and the weapon

A character's animation layers are state machines loaded from `.afsmb` files (see [animation-layers.md](animation-layers.md)), with the clips each state plays in a matching animation set (`.asb`). This doc describes the state machine format as decoded, how it was decoded, and what Rico's graphs do with the weapon: the conditions that read it, the state tasks that act on it, the upper-body actions, the firing recoil, the hand-pose clips, and the engine's path for playing a clip from code. The decoder is [`tools/anim_graph`](../../../tools/anim_graph). Related: [idle-stance.md](idle-stance.md) (the modifiers that pick a state's clip variant), [hands-locomotion-and-state.md](hands-locomotion-and-state.md) (the attach bones and the bone tasks), and [aim-state.md](../gameplay/aim-state.md) (the aim flags and the inventory permissions).

## The state machine format

An `.afsmb` is an RTPC property container whose root holds one object, the state machine. The engine's loader (`NAnimationSystem::CStateMachine::Load`, `CStateMachine::LoadStateTransitions`, and `CTransition::Load`) reads it as follows; the property name hashes are in `tools/anim_graph/afsmb.py`, named after what the loader reads each into.

- The state machine's children are the conditions, the states, the transitions, the state tasks, and the transition event names. Each condition, state, transition, and task is a child object of its list, and everything else refers to them by their position in that list, so the lists must be read in the order the file stores them.
- Each condition's class is a parallel table on the state machine: one class hash per condition, in condition order, with a second table of (class, count) pairs. A class hash is `HashString` of the class name (`hashlittle` with a zero seed), so `CWeaponWieldedCondition` names its own entries. Each condition object carries its name (`C_WEAPON_WIELDED`) and its settings (a slot, a weapon id, a segment name, a distance).
- Each state's class is likewise a parallel table: `CState`, `CAnimationState`, `CVariableSpeedState`, `CControlTimePerSamplerState`, `CVerticalAimBlendState`, and the other state classes.
- Each task's type is a parallel table too, but a task type's hash is not a hash of its name: the engine's state-task registration table pairs each type hash with its `CStateTask_<NAME>` string and its entry points.
- A state carries a (first, count) range into the transition-pointer table, a list of transition indices; its transitions are the ones it can leave by. It also carries the list of its task indices.
- A transition carries a (first, count, valid-on mask) range into the condition-pointer table, a list of condition indices, and its evaluation method, all-of or any-of. Bit *j* of the mask is the value the *j*-th condition must evaluate to, so a condition can be required false.
- Two per-transition tables on the state machine give each transition's destination state and the event that fires it, an index into the event names (an act such as `ACT_STOP`, or `ACT_UPDATE`, which is evaluated on every update).
- The state machine carries the ranges of its global transitions (taken from any state) and its external transitions, and the index of its initial state.

The index tables are byte arrays of big-endian 16-bit indices.

### How it was decoded

The layout comes from the loader's code in the symbol dump; the files are Rico's four graphs from the patch archive (see [animation-layers.md](animation-layers.md), "The layers"). The decoder parses the binary RTPC directly: the Gibbed property converter's XML sorts each object's children by name, which scrambles the positional indices every table depends on. Condition and state class names are recovered by hashing every class name the symbol dump has a file for and matching the hashes; every class in Rico's graphs resolves. Task type names come from the dump's state-task registration table. Condition, state, and act names are stored as strings in the file.

## Conditions that read the weapon

Every weapon condition in Rico's graphs reads the character's selected slot ([`Character::m_SelectedWeaponSlot`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_SelectedWeaponSlot)) through [`Character::GetWeaponInInventory`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-GetWeaponInInventory), not the weapon a hand holds. "Wielded" means a weapon state of [`E_WS_WIELDING`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponState##variant-E_WS_WIELDING), [`E_WS_DUAL_WIELDING`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponState##variant-E_WS_DUAL_WIELDING), or [`E_WS_MOUNTED`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponState##variant-E_WS_MOUNTED), and the planted explosive counts while [`Character::IsPlantingExplosive`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-IsPlantingExplosive) holds.

`IsWieldedInLeftHand` compares the first gun's attach bone for the weapon's current state ([`WeaponData::m_lBoneAttachementPerWeaponState`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##field-m_lBoneAttachementPerWeaponState)) with the left hand's attach bone. That happens while a base-layer `clear_right_hand` bone task has moved the gun to the left hand (the grenade throws, planting and detonating explosives, and some grapple-attach states). It never looks at the dual-wield pair's second pistol, which is always the second gun.

The graphs also use `CWeaponNextSelectedCondition` (`C_NEXT_SELECTED_*`, the slot being switched or drawn to), `CWeaponMagazineEmptyCondition` (`C_AMMO_IN_MAGAZINE`), `CWeaponHasMagazineInsertedCondition` (`C_HAS_MAGAZINE_INSERTED`), and `CAimingCondition` (`C_IS_AIMING`, `C_IS_AIMING_WEAPONS`). Their bodies were read only in the symbol dump, so what they test is unverified. `CWeaponEquippedCondition` exists but no Rico graph uses it. The partial sync and additive graphs have no weapon conditions at all.

## What the weapon conditions select in the base graph

- `C_WEAPON_WIELDED` splits every on-foot family into a combat and a non-combat version: `S_MOVE_NO_AIM` against `S_MOVE_NON_COMBAT`, the combat walk starts against the `_NON_COMBAT` ones, the start-to-move exits, the `_NO_AIM` flick turns against the unarmed ones, and the stunt turns. The no-aim strafe (`S_MOVE_STRAFE`) is entered only unarmed, and the motorbike's aim states (`S_AIM_*_RIDING_MOTORBIKE`) need a wielded weapon. The move states swap families on the next move act: `S_MOVE_NON_COMBAT` takes `ACT_MOVE_NO_AIM` to `S_MOVE_NO_AIM` while `C_WEAPON_WIELDED` holds, and the reverse. The idle has no such swap; it changes clips through the modifiers only ([idle-stance.md](idle-stance.md)).
- The combat states' default clips are themselves armed: `ANIM_WALK_START_0` plays the rifle no-aim walk start's lower, head-torso, and arms clips with no modifier active, `ANIM_FLICK_120L_NO_AIM` the rifle no-aim flick, and `ANIM_MOVE_NO_AIM` and the walk starts the rifle hand pose, while the non-combat states play the unarmed clips and the non-combat hand pose. So with any weapon wielded, the lower body's walk starts and flick turns, and their root motion, are rifle clips whatever the weapon's class.
- `C_HEAVY_WEAPON`, the selected slot being the heavy slot in any state, replaces the idle with `S_IDLE_AIM_FOCUS` (the minigun's idle), takes the aim-strafe moves to `S_MOVE_AIM_FOCUS*`, and blocks the idle's equip and unequip transitions: `ACT_ON_EQUIP_WEAPON` from `S_IDLE` and its no-aim transitions to `S_IDLE_TRANS_TO_AIM` needs it false.
- `C_PLANTED_EXPLOSIVE_WIELDED` swaps the grapple-attach and upside-down stunt states for their planted-explosive variants, and blocks the upside-down rotations, the reel to a helicopter, and some stunt-to-driver moves.
- `C_RPG_GUITAR_CASE` and `C_STUPKA_210` gate the mortar states.
- No weapon condition guards a transition into the ledge climbs, the parachute, the wingsuit, swimming, or a vehicle entry.

## The base layer's weapon tasks

The base graph's state tasks act on the inventory directly. Each runs on entering its state:

- `NWeaponUnequipTask` ([`NWeaponUnequipTask_OnEnter`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon_animation::NWeaponUnequipTask_OnEnter)) acts on the wielded weapon. Most instances have `Instant` set, which unequips a player's weapon at once ([`WeaponBase::OnUnequip`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##vfunc-OnUnequip)); they run on every vehicle entry, seat, and seat change, the motorbike, pogostick, and cow rides, the mounted-gun pickups and seats, the wingsuit openings and its boost, barrel-roll, evade, and flinch states, free fall and fast fall (`S_FALL_TO_FREEFALL`, `S_FREE_FALLING`, `S_FAST_FALLING`, `S_JC_SEQUENCE_TO_FREEFALL`, `S_RAGDOLL_TO_FREEFALL`), the dives under water, the hit-reaction flights, the ragdoll, the get-up, dying, and the guitar case's exit. The instances without it queue `UB_ACT_HOLSTER` instead, on the mounted-gun and cow-ride entries, the crawl, and the surface-swim starts. Both return the player to normal aim ([`Player::SetAimMode`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::player::Player##func-SetAimMode)).
- `NDropWeaponStateTask` ([`NDropWeaponStateTask_OnEnter`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon_animation::NDropWeaponStateTask_OnEnter)) is configured for the heavy slot ([`E_SLOT_HEAVY`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::inventory::WeaponSlot##variant-E_SLOT_HEAVY)) and drops its weapon in any state through [`Inventory::DropWeapon`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::inventory::Inventory##func-DropWeapon). It runs on every grapple and tether fire, grenade throw, fall, free fall and fast fall, parachute opening and parachute-to-fall, wingsuit opening, boost, and fall, reel-in to a fall, vehicle and motorbike entry, surface swim, crawl, and hit-reaction flight and stumble, so a heavy weapon is dropped by the first of these the character enters. That the drop also takes a holstered heavy weapon is read from the code and not seen in game.
- `NStopUsingWeaponStateTask` ([`NStopUsingWeaponStateTask_OnEnter`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon_animation::NStopUsingWeaponStateTask_OnEnter)) stops using the selected weapon in the ragdoll, crash, dying, drowning, and get-up states.
- `NWeaponHideInVehicleTask` ([`NWeaponHideInVehicleTask_OnEnter`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon_animation::NWeaponHideInVehicleTask_OnEnter)) has two instances in every vehicle seat and seat-transition state, one for the two-handed slot and one for the special slot. In a vehicle with [`Vehicle::m_HideCharacterWeapons`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/vehicle::vehicle::Vehicle##field-m_HideCharacterWeapons) set it makes that slot's holstered weapon holstered-invisible until the state exits.
- `NSetWeaponStateTask` runs in `S_GUITAR_CASE_EXIT` alone.
- `NSetWeaponPredefinedBoneTask` moves guns between bones: `clear_right_hand` (the gun to the left hand) in the grenade throws, explosive planting and detonation, and some grapple-attach and landing states; `clear_left_hand` across the on-foot locomotion, the jumps, the grapple fire and reel states, and the motorbike aim states, most instances gated on the `CLEAR_LEFT_HAND` segment. See [hands-locomotion-and-state.md](hands-locomotion-and-state.md), "The attach-bone table is rewritten every pass".
- `NWeaponOffhandIKTask`, `NAimIKTask`, and `NStateTask_InputWeaponTask` (the base layer's weapon input) run in many states each.

Which states own the tasks, from the decoded base graph: the unequip task runs in 220 states, 208 of them instant. Besides the families above, the instant ones include every grapple reel into a vehicle's seat, onto a motorcycle, and into a helicopter, the stunt positions' entries and melee, the vehicle exits that roll out or hang, and the wingsuit's opening from the parachute, which is the one parachute state to carry it: opening the parachute itself puts nothing away, and only drops a heavy weapon. The 12 without `Instant` are the mounted-gun entries, the pogostick and cow rides, the crawl, and the three surface-swim starts. The hide-in-vehicle task's two instances share 63 states, every one a seat, a seat change, or a seat's entry or exit. The stop-use task runs in 19, the ragdoll, crash, dying, drowning, and get-up states; the heavy-weapon drop in 133, 69 of which also unequip. No partial, sync, or additive graph carries any of them.

`NWeaponEquipTask` ([`NWeaponEquipTask_OnEnter`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon_animation::NWeaponEquipTask_OnEnter)) and `NInventorySelect` occur in none of Rico's graphs, so nothing in the player's graph equips a weapon on its own. The inventory permission tasks (`NSetInventoryPermissions`) are the graph's other effect on the inventory; which states carry them is in [aim-state.md](../gameplay/aim-state.md).

## The upper-body actions

`rico_partial_global` holds the upper-body actions: the `S_UB_*` draw, holster, and switch states (per source and destination slot, with parachute variants), the reloads (per weapon family, with `_LEFT` variants), the shotgun pump, the sniper bolt, the pickups (per weapon id), the grenade throws, the explosives, and the parachute's arm states. Its initial state, `S_GLOBAL_PARTIAL_NULL`, is its idle. Its transitions key on the per-weapon `C_<WEAPON>` conditions, `C_WEAPON_WIELDED`, the next-selected conditions, the magazine conditions, and `C_LEFT_HAND_WIELD`, which selects the left-handed reload and pump states (`S_UB_RELOAD_RIFLE_LEFT`, `S_UB_RELOAD_RIFLE_BACK_LEFT`, `S_UB_RELOAD_SHOTGUN_START_LEFT`, `S_UB_RELOAD_MACHINE_GUN_VDOVA_89_LEFT`, `S_UB_RELOAD_GRENADE_LAUNCHER_UPU210_LEFT`, and `S_UB_SHOTGUN_PUMP_LEFT`).

Every `S_UB_*` state has an unconditional transition on `ACT_ABORT_WEAPON_PARTIAL` back to `S_GLOBAL_PARTIAL_NULL`; the parachute arm states, the detonations, and the explosive reloads (`S_JC_UB_*`) do not. The actions' effects on the weapon come from their clips' track messages, which [`WeaponBase::HandleTrackMessage`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-HandleTrackMessage) answers: the draw clip's equip message calls the equip virtual ([`OnEquip`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##vfunc-OnEquip)) and the holster clip's unequip message the unequip virtual; others start reloads, eject magazines, fire attached effects, complete pickups, and detach mounted guns. The character's message handling picks the weapon a message addresses by a target in the message: a fixed slot, the selected slot, the wielded weapon, the grenade slot, or the interaction's weapon (read in the symbol dump; unverified). A clip still playing therefore equips or unequips its slot's weapon when its message fires, whatever happened to the weapon since the clip began.

The draw act ([`Character::DrawWeapon`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-DrawWeapon) queues `UB_ACT_DRAW`) adds the `S_UB_DRAW_*` state's visual, the drawing state bit for the state's length, permission blocks for the draw, a bone task on the two-handed draws, and `ACT_ON_EQUIP_WEAPON` to the base layer, which from `S_IDLE` plays `S_IDLE_TRANS_TO_AIM` and which no other base state listens for. None of this is a precondition of a later state. Selecting a slot alone ([`Character::SetSelectedWeaponSlot`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-SetSelectedWeaponSlot)) plays nothing and equips nothing.

The partial global layer's animation set, `rico_partial_global.asb`, is not in any archive's file table under that name: the tables hold the hashes of `rico_base.asb` and `rico_partial_sync.asb` only, and its name appears only in a resource dependency list. It was not recovered, so which bones the upper-body action clips drive is unverified.

## Recoil and the vertical aim blend

The firing kick is an additive. Rico's additive graph is almost entirely vertical aim blend states (`CVerticalAimBlendState`), and its aim nodes in `rico_additive_sync.asb` carry one recoil clip per gun: `rico_loco_idle_rev_aim0_recoil_rarm_add` and `rico_loco_idle_rev_aim0_recoil_larm_add` for the pistols' modifier, `rico_loco_idle_rifle_aim0_recoil_add` and its run variant for rifles, `rico_loco_run_rpg_aim0_recoil_add` for launchers, and parachute and motorbike variants.

[`VerticalAimBlendState::UpdateSamplers`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/aim::aim::VerticalAimBlendState##func-UpdateSamplers) drives them. When the state's recoil flag is set and a weapon is wielded, it runs one recoil sampler per gun of the wielded weapon ([`WeaponBase::GetNumRecoilAnimationNeeded`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-GetNumRecoilAnimationNeeded)), each at its gun's own time since its last shot ([`WeaponData::m_TimeSinceLastFire`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##field-m_TimeSinceLastFire)) and at the weapon's maximum recoil weight until the clip ends. The aim's yaw and pitch are measured from the left arm when the wielded weapon sits in the left hand, from the right arm for a heavy weapon and the grapple fire, and from the head otherwise. So the recoil is per gun, and per arm for the pistol pair, but it follows the one wielded weapon and plays only inside the aim states. Rico's graphs have no recoil state of their own.

## Clips, body parts, and the hand poses

An animation node in an `.asb` lists up to about a dozen clip slots, each a separate Havok spline-compressed clip with a binding naming the bones it drives. The body is split by clip rather than by a bone mask: Rico's on-foot nodes play a lower-body clip, a head-torso clip, an arms clip, and a hand-pose clip from `hands_bank/`, and some nodes use `noarms`, `larm`, `rarm`, `upper`, `torso`, or `head` splits instead. The splits are inferred from the clip names; only the hand-pose clip's binding was read.

`hands_bank/hands/pose_hands_rico_rifle_right_hands.ban` binds every finger bone of both hands (the thumb, index, middle, ring, and pinky chains, with the ring's and pinky's in-hand bones) and nothing else. The hand poses are one clip per weapon class, both hands together: `rifle_right`, `rifle_left` (used once, in a grapple-attach state that moves the rifle to the left hand), `rev` (the pistols, both hands), `rpg`, `expl_prime`, `noncombat`, and grapple variants. Apart from the rifle's right and left pair there is no per-hand pose.

Which hold plays is chosen per weapon class, through the base layer's modifier variants (`WEAPON_MODIFIER_ASSAULT`, `_REV`, and `_RPG`, their `AIM_` and `EQUIPPED_` forms, and `C4`; see [idle-stance.md](idle-stance.md)), not per weapon: every rifle, submachine gun, shotgun, and sniper rifle shares the `ASSAULT` set, and the pistols and revolvers the `REV` set. A modifier variant swaps a whole node, its lower, arms, head-torso, and hand clips together. Per-weapon clips exist only in the upper-body action layer (the reloads, pumps, bolts, pickups, draws, and switches), keyed by weapon id.

## Playing a clip from code

The engine can play any clip by path on a layer. [`AnimationController::PlayCustomAnimation`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::AnimationController##func-PlayCustomAnimation) acquires the clip resource for the path, builds an [`AnimationInstance`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::pose_producer::AnimationInstance##func-Construct) of it over the controller's skeleton, and hands it to the layer's driver ([`AnimationDriverTransition::PlayCustomAnimation`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::pose_producer::AnimationDriverTransition##func-PlayCustomAnimation)) with a blend time. The instance's creation context carries its easing, start and finish trims, speed, mirror flag, and loop mode; with the mirror flag set the clip is bound mirrored. The call `PlayCustomAnimation` makes to acquire the resource is labelled `CAnimationTrack::GetHandle` by the disassembler, which does not fit its use; what that function is beyond this call is unverified. The clip resource for a path also comes from [`AquireAnimation`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::pose_producer::AquireAnimation), which takes it from the global resource cache by the hash of the path's compiled name, or from [`AquireAnimationFromCache`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::pose_producer::AquireAnimationFromCache) with an explicit cache.

A layer's blender ([`Blender`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::pose_producer::Blender)) samples its instances: [`Blender::AddSampler`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::pose_producer::Blender##func-AddSampler) registers an instance's Havok animation control with the blender's animated skeleton and keeps a reference to it, [`Blender::ClearSamplers`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::pose_producer::Blender##func-ClearSamplers) removes them all, and [`Blender::UpdatePose`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::pose_producer::Blender##func-UpdatePose) samples them into a pose. The functions the disassembler names as the blender's constructor and its time update are something else (the constructor builds a Havok animated skeleton into a shared pointer, and the time update computes a bone's model-space transform on demand), so neither the blender's construction nor its time update is established. The instance's time, weight, and duration accessors carry their names only in the disassembler; unverified. Whether a blender can sample outside the pose job, which supplies the reference pose and the buffers, is unverified.

## Unverified

- What the next-selected, magazine, and aiming conditions test, and the character's choice of the weapon a track message addresses.
- The bone lists of the arms, head-torso, lower-body, and recoil clips; only the hand-pose clip's was read.
- The upper-body action layer's clips, whose animation set was not recovered.
- That the heavy-weapon drop task takes a holstered heavy weapon in play.
