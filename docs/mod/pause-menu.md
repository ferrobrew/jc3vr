# The VR menu in the pause menu

The mod's VR settings live inside the game's own pause menu. One `VR` entry in the root menu, directly below `OPTIONS`, opens the game's settings screen with the VR pages as tabs on the screen's own tab bar, each page described in Rust, so the pages are drawn by the pause movie's own tab bar, list, rows, option picker, slider, message box, sounds, and gamepad and mouse handling. The mod ships no Flash of its own and does not patch `pause.gfx`: it reaches the movie through the Scaleform value API from five detours on [`PauseUI`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::PauseUI) and one on [`UIBase::InvokeImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_base::UIBase##func-InvokeImpl). The engine side (the movie's structure, the commands it sends, and what code outside it can reach) is in [`engine/pause-menu.md`](../engine/pause-menu.md). The code is `payload/src/pause_menu/`.

The feature is behind `pause_menu.enabled`, on by default, with a checkbox in the debug UI's HUD tab (under "Pause menu", which also shows the menu state). The setting is read when the pause menu opens, so a change takes effect the next time it does. With it off, no entry is added and every hook calls through.

## Route

The VR settings need a heading with children, and the movie offers two structures for one. Folders (an entry that opens a sub-list) are the developer menu's: a folder is drawn on plain debug text fields with the main buttons hidden, so it would not look like the shipped menu. The settings screen's tab bar is the other, and it is the one used: it is the shared navigation bar that the game's other menus also use (see [the engine doc](../engine/pause-menu.md#the-tab-bar)), the settings screen still names a tab per native page before hiding it, and its selectors, shoulder-button hints, mouse handling, and sounds are the movie's own. So the VR settings are one `VR` entry whose screen shows the VR pages as tabs. The movie's own code opens the settings screen, and the mod replaces the page the screen is about to read while the game fills the pages. The rest of the game's pages stay as the game built them.

The entry's label is plain text: a label beginning with `&` or `#` would be looked up as a localisation key. The registry is capped (`MAX_PAGES` in `pause_menu/pages/mod.rs`) at the tab bar's selector count ([`TAB_COUNT`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::SettingsUI)); a page past the cap gets no tab and a warning is logged.

## The root entry

The entry is in the root menu the pause menu opens on: the in-game menu, or the front-end menu on the title screen (`model/root.rs` decides from [`m_IsValidMenu`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::PauseUI##field-m_IsValidMenu)). It sits directly below `OPTIONS`. The movie can only append or prepend to a list from outside, and the engine prepends its own entries (resume and the rest) and appends a few (go online), so the entry is appended while the movie's `InitMenu` builds the root menu, right after the options entry and before the engine's appends; see [the engine doc](../engine/pause-menu.md#menus-and-entries) for how a root menu is ordered. In the in-game menu the movie adds the main-menu entry right after the options entry in the same call, and only when the main-menu list is built first. So H6 runs that `InitMenu` with the main-menu list marked invalid in the valid-menus array, appends the VR entry, runs `InitMenu` again (every other list is built by then, so it builds the main-menu list alone), and appends a main-menu entry as the movie builds its own: labelled `&pause_main_menu`, of type [`OPTION_MAIN_MENU`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::PauseUI). The in-game menu then reads resume, the engine's other entries, `OPTIONS`, `VR`, `MAIN MENU`, and go online. On the title screen the membership link, when the SKU shows one, is added in the same call as the options entry, so there the VR entry follows it. When `InitMenu` could not be run that way (it was queued, or the screen was not active), H1 appends the entry to the end of the root menu after the fill and logs a warning.

The root menu's selection opens nothing on the settings screen: only the options menu's dispatch does, and the document's menu state, which picks the dispatch, is private. So the entry is an event entry ([`OPTION_EVENT`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::PauseUI)) posting `jc3vr.pause_menu.open` (`ENTRY_EVENT` in `model/command.rs`), with no confirmation and without closing the menu. Selecting it sends that as the `event` command, which H3 takes (the engine never sees it) while the document is still inside its selection handler, and opens the screen through the document's public methods (`runtime/root.rs`): it switches the entry's type to the graphics entry's ([`OPTION_GRAPHICS`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::PauseUI)), calls `ShowPauseFromHideCredits`, which puts the document in the options menu's state without laying out another list, and calls `OnSelect`, whose options-menu dispatch finds the VR entry still selected and opens the settings screen on the graphics page; then it switches the type back. The entry object is reached for this through a member the mod sets on the main-button container (`jc3vr_vr_entry`), since the lists are private and no managed value is held across frames. The nested selection plays the movie's selection sound a second time; H3 drops that one. Without a gamepad, the opening also shows the back button the options menu shows (`MCI_back_letterbox`).

Backing out of the VR screen returns to the root menu. The document's own back leaves the settings screen for the options menu's state and sends `persist_changes` last; H3 then calls `SwitchToMenu` with the root menu, which lays it out again with the VR entry highlighted (the document remembers each list's selection), puts the document back in the root menu's state, and hides the back button. A further back closes the pause menu, as it does from the root menu. When an opening never reached the populate (the movie refused a call), H3 does the same at once.

## Tabs

The settings screen's own tab switch keeps each tab's scroll position in a private array keyed by page slot, which the native pages share, and it cannot be read or cleared from outside the movie: a VR tab switch through it would leave a VR page's position for the native page opened next in the same pause (see [the engine doc](../engine/pause-menu.md#the-settings-screen)). So the VR tabs never go through it. Every VR tab is shown in the graphics page's slot, and the mod switches tabs itself and keeps the VR tabs' positions apart (`pause_menu/model/tabs.rs`).

- Opening: the screen sets its tab bar up for the native pages and hides it after the page is installed, so on the next update (H4) the mod names one selector per VR page (`SetButtonVariables`), unlocks those and locks the rest (`SetButtonLocked`, which also lays the bar out), sets the bar's select callback to the pause document's own `Invoke` method, selects the shown tab, and shows the bar.
- Choosing a tab: clicking a selector or a shoulder-button hint calls the callback with the tab's index, and the document's `Invoke` sends that index, as text, as a command. The command detour (H3) recognises the hashes of those names (`TabCommands`, hashed with the engine's own command hash on first use), never passes them to the game, and records the tab; the update switches when the list is in its root state. A gamepad's shoulder buttons reach the document as `OnNextTabButton` and `OnPrevTabButton`, which it ignores on the settings screen; H6 steps the bar's own cycling for them, which ends in the same callback.
- Switching: the mod reads the old tab's position (`GetTopIndex`, `GetSelectedRow`), leaves its page (running its `on_close`), writes the new page's rows into the shown page object and redraws (`RefreshCurrentScreen`, which also rewrites the list title), restores the new tab's saved position fitted to its current rows (`DeHighlightCurrent`, then `RestoreSavedState`), and moves the bar's selection. A tab not visited yet opens at its top. There is no slide animation; the native switch's slide belongs to the screen's own switch.
- Leaving: backing out of the screen saves the tab's position, hides the bar again, restores the row clips' label style (below), and returns to the root menu. The VR entry reopens on the last tab, at its position, until the menu closes; the memory is per pause.

The callback stays set after the VR screen closes, until the settings screen next opens and sets its own. The only other caller of the hidden bar is the controls screen's shoulder buttons, whose tab commands the detour drops while no VR tab is shown.

## Section headers

The settings list has no header row, no separator row, and no group title of any kind (see [the engine doc](../engine/pause-menu.md#row-objects-and-widgets)), and an empty row cannot stand between groups because the list's up and down stop at one. The closest native presentation is the list's own title: a one-line text field over a separator, of about a row's height. A header is therefore drawn on a row clip as the title: its label in the list title's text format (read from `MCI_title` with `getTextFormat` and applied to the row label with `setTextFormat` and `defaultTextFormat`, since the list sets the label's text on every redraw), over the separator every row clip already draws, with nothing on the right. The row itself is a key-binding row with no key text, so selecting it only plays the refusal sound.

The list reuses its clips as it scrolls, so each frame the row pass gives each clip the style of the row it now shows; `HeaderStyles` (`pause_menu/model/headers.rs`) changes a clip only when the kind of row it shows changes. A clip's own format is kept on its row container (a dynamic class) the first time it is styled, and every styled clip gets it back when the player leaves the VR screen or a native page is put in place, so the native pages never see a header style.

A header is not selectable: when the highlight lands on one, the update moves it on with the list's own `HighlightNext` or `HighlightPrev`, in the direction it was going (`skip_header`), or the other way at the top or bottom of a page. A page opening on a header moves to the row below it.

## The session

`pause_menu/model/state.rs` holds the state machine and `pause_menu/runtime/session.rs` the shared session:

- `Closed`: no VR entry in the loaded movie.
- `EntryAdded { pages }`: the root menu has the VR entry, which opens on `pages` tabs.
- `Shown { pages, page }`: the settings screen shows the VR tabs, with page `page` selected.

Activation resets the session to `Closed` and adds the entry (`EntryAdded`), recording the root menu it is in. The VR entry opening the settings screen moves it to `Shown` on the last tab shown this pause; choosing another tab moves it to `Shown` on that tab; leaving the screen returns it to `EntryAdded`; the menu deactivating, or its movie unloading, returns it to `Closed`.

A page's `on_close` (which cancels a calibration in progress and drops a pending reset confirmation) runs whenever a transition leaves the page, whatever the path: the player switching to another tab, the player backing out of the settings screen (`persist_changes`), the menu deactivating (H5), the movie unloading (`inactive`), the next activation finding a stale session, a reinstall failing, or a refresh off the capture thread putting the native page back. The movie sends `persist_changes` only when the player backs out of the settings screen; the pause key, the UI manager forcing the menu closed, and game-state changes deactivate the menu without it, and H5 is what covers them. Every path goes through one transition in `runtime/session.rs`, which compares the state before and after (`left_page` in `model/state.rs`) and returns the page left, so `on_close` runs once per stay however many of these fire; it runs after the session lock is released. The session also keeps the shown page's contents (to resolve its rows' commands), the live-value diff, a deferred-rebuild flag, the populate flag described under H3, the VR entry's opening flag (raised by H3 around the opening and lowered by H2, which installs a VR page only when it is up, so a flag still up afterwards means the screen never populated), the flag that drops the opening's second selection sound, the root menu, the tabs' memory, a pending tab and the deferred tab-bar setup, the row the highlight was last on, the row clips' label styles, and the pause screen's address (for H6).

The session lock is never held across a call into the movie or into an item's functions: a call into the movie can re-enter the command hook synchronously (a widget playing a sound sends an event command), and the lock is not re-entrant. Each hook copies what it needs, releases the lock, works, and writes back; a generation counter tells a write-back whether the page changed in between.

## Hooks

H1 to H4 and H6 run on the UI capture thread. H1 to H3 run inside the root movie's advance; H4 is the pause screen's per-frame update and H6 its input, whose threads are checked before any value is touched. H5 runs on whichever thread requests the deactivation and never touches the movie.

H1 is a detour on [`PauseUI::OnActiveImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::PauseUI##func-OnActiveImpl). It closes any stale session, records the pause screen as activating for H6, and calls the game, which builds the fresh movie's menus; H6 adds the VR entry from inside that (see [The root entry](#the-root-entry)) and records the pause screen's address. When the session is still closed afterwards and the feature is on, H1 appends the entry to the end of the root menu. The root menu is laid out by the game's `SwitchToMenu` at the end of the fill, so the entry shows.

H2 is a post-detour on [`PauseUI::PopulateSettings`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::PauseUI##func-PopulateSettings), which the movie's `populate_settings` command and the update's refresh both call. When the screen is opening (the populate flag is up), the VR entry's opening flag tells whether the VR entry opened it; the hook lowers it. When the VR entry opened the screen, the hook builds the last tab shown this pause (the first, the first time), encodes its rows, writes a page object `{m_Name, m_Settings}` over the graphics page's slot ([`PAGE_GRAPHICS`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::SettingsUI)) of `m_SettingsArray`, and asks the next update to put the VR tabs on the bar. A refresh while a VR tab is shown reinstalls that tab's page. The movie then shows it: the panel title is the page title. When a native entry opened the screen, the session leaves any VR page, the native pages are untouched, and the hook hides the tab bar and restores any header-styled row clip. A failed install logs an error and leaves the native page, and so does a populate off the capture thread: the game has just put its graphics page back in the slot, so the session leaves the VR page rather than go on describing it.

H3 is a detour on [`PauseUI::HandleCommandImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::PauseUI##func-HandleCommandImpl). It decodes the command and its arguments (`model/command.rs`) and routes it:

| Command | Condition | Handling |
|---|---|---|
| `populate_settings` | always | calls through with the populate flag raised, so H2 knows the screen is opening |
| `event` with `jc3vr.pause_menu.open` | the entry is added and no VR page is shown | opens the VR screen from the root menu (see [The root entry](#the-root-entry)); the game never sees it |
| `event` with `jc3vr.pause_menu.open` | any other state | dropped |
| `event` with `jc3_gui_msg_box_show_hide` | the VR entry is opening the screen | dropped once: it is the nested selection's sound, and the root menu's own follows |
| `set_setting_value` | id in the VR band, row of the shown page | applies the value to the item; the game never sees it |
| `get_key_for_action` | id in the VR band, row of the shown page | runs the button's action; the game never sees it |
| a tab command | a VR tab is shown | records the tab for the next update; the game never sees it |
| a tab command | any other state | dropped |
| either of the two | id in the VR band, any other state | dropped, never reaches the settings manager or the key capture |
| `restore_default_keymap` | a VR page is shown | resets the page's value items to their defaults and rebuilds the page |
| `persist_changes` | a VR page is shown | calls through, then saves the tab's position, leaves the page (running its `on_close`), hides the tab bar, restores the row clips' label style, and returns to the root menu |
| the base `inactive` | always | calls through, then closes the session (running the page's `on_close` if H5 has not) |
| anything else | | calls through |

The command detour routes regardless of the toggle; with no page installed it passes everything through except a VR-band id and the entry's event, which cannot occur. String arguments are read as the engine reads them (a managed string through its string-data pointer) and only compared with the two names above. The movie's reset-all sends one `set_setting_value` per row, headers and buttons included; items that hold no value ignore it.

H4 is a post-detour on [`PauseUI::UpdateImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::PauseUI##func-UpdateImpl). While a VR page is shown and the screen is active, it first finishes opening the VR tabs (once per opening, see [Tabs](#tabs)), then switches to a chosen tab when the list is in its root state, then runs the page's per-frame hook (`on_frame`, which may ask for a rebuild), then a deferred rebuild, then, in the root state, moves the highlight off a header, and last runs the row pass: the header styles and the live values. Rebuilds are deferred to here because the command hook runs inside the movie's own handler, which redraws the selected row after the command returns. A rebuild waits while the list is not in its root state (the settings screen's `IsInRootState` is false: an option picker or message box of its own is open), because the list sends the picker's answer to whatever row is highlighted when it closes, and a rebuild in between would move that to another row; the request stays and runs on the first frame the list is back. A rebuild writes the new rows into the shown page object, calls the settings screen's `RefreshCurrentScreen`, rewrites the list's title, and focuses the page's first button with the list's `MoveSelectionHighlight` and `SetHighlightedRow` (both are needed: the refresh leaves the first row highlighted and selected, and highlighting alone would leave the selection behind). The session records the new page as soon as the refresh has run, since from then on the rows' ids refer to it; a refused focus call is only logged. A rebuild that fails before the refresh leaves the old rows and the old record. The record is also skipped when the session moved on during the rebuild (H5 closed it from another thread).

H6 is a detour on [`UIBase::InvokeImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_base::UIBase##func-InvokeImpl), through which the engine calls every AS3 method on a screen, among them [`PauseUI::OnActiveImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::PauseUI##func-OnActiveImpl)'s `InitMenu` and the document's input handlers, which [`UIBase::BaseOnManageInput`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_base::UIBase##func-BaseOnManageInput) calls by name. An `InitMenu` on the screen H1 is activating, with the feature on, a root menu valid, the call on the capture thread, and the screen active, runs as described under [The root entry](#the-root-entry); every other `InitMenu` calls through. After any other call, when it was `OnNextTabButton` or `OnPrevTabButton` on the pause screen, a VR tab is shown, and it ran on the capture thread, the hook calls the tab bar's method of the same name, which steps to the next or previous tab and reports it through the callback. Every other call, and every other screen's, only pays a name comparison and an atomic load.

H5 is a post-detour on [`PauseUI::OnDeactivateImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::PauseUI##func-OnDeactivateImpl), which [`UIBase::Deactivate`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_base::UIBase##func-Deactivate) calls for every deactivation of the loaded menu, before the movie is unloaded. It closes the session and runs the shown page's `on_close`, as described under the session. The game saves its own settings in the same function.

## Values and threads

`pause_menu/gfx/` wraps the Scaleform value API ([`ValueObjectInterface`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::ValueObjectInterface)). `CaptureThread::current()` returns a token only on the thread [`UIManager::m_CurrentCaptureThread`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_CurrentCaptureThread) names; it is neither `Send` nor `Sync`. `GfxValue<'t>` is an owned, boxed value borrowing the token: the box pins a managed value (it is a node on the movie's external-references list), and dropping it releases the reference through [`ObjectRelease`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::ValueObjectInterface##func-ObjectRelease). Because the value borrows the token, it cannot be stored past the hook call, so no managed value is held across frames. The object calls (members, elements, methods) accept only an object, an array, or a display object ([`VT_OBJECT`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::Value), `VT_ARRAY`, `VT_DISPLAY_OBJECT`); a managed string or closure is refused rather than passed to the object interface. The hooks hold the pause screen as a pointer (`gfx::Screen`), never a `&mut PauseUI`, because a call into the movie can re-enter the game's command handler, which writes the screen's fields through its own pointer; a field is read through its raw place, and the screen is borrowed only for the length of one `CreateObject` or `CreateArray` call. Every access starts again from the screen's [`m_Clip`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_base::UIBase##field-m_Clip), copied with an added reference ([`ObjectAddRef`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::ValueObjectInterface##func-ObjectAddRef)).

Arguments and fields are written as unmanaged values laid out the way the engine's own [`SetIntField`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/ui::ui_base##func-SetIntField) and [`SetStringField`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/ui::ui_base##func-SetStringField) build theirs (a C string pointer for a string, an int for an int), which the movie copies. Row objects and arrays are created with [`UIBase::CreateObject`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_base::UIBase##func-CreateObject) and [`CreateArray`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_base::UIBase##func-CreateArray), as [`SettingsUI::AppendSettingToggle`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::SettingsUI##func-AppendSettingToggle) does. The command handler reads `set_setting_value`'s arguments as plain ints without checking their type; the mod decodes ints, and numbers with an exact integer value, and treats anything else as a malformed command it passes through.

## The page model

A page is data, defined beside the settings it edits (`pause_menu/model/page.rs`) and registered in `PAGES` (`pause_menu/pages/mod.rs`):

- `PageDef { tab, build, on_close, on_frame }`: the tab's label, a `fn() -> Page` that builds the page's current contents (called on open and on every rebuild), an optional `fn()` run once when the page's stay ends, by whichever path (a tab switch included; see the session), to reset its state, and an optional `fn() -> ButtonOutcome` run every frame while the page is shown, for work that runs over time; returning `Rebuild` rebuilds the page.
- `Page::new(title)` with the builders `.header(text)` (a section header, see [Section headers](#section-headers)), `.text(text)`, and `.item(item)`.
- `Toggle { label, get, set, default }` over a `bool`.
- `Choice { label, options, get, set, default }` over an index into a static list of labels.
- `Slider { label, range, format, get, set, default }` over an `f32`: `SliderRange::new(min, max, steps)` maps `[min, max]` onto the integer notches `[0, steps]` (the movie's left and right step a tenth of the notches, truncated to an integer, so the registered pages use notch counts that are multiples of ten, which a registry test checks), and `SliderFormat::new(decimals, suffix)` says how the value reads in the label.
- `Readout { label, read }`: a `fn() -> SmolStr` shown on the right and refreshed every frame.
- `Button { label, caption, action }`: selecting it runs `action`, which returns `ButtonOutcome::Stay` or `ButtonOutcome::Rebuild`.

The accessors are plain function pointers, so non-capturing closures work (`get: || CONFIG.lock().x`). They run on the capture thread inside the hooks, without the session lock, and must not call into the movie.

A step-by-step page (the body calibration) keeps its step in a static beside its definition. Its `build` lists the current step's rows, and its buttons and per-frame hook return `Rebuild` when the step changed; H4 then reinstalls the page and focuses its first button, so each step puts its main action first. Text rows are one upper-cased line each, so instructions are split over several rows. The message box is not used for steps: the list only routes its input while its own private state says it opened it.

## Pages

Four pages are registered, in this order, as the tabs `BODY` (`controllers/body/menu.rs`, titled `VR: BODY`), `CONTROLS` (`controllers/menu/controls.rs`, `VR: CONTROLS`), `COMFORT` (`controllers/menu/comfort.rs`, `VR: COMFORT`), and `DISPLAY` (`controllers/menu/display.rs`, `VR: DISPLAY`). Labels are written in upper case in the source because that is how the movie shows them: it upper-cases row labels and key text, and shows option labels as given. A registry test checks it.

### Settings pages

`VR: CONTROLS` and `VR: COMFORT` edit the controller settings, the VR turn settings, and the grapple's view, and `VR: DISPLAY` the rendering and the floating panel; the other settings that could matter in the headset (the swimming level view, the grapple's blend tuning, the mouse sensitivity) stay in the debug UI. The stereo cameras' `stereo.ipd` is not offered: it spaces the eyes only for the flatscreen stereo, since under a headset each eye's view, its separation included, comes from the runtime. Their items are built by the `config_toggle!`, `config_slider!`, and `config_choice!` macros in `controllers/menu/mod.rs` from a place in the configuration (`|c| c.controllers.aim.gun`): the item reads and writes that place and takes its default from `Config::new`, so the page's reset (Y) restores the configuration's defaults. A change applies at once and goes through `config::edit()`, so the settings file saves it like any other change the user makes ([settings.md](settings.md)); the pages do no saving of their own. Nothing is saved when nothing changed, so browsing the menu does not create the file.

`VR: CONTROLS` has the master switch, the control scheme, the dominant hand, the move direction and the move stick's deadzone; the turn mode, the smooth-turn speed, and the snap angle (a choice of 15, 30, 45, 60, or 90 degrees; an angle saved between them shows as the nearest); the hand IK, hand aiming for the guns and the grapple, the aim assist strength, the gun aim marker, hiding the game's crosshair, the finger curls, and the physical hands and their strength; the HUD on the hands (the atlas as a whole, the weapon readout above the gun hand, and the tether readout above the forearm) and the world-placed markers; the holsters, the foregrip, recoil and its strength, the one-handed weight, the two-handed weight and its strength, scopes, the weapon wheel, the fire input drawing a weapon, the game switching away from an empty weapon, each hand firing its own dual-wielded pistol, the magazine reload with chambering by hand after a dry gun, the pouches' outlines, thrown grenades with the grenade pouch's side of the chest, thrown C4, and the wrist detonator; haptics, their strength, and the game's rumble; and the vehicles (the driver's weapons and mounted guns by hand; the six physical controls as one switch; the steering wheel's tracking, full lock from 60° to 180°, and response; the wingsuit's arm steering, what pitches it, the wrist tilt that pitches fully, the pitch's inversion, and its readout in the headset, a diagnostic; and the parachute handles, their marks, their height above the shoulders, the full pull, and the brake threshold). Its last section shows the settings file's state (`SETTINGS FILE`: `UP TO DATE`, `SAVING`, `FAILED, SEE LOG`, or `NOT SAVED`) and offers `RESET TO DEFAULTS`, which replaces the page with a confirmation. The confirmation's first, focused button keeps the settings; the second resets the controller, turn, and grapple comfort settings except the per-weapon sight calibration, which is measured rather than chosen. The display settings are left to `VR: DISPLAY`'s own reset (Y).

`VR: COMFORT` opens on a `VIEW` section with `RECENTER VIEW` and a `STATUS` readout, so the page opens with the recenter focused. The button asks for the recenter the F7 key does (`vr::request_recenter` with `roomscale::manual_recenter_kind`: yaw and height while the roomscale chase keeps the body under the head, the full re-base otherwise). The request is deferred to the start of the next frame because the menu runs on the capture thread in the middle of one, where the frame in flight holds the runtime lock a recenter in place would wait on. `STATUS` reads `LOOK AHEAD, THEN PRESS`, then `RECENTERING` until the frame takes the request (`vr::recenter_count` changes), `RECENTERED` for three seconds after, or `NOT DONE, SEE LOG` when a second passes without it (a running headset drops a request only before it has a head pose, which it logs); `NO HEADSET` while no VR session runs, since a request is then dropped. The `VIEW` section also has `STEADY VIEW ON FOOT`, the on-foot view anchored to Rico's root, and a `MOVEMENT` section follows it with `SMOOTH STICK MOVEMENT`, `MOVE ACCELERATION`, `MOVE DECELERATION`, and `NO TURNING ANIMATIONS` ([body/locomotion.md](body/locomotion.md)). A `GRAPPLE` section has `VIEW ON THE GRAPPLE` (`headpose.grapple.mode`: `HOLD STILL`, `KEEP LEVEL`, or `SWING WITH BODY`; [body/grapple-comfort.md](body/grapple-comfort.md)). The rest of the page has the posture, the roomscale chase and its deadzone, the crouch body fold and collision, the seated crouch depth, the head-in-geometry fade, and the comfort fade's out and in times, and a `VEHICLES` section ends it with the vehicle seat transition and the driving view (`FIT VIEW TO THE WHEEL` and `FIT VIEW IN BOATS TOO`, [input/steering-wheel.md](input/steering-wheel.md)).

`VR: DISPLAY` has a `RENDERING` section with the per-eye `RESOLUTION` (`vr.resolution_scale`, 0.5 to 2.0 of the runtime's recommendation), FSR's anti-aliasing and its sharpening and sharpness ([rendering/fsr.md](rendering/fsr.md)), and the foveated rendering ([stereo/foveation.md](stereo/foveation.md)), and a `FLOATING PANEL` section with the panel's distance and apparent size and `RETICLE PLACEMENT` (`hud.reticle_align`: `WHERE YOU AIM` or `GAME'S PROJECTION`; [hud.md](hud.md)). Each applies on the next frame, except that the OpenXR swapchain keeps the size it was created at: a resolution change resizes the scene at once, and the image sent to the headset follows when the game restarts, which two text rows under the slider say. The resolution also acts only while `vr.native_resolution` is on.

A test puts every value item of these pages through its whole range against a per-thread configuration, checks that each reads back what it wrote and that the file stays valid, and checks that the page's reset returns the defaults.

### Body calibration

`VR: BODY` opens on a summary: a `YOUR BODY` section with the player's saved dimensions (the `[body]` section of the settings file; the seated eye height among them, `---` when none is saved) and whether they are still the generic defaults, a `CALIBRATION` section with the `STANCE` choice (`STANDING` or `SEATED`) and the button that starts the calibration, a `SCALING` section with the body-scaling switches (`controllers.body.remap_head` and `remap_hands`), a `PROCEDURAL BODY` section with `BODY FROM YOUR HEAD` (`controllers.body.procedural.mode`: `OFF`, `TEST`, or `FULL`; [body/procedural-body.md](body/procedural-body.md)), `WALKING LEGS` (`controllers.body.procedural.gait`), `LEGS IN THE AIR` (`controllers.body.procedural.air_legs`), `HANDS OUT OF THE BODY` (`controllers.body.procedural.keep_out`), and `SHOULDERS FOLLOW THE HANDS` (`controllers.body.procedural.clavicles`), and an `ALIGNMENT` section with `BODY FACES YOUR TORSO` (`controllers.body.alignment.root_follow`) and `CHEST FACES YOUR TORSO` (`drive_chest`; [body/alignment.md](body/alignment.md)). The body turning to face the torso works alongside the procedural body, which plants and steps its feet as the body turns. The chest turn is the body IK's, which stands down while the procedural body owns the torso, so under `FULL` it acts only in the states the body hands back to the animation; a text row says so. `STANCE` defaults to `SEATED` in the seated posture (`controllers.roomscale.posture`) and in the automatic posture while it detects the player seated, and to `STANDING` otherwise; a choice lasts until the page is left, and is not saved. The calibration is a three-step flow, each step under a header naming it (`STEP 1 OF 3: HEIGHT`), with a short instruction, its main action first, a `STATUS` readout right below it, and its live readouts after. Standing:

1. Height: standing straight and looking ahead. `EYE HEIGHT, LIVE` is the head's height above the STAGE floor and `HEIGHT, ESTIMATED` the height derived from it. `CANCEL` returns to the summary, which is this step's way back.
2. Arm span: a T-pose with the controllers held. `CONTROLLER GAP, LIVE` is the distance between the two grip poses, `ARM SPAN, ESTIMATED` the fingertip span derived from it, and `HEIGHT, FROM STEP 1` the height step 1 measured. `BACK` returns to step 1; `CANCEL` to the summary.
3. Review: `SAVE` first, then the result under `MEASURED` (height, eye height, arm span) and `ESTIMATED` (the shoulders and the arm segments), then, when a seated eye height is saved, that value under `KEPT FROM THE SAVED BODY`, then `MEASURE AGAIN`: `BACK` measures the arm span again with the same height, `RETRY` starts again from step 1 (`BOTH STEPS`), and `CANCEL` returns to the summary. `SAVE` (`body::save`) validates the dimensions and applies them at once through `config::edit()`, so the settings file saves them.

A standing calibration does not measure the seated eye height, so it keeps the saved one, unless the new standing eye height is not above it. Seated, the player sits upright in the chair they play in:

1. Seated eyes (`STEP 1 OF 3: SEATED EYES`): `EYE HEIGHT, LIVE` as standing. The value becomes the saved `seated_eye_height`, where the seated eye reference starts and what the automatic posture's thresholds sit against ([the controllers doc](input/controllers.md#body-dimensions)). The height is not measured.
2. Arm span: as standing, but the height is estimated from the span, so the step shows `HEIGHT, ESTIMATED` from the live gap and `SEATED EYES, FROM STEP 1` in place of the measured height.
3. Review: `MEASURED` has the seated eye height and the arm span. `ESTIMATED` starts with a `HEIGHT` slider (1.20 to 2.40 m, a centimetre a notch) set to the estimate, for the player to correct; the standing eye height, the shoulders, the hand, and the arm segments below it follow the slider at once, and the slider's reset (Y) returns the estimate. `BACK` drops a corrected height along with the span. `SAVE` writes every value, measured and estimated.

Lengths read in metres to the centimetre (`1.68 M`), and `---` where there is no value. A T-pose leaves no hand free to point at the menu, so `MEASURE` starts a countdown of three seconds, then samples for one second; the page's per-frame hook feeds the capture. Step 1 takes the mean of the samples and step 2 the widest. A frame without a measurement is skipped, in the countdown and in the window alike, and the window needs five samples to count. A finished capture moves to the next step and rebuilds the page.

`STATUS` shows the countdown (`GET READY: 3 S`), the sampling (`MEASURING, HOLD STILL`), else the last problem, else whether the measurement is available (`READY TO MEASURE`). The problems are:

- `MEASURE` refused, or a window that got too few samples, because no VR frame is rendering (`NO HEADSET`), the session has no STAGE space (`NO FLOOR HEIGHT`), the STAGE space cannot be located (`HEADSET NOT TRACKED`), no controller snapshot is published (`NO CONTROLLERS`), or a grip has no valid position (`LEFT CONTROLLER LOST`, and the right). A window short of samples for no recorded reason shows `TOO FEW SAMPLES, RETRY`.
- A result outside the accepted ranges, with the value refused: a standing eye height under 1.0 m or over 2.3 m (`EYES TOO LOW: 0.95 M`, `EYES TOO HIGH: …`), a seated eye height under 0.7 m (`EYES TOO LOW: …`) or over 1.5 m (`STANDING? EYES: 1.68 M`), an arm span under 1.2 m or under 0.85 of the height (`SPAN TOO SHORT: …`), or over 2.4 m (`SPAN TOO LONG: …`). The step stays.
- On the review, `SAVE FAILED, SEE LOG`; otherwise `READY TO SAVE`, or `CHECK: SPAN OVER HEIGHT` when the arm span is more than 1.15 of the height, which is accepted but most likely means a standing calibration was taken seated. A seated height corrected out of range shows why `SAVE` does nothing: the refusals above for the standing eye height and the span, or `HEIGHT TOO SHORT` when the standing eyes would be no higher than the seated ones.

Every problem is also logged with its full reason (target `controllers`), at most one line a second, the next line counting those held back.

A grip's position counts whether the runtime measured it or inferred it, because arms spread in a T-pose are outside the cameras of an inside-out headset, which then reports the controllers' positions as inferred. The arm span has no upper bound relative to the height: the controllers cannot be further apart than the arms reach, so a span far over the height means the height is short, as it is when a standing step 1 was taken seated. How the dimensions are derived is in [the controllers doc](input/controllers.md#body-dimensions). Leaving the page abandons a calibration in progress. The flow's state machine is `controllers/body/calibration/flow.rs` and is unit-tested (both stances, the height correction, and the stance's default from the posture), as are the height estimate from the span, the values derived after a correction, the page's status texts, their fit in the row, and the log's rate limit.

## Row encoding

`pause_menu/model/rows.rs` encodes each item as the row object one of the movie's widgets draws. Every row sets `m_Type` (its id), `m_Format`, `m_Name`, `m_Value`, `m_DefaultValue` (the reset-all reads it for every row), and `m_NeedConfirm` (false).

| Item | Format | Other fields | Behaviour |
|---|---|---|---|
| Header | key | as Text | drawn in the list title's style and skipped by the highlight (see [Section headers](#section-headers)) |
| Text | key | `m_KeyText` empty, `m_Image` empty, plain `m_Interaction`, not customisable | selecting plays the refusal sound |
| Readout | key | `m_KeyText` is the value, not customisable | as above; the value is live |
| Button | key | `m_KeyText` is the caption, customisable, `m_Action` is the id | selecting sends `get_key_for_action` |
| Toggle | toggle | `m_Labels` `OFF`/`ON`, `m_Values` 0/1 | the option picker |
| Choice | toggle | `m_Labels` the options, `m_Values` their indices | the option picker |
| Slider | slider | `m_MinValue` 0, `m_MaxValue` the notch count | the value is written into the label |

Row ids (`pause_menu/model/ids.rs`) live in a band of their own far above the game's setting types and key actions, and encode the page's registry index and the item's index, so a command for a page no longer shown is recognised and dropped. Values are never negative: the list uses negative values as its own context-menu codes.

## Live values

The list shows a scrolling window of the page on a fixed set of row clips ([`ROW_CLIP_COUNT`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::pause_ui::SettingsUI)) under `MCI_settings_screen.MCI_panel.MCI_container.MCI_root.MCI_manager`. Each frame, H4's row pass asks each clip for the row object it shows (`GetData()`), decodes its id, sets the clip's label style for a header or another row, and computes the item's live text: a readout's value, a slider's label with its value, or a button's caption (the list replaces it with `...` when the button is selected, expecting a key capture). `LiveSlots` (`pause_menu/model/live.rs`) remembers what was last written per clip and asks for a write only when the clip's item or text changed; a write sets both the row object's field (`m_KeyText` or `m_Name`, so the list's own redraws show it) and the clip's text field, upper-cased as the list draws it. Any applied value or pressed button invalidates the diff, because the list has redrawn the row from its object. The pass never calls the row's `FillData`, which would restart the highlighted row's animation.
