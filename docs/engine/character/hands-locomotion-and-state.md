# Hands, locomotion, and character state

The weapon-to-hand attachment chain, the per-arm aim IK systems, the character's root-motion and collision-proxy movement path, and the per-tick signals that report what the player character is doing. Section 1 covers the weapon-attachment (prop) chain. Section 2 covers the two shipped per-arm aim IK systems. Sections 3 and 4 cover the character root, the displacement and proxy-input path, scene queries, teleport writers and their detection signals, the vehicle seat attach pose, root-motion summing, the proxy capsule, and pause. Section 5 covers the character state-bitflag words, the state-machine-hash predicates, vehicle class, grapple states, and the UI and pause signals.

The verified addresses, field offsets, and constants are in the pyxis defs: mainly [`Character`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character) and [`StateBitFlag`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/state::StateBitFlag), the [`equipment::weapon`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/equipment::weapon), [`animation::arm_aim_ik`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/animation::arm_aim_ik), [`input::locomotion`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/input::locomotion), [`physics`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/physics), and [`game_world`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/game_world) modules, and [`Clock`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock).

Related: [humanik.md](humanik.md) (the solver, the effector ids, and the injection seam), [skeleton.md](skeleton.md) (the Joint API and the pose pipeline), [aim-pipeline.md](../gameplay/aim-pipeline.md) (the aim point and fire direction), and [grapple-pipeline.md](../gameplay/grapple-pipeline.md) (grapple targeting). Interface points with the aim and grapple pipelines are marked inline.

## 1. Weapon-to-hand attachment (the props system)

### The weapon model follows a hand safe bone, not `UpdatePropEffects`

The name [`Character::UpdatePropEffects`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-UpdatePropEffects) suggests that it places the wielded weapon, but it does not. It does three things: a head-bone `SetJoint` on the [`SafeBoneIndex::HEAD`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-HEAD) safe bone, then [`Inventory::UpdateAttachmentEffects`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::inventory::Inventory##func-UpdateAttachmentEffects), then `UpdateBalloonHead`. It does not compute the wielded weapon's transform.

The weapon model's placement is a bone attachment. Each weapon carries, per weapon state, an `NBone::ESafeBoneIndex` that names the bone it rides:

- [`WeaponBase::GetCurrentBoneAttachement`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-GetCurrentBoneAttachement)`(weaponIndex)` returns [`WeaponData::m_lBoneAttachementPerWeaponState`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##field-m_lBoneAttachementPerWeaponState)`[m_State]`, which is one of the `ATTACH_HAND_*` safe bones.
- [`WeaponBase::ChangeBoneAttachement`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-ChangeBoneAttachement)`(bone, weaponIndex)` rebinds it.
- `CWeaponBase::IsLeftHanded` is `bone == ATTACH_HAND_LEFT`.

The relevant safe bones are [`ATTACH_HAND_RIGHT`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-ATTACH_HAND_RIGHT), [`ATTACH_HAND_LEFT`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-ATTACH_HAND_LEFT), [`ATTACH_HAND_RIGHT2`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-ATTACH_HAND_RIGHT2), [`ATTACH_HAND_LEFT2`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-ATTACH_HAND_LEFT2), [`RIGHT_HAND`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-RIGHT_HAND), and [`LEFT_HAND`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-LEFT_HAND), bound with their name hashes in the [`SafeBoneIndex`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex) enum (`NBone::ESafeBoneIndex`).

The transform chain is: weapon world ← hand attach bone ← character world. The `ATTACH_HAND_*` bones are dedicated attach points, and a gun on one takes the bone's world matrix as its own, with no offset matrix in between (see "The gun's pose in the hand is animated" below). Each hand has two: the primary one (`ATTACH_HAND_RIGHT`, `ATTACH_HAND_LEFT`), which a gun held in that hand rides, and the second one (`ATTACH_HAND_RIGHT2`, `ATTACH_HAND_LEFT2`), the support hand's grip point, which [`Character::UpdateSecondaryHandIKPass`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-UpdateSecondaryHandIKPass) brings to a two-handed weapon's grip point (see [animation-layers.md](animation-layers.md)). A gun can ride a second attach point too when its table names one.

### The gun's pose in the hand is animated

For a character holding a gun in a hand state, the gun's placement, [`WeaponData::UpdateAttachmentTransforms`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##func-UpdateAttachmentTransforms), sets [`m_WorldMatrixT1`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##field-m_WorldMatrixT1) straight from [`Character::GetWorldMatrixForBone`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-GetWorldMatrixForBone) for the bone the gun's table names: the bone's model-space matrix in the current pose times the character's world matrix. Only a holster or back bone is composed with the gun's own attach offset, and only when the weapon's attach tuning asks for it. So the gun's pose relative to the wrist is exactly the attach bone's pose relative to the wrist in the current pose.

The attach bones are ordinary bones of the skeleton. The pose job builds every bone's local transform from the clips playing on each layer, over the skeleton's reference pose ([`Blender::UpdatePose`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::pose_producer::Blender##func-UpdatePose), and [animation-layers.md](animation-layers.md)), so an attach bone's pose relative to the wrist is whatever the clips give it, or the reference pose where no clip keys it. A clip that keys an attach bone therefore turns or moves the gun in the hand, and two clips that key it differently, blended, sweep the gun between their two poses over the blend. The placement only reads the bone. Which shipped clips key the attach bones is unverified: the clip data was not decoded.

The skeleton's bind pose gives each attach bone's rest pose relative to its wrist: [`AnimationController::GetBindPoseBoneMatrix`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::AnimationController##func-GetBindPoseBoneMatrix) returns a bone's bind-pose model-space matrix, which belongs to the skeleton resource and does not change with the animation. A `SetJoint` ([`AnimationController::SetJoint`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::AnimationController##func-SetJoint)) on an attach bone before a placement moves the gun, and everything derived from its cached transform, with it (see "What derives from the attach bone" below).

### Where the weapon's world transform is computed per frame

[`WeaponBase::GetTransform`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-GetTransform) returns [`WeaponData::GetWorldMatrixT1`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##func-GetWorldMatrixT1). That function reads the gun's own cached world matrix, [`WeaponData::m_WorldMatrixT1`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##field-m_WorldMatrixT1), and scales it by [`WeaponData::m_HolsteredScaleValue`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##field-m_HolsteredScaleValue) when the owning weapon's state is [`WeaponState::E_WS_HOLSTERED`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponState##variant-E_WS_HOLSTERED). The model-instance attachment update refreshes that cache each frame from the attach bone: the weapon is a child model instance whose parent is the hand attach bone. Sim-side consumers, such as the `GetIPfxInstanceClosestTo` physics query and the fire origin, read this cached `T1`.

The render transform is not `T1`. The virtual [`WeaponBase::UpdateRender`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-UpdateRender) runs in the render phase. The IDB mislabels it as `CWeaponData::UpdateRender`; it loops over the weapon's `CWeaponData` list, [`WeaponBase::m_lWeaponData`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##field-m_lWeaponData), with the per-data body inlined. For each `CWeaponData`, it lerps [`m_WorldMatrixT0`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##field-m_WorldMatrixT0) to `m_WorldMatrixT1` by the render context's `dtf`, applies the holstered scale when the weapon state is holstered, and pushes the result to the gun's model instance, [`WeaponData::m_BaseModelInstance`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##field-m_BaseModelInstance), with [`ModelInstance::UpdateMatrix`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::model_instance::ModelInstance##func-UpdateMatrix) (a plain matrix store). It also updates the skinning of the weapon's own animated model with the same `dtf`. The hand mesh that holds the weapon interpolates separately, through the character's [`MakeSkinningPalette`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::pose_producer::PoseProducer##func-MakeSkinningPalette)`(dtf)` blend of the `T0`/`T1` poses ([20-animation-judder.md](../../issues/20-animation-judder.md)).

### A gun's separate model parts

A gun can draw parts of itself as separate models: a magazine, a pistol's slide, a minigun's barrel. Each is a weapon component, [`ModelAttachementWeaponComponent`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::ModelAttachementWeaponComponent), or one of the barrel recoil and barrel spin components derived from it, which share its render update. A part keeps its own pair of cached world matrices ([`m_WorldMatrix`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::ModelAttachementWeaponComponent##field-m_WorldMatrix) and [`m_WorldMatrixSaved`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::ModelAttachementWeaponComponent##field-m_WorldMatrixSaved)). Its placement ([`UpdateAttachmentTransforms`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::ModelAttachementWeaponComponent##func-UpdateAttachmentTransforms)), run from the weapon's attachment placement, sets the current one to the part's [`m_Offset`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::ModelAttachementWeaponComponent##field-m_Offset) composed with the gun's `GetWorldMatrixT1`, after shifting it into the saved one on an advancing placement. Its render update ([`UpdateRender`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::ModelAttachementWeaponComponent##func-UpdateRender)), which the weapon's render update calls for each component after pushing the guns' matrices, interpolates the two and pushes the result to the part's own model instance. The part therefore follows the gun's sim-rate transform, not the gun's render push: anything that changes the gun's pushed matrix alone leaves the parts where the simulation put them.

An animation task (`NWeaponModelAttachementSetBoneTask`) can put a part on one of the holder's bones instead ([`AttachToCharacterBone`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::ModelAttachementWeaponComponent##func-AttachToCharacterBone), which sets [`m_CharacterBone`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::ModelAttachementWeaponComponent##field-m_CharacterBone)), as a reload does with the magazine. The bone lasts only until the component's end-of-pass hook ([`UpdatePostFinalizePose`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::ModelAttachementWeaponComponent##func-UpdatePostFinalizePose)) resets it, so the render update cannot tell which bone the part was last placed on. The IDB mislabels the render update `NInteractionGraphExitTasks::NAnimationDrivenOnlyMotion::Update`, and puts its name on a function that reads a gun's fields instead.

### What derives from the attach bone and what derives from the weapon cache

Everything that reads the weapon transform derives from the hand attach bone: the weapon model, the muzzle effects, and the weapon's own physics proxy. A `SetJoint` on the attach bone in the post-finalize phase therefore moves all of them together and consistently. The fire logic does not read the attach bone for direction (see below).

The weapon's cached `T1` ([`WeaponData::m_WorldMatrixT1`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##field-m_WorldMatrixT1)) is downstream of the attach bone, not upstream. The hand bone, and with it the hand mesh and the arm IK's grip, does not read `T1`. A change to `T1` alone, or to the return of `GetWorldMatrixT1`, moves the rendered weapon and its muzzle but leaves the hand where the animation put it, so the hand and the weapon separate.

### Dual-wield: one weapon object, per-gun attach bones

A dual-wield slot (`E_SLOT_DUAL_WIELD`) is one `CWeaponBase` that holds a vector of `CWeaponData` ([`m_lWeaponData`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##field-m_lWeaponData), one entry per gun), not two weapon instances. Each gun carries its own `m_lBoneAttachementPerWeaponState[m_State]`, indexed by `weapon_index`. [`GetCurrentBoneAttachement`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-GetCurrentBoneAttachement)`(weapon_index)` returns that gun's attach bone for the current weapon state. [`ChangeBoneAttachement`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-ChangeBoneAttachement)`(bone, weapon_index)` rebinds one gun's bones independently; it writes the slot of every weapon state, [`WeaponState::E_WS_NUM`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponState##variant-E_WS_NUM) slots in all. The table each gun rides is rewritten from the weapon's slot at the end of every pose-finalization pass; see "The attach-bone table is rewritten every pass" below.

Placement is independent per gun. Each gun has its own attach bone, so the two guns share no transform. The per-barrel aim-target write ([aim-pipeline.md](../gameplay/aim-pipeline.md), dual-wield) gives each gun its own target.

State is shared. The pair has one `m_State`, one aim flag, and one reload, equip, and holster animation, and `GetCurrentBoneAttachement` is keyed on that single `m_State`. The two guns are posed independently only in the free-aim states (`E_WS_WIELDING`, `E_WS_DUAL_WIELDING`). When `m_State` leaves them, a single canonical two-gun animation drives both hands.

### The attach-bone table is rewritten every pass

A gun's table is not set once at equip time. [`Character::UpdatePassFinalizePose_Parallel`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-UpdatePassFinalizePose_Parallel) runs, in order: the character's state tasks for the pass; [`Inventory::UpdateAttachmentTransforms`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::inventory::Inventory##func-UpdateAttachmentTransforms), which places every slot weapon's guns on the bones their tables name for the weapon's state (and is run again after the `MAIN` IK solve, from [`Character::UpdateSecondaryHandIKPass`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-UpdateSecondaryHandIKPass), and from the character's prop-transform update); and, near the end, [`Inventory::UpdateInventoryPostFinalizePose`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::inventory::Inventory##func-UpdateInventoryPostFinalizePose). That last call runs each weapon's [`WeaponBase::UpdatePostFinalizePose`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-UpdatePostFinalizePose), which rewrites every gun's entries for the wielding, dual-wielding, and holstered states from [`m_EquipSlot`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##field-m_EquipSlot). The IDB mislabels it `CWeaponBase::CalculateAttachOffsets`. A bone written into a table between two passes therefore places the gun only if it is written before the placement, and it lasts only until the end of that pass.

For the dual-wield slot the rewrite puts gun 0 on [`ATTACH_HAND_RIGHT`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-ATTACH_HAND_RIGHT) in the wielding and dual-wielding states and on [`RIGHT_HOLSTER`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-RIGHT_HOLSTER) when holstered, and gun 1 on [`ATTACH_HAND_LEFT`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-ATTACH_HAND_LEFT) when dual-wielding and on [`LEFT_HOLSTER`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-LEFT_HOLSTER) otherwise. The wielding state ([`E_WS_WIELDING`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponState##variant-E_WS_WIELDING)) is the slot's one-pistol state: gun 0 in the right hand, gun 1 waiting on the left thigh holster. The engine special-cases it: `CWeaponBase::SetState` resets [`m_NextWeaponToFire`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##field-m_NextWeaponToFire) to gun 0 on entering it, the tail of [`Fire_ProjectileBase`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-Fire_ProjectileBase) keeps the index at gun 0 in it, `CWeaponData::UpdateAttachedEffects` skips gun 1's fire-effect restart in it, and `CWeaponBase::SetVisible` hides every gun after the first in it, but the player's draw sets the state without calling `SetVisible`. The player's draw (`CWeaponBase::OnEquip`) always sets the dual-wielding state, and a non-player without a particular blackboard value gets the wielding state, which is the single pistol NPCs carry.

Within a pass, state tasks move single guns between these bones, and so between hand and holster, while the weapon stays wielded. `NSetWeaponBoneTask` rebinds one gun to a named bone inside an animation segment; the motorbike's dual-wield draw, holster, and switch states use it to draw and holster one pistol at a time. `NSetWeaponPreDefinedBoneTask` has three modes: `clear_left_hand` parks gun 1 on its holster and sets the wielding state, `clear_right_hand` parks gun 0 on the right holster, and `restore_default` puts gun 0 back in the right hand; outside its segment the task (and its exit) sets the dual-wielding state back. Which shipped states carry these tasks was decoded from the Rico state machines by reading each state's task-index vector, which is an inference about the format and is unverified; by that decode `clear_left_hand` runs in many on-foot locomotion, jump, and grapple states, and `restore_default` in every reload state. Both tasks call [`WeaponBase::SkipRenderInterpolationForOneFrame`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponBase##func-SkipRenderInterpolationForOneFrame) for the gun they move. That sets the gun's [`m_SkipRenderInterpolation`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::weapon::WeaponData##field-m_SkipRenderInterpolation), which makes the gun's next placement copy its new world matrix into `m_WorldMatrixT0` too, so the render update draws it at its new bone without blending across the move; the end-of-pass rewrite clears the flag. None of these functions are bound in pyxis except where linked.

`CWeaponBase::IsWieldedInLeftHand` (gun 0's current bone is `ATTACH_HAND_LEFT`) is read by an animation-graph condition and by the vertical-aim blend samplers, so a table that puts gun 0 in the left hand while the graph evaluates can change the states the graph picks.

### Muzzle-flash and shell effects and fire logic (aim-pipeline interface point)

The wielded weapon's effects (muzzle flash, fire particle, casings, and sounds) live in the `CAttachedEffectContainer`. [`AttachedEffectContainer::UpdateAttachedEffects`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::attached_effects::AttachedEffectContainer##func-UpdateAttachedEffects) updates them, per instance, through [`AttachedInstance::UpdateTransform`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::attached_effects::AttachedInstance##func-UpdateTransform). Each attached instance resolves its transform through a virtual resolver, a vtable call that reads a bone or socket on the weapon model (the muzzle bone). It then copies the transform block ([`EffectTransformInfo`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::attached_effects::EffectTransformInfo)), applies its transform modes, and derives a per-frame velocity (`Δposition · 30`, which is the position delta scaled to the fixed tick) for the effect's own motion.

The muzzle transform is derived from a bone on the weapon model, resolved relative to the weapon's cached `T1`, which rides the hand bone. The muzzle flash therefore follows any change to the hand attach bone. It also follows a change to `CWeaponData`'s `T1` alone, because the resolver composes on that matrix.

The shot origin is the muzzle and the shot direction is the weapon's stored aim point, so moving the weapon moves the shot origin but not the direction. See [aim-pipeline.md, "Fire direction, end to end"](../gameplay/aim-pipeline.md#fire-direction-end-to-end-getshotmatrix).

## 2. Per-arm aim IK

The game ships two per-arm aim IK systems. Both are player-only, both feed `CHumanIK` rotation effectors on `PASS_MAIN` at [`SolveStep::UPPER_BODY`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::ik::SolveStep##variant-UPPER_BODY), and both are gated on the same blackboard aim-IK weight, [`ObjectBlackboard::AIM_IK_WEIGHT_ID`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/blackboard::ObjectBlackboard::AIM_IK_WEIGHT_ID). There is no generic left-arm aim IK. The second system is the grapple reel-in arm.

### Right-arm aim IK (the gun arm): three effectors, including the head

[`RightArmAimIK::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::RightArmAimIK##func-Update) runs only when `CCharacter::IsPlayer` is true. It reads the aim weight (blackboard `AIM_IK_WEIGHT_ID`), builds `inverse(m_WorldMatrixT1)` (world to model), brings the aim target into model space, then loops over three effectors, calling [`RightArmAimIK::UpdateAimEffector`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::RightArmAimIK##func-UpdateAimEffector) for each on [`Character::m_HIK`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_HIK).

The task's instance properties are [`RightArmAimIKInstanceProperties`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::RightArmAimIKInstanceProperties): a pole vector and three [`AimEffectorProperties`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::AimEffectorProperties) entries (`NRightArmAimIK::SAimEffectorProperties`), one per `EAimEffectorTypes` value: `AET_RIGHT_ARM`, `AET_RIGHT_HAND`, and `AET_HEAD`, in that order. Each entry holds the bone index, the bone position, the gain, and the aim direction and rotation axis that `UpdateAimEffector` derives.

The gun-aim IK drives the right arm, the right hand, and the head toward the aim target, with the per-effector gains [`RightArmAimIK_ArmGain`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::RightArmAimIK_ArmGain), [`RightArmAimIK_HandGain`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::RightArmAimIK_HandGain), and [`RightArmAimIK_HeadGain`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::RightArmAimIK_HeadGain). `UpdateAimEffector` computes the current-to-target rotation (axis and `acos` angle) and calls the axis-vector overload, [`HumanIK::AddEffectorTargetRotationVector`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::ik::HumanIK##func-AddEffectorTargetRotationVector), with `SolveStep::UPPER_BODY` and [`Pass::MAIN`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::ik::Pass##variant-MAIN). It then writes [`HumanIK::m_TargetReachR`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::ik::HumanIK##field-m_TargetReachR)`[effector]`.

Because the gun-aim IK drives the head effector ([`Effector::HEAD`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::ik::Effector##variant-HEAD)), the game turns the head toward the aim reticle whenever the player aims. Any other head target on the same solve, such as a head `SetJoint` or a body-IK head target ([humanik.md](humanik.md)), competes with it.

### Reel-in aim IK (the grapple arm): one arm effector and the chest (grapple-pipeline interface point)

[`ReelInAimIK::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::ReelInAimIK##func-Update) is also player-only and gated on [`ObjectBlackboard::AIM_IK_WEIGHT_ID`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/blackboard::ObjectBlackboard::AIM_IK_WEIGHT_ID). It drives a single arm effector ([`ReelInAimIKInstanceProperties`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::ReelInAimIKInstanceProperties) has one `m_AimEffectors` entry) through [`ReelInAimIK::UpdateAimEffector`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::ReelInAimIK##func-UpdateAimEffector), plus a separate chest-end rotation. The two targets come from different sources.

The arm target is the live [`PlayerAimControl::m_AimPos`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/aim::aim::PlayerAimControl##field-m_AimPos) entry for the weapon slot, [`TargetType::TARGET_WEAPONS`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/aim::target::TargetType##variant-TARGET_WEAPONS), not the grapple slot. The function reaches the aim control through the player's [`Player::m_AimControl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::player::Player##field-m_AimControl), reads that `m_AimPos` entry, and transforms it into character-local space with the inverse of the character's world matrix. `UpdateAimEffector` computes the direction from the `RIGHT_ARM` bone to that point and adds a rotation on the `RIGHT_ARM` effector (`CHumanIK::AddEffectorTargetRotation`) that turns the axis of the right-hand attach bone ([`SafeBoneIndex::ATTACH_HAND_RIGHT`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-ATTACH_HAND_RIGHT)) onto that direction. The target is the current aim point, not the hook's position or the target latched when the hook fired.

The chest target comes from the hook. The function calls [`Character::GetGrapplingHook`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-GetGrapplingHook) and, when the hook's [`GrapplingHook::m_ActiveWire`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::grappling_hook::GrapplingHook##field-m_ActiveWire) is non-null, transforms the position stored on the hook in [`GrapplingHook::m_CachedReelTargetPosition`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::grappling_hook::GrapplingHook##field-m_CachedReelTargetPosition) into character-local space. It measures the signed horizontal angle, around the `SPINE` bone, between the arm target and that position. When the angle passes a threshold constant, the function scales the excess to a rotation of up to [`ReelInAimIK::MAX_CHEST_ROTATION_DEGREES`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::ReelInAimIK::MAX_CHEST_ROTATION_DEGREES) and weights it by one minus the reel animation segment's local time. It then adds a chest-end rotation with `AddEffectorTargetRotation`. The decompiler does not resolve every argument of that call, so how the angle and weight reach it is inferred. The name `m_CachedReelTargetPosition` has medium confidence: the function reads the field, and the name comes from a `CGrapplingHook` layout that matches at the neighbouring mapped fields. The function uses [`HumanIK::GetChestEndEffectorId`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::ik::HumanIK##func-GetChestEndEffectorId) for the chest target and [`AimIKUtil::GetIKWeightValue`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::arm_aim_ik::AimIKUtil##func-GetIKWeightValue) for the reel-in weight envelope. The arm reference bone is [`SafeBoneIndex::RIGHT_ARM`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-RIGHT_ARM); the function also samples [`SafeBoneIndex::SPINE`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::SafeBoneIndex##variant-SPINE).

The reel-in arm pose is the grapple-pipeline interface point. Where the hook fires and attaches is grapple targeting, documented in [grapple-pipeline.md](../gameplay/grapple-pipeline.md). The reel-in IK poses the arm and chest toward that result.

### Activation and solve ordering

Both `Update` functions are animation state tasks. They run when the corresponding state is active in the character state machine: the weapon-aim state for the right-arm IK and the grapple reel-in state for the reel-in IK. The state-task function tables that reference them are not modelled in the defs. The aim-state conditions that activate aim IK (`NAimIKTask::Update`) are in [aim-state.md, "Arm and look IK"](../gameplay/aim-state.md#arm-and-look-ik). Both tasks queue their targets during animation-graph evaluation, before the `HasTargets(PASS_MAIN)` gate in `UpdatePassFinalizePose_Parallel` ([humanik.md](humanik.md)). Targets queued by other code before that gate share the same solve. The pass step is the maximum of the queued steps, and effectors are keyed by id, so rotation targets on distinct effector ids do not collide.

Hand position effectors exist alongside the rotation effectors. `GetEffectorIdFromBoneIndex(m_HIK, wristBoneIndex)` yields [`Effector::LEFT_WRIST`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::ik::Effector##variant-LEFT_WRIST) and [`Effector::RIGHT_WRIST`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/animation::ik::Effector##variant-RIGHT_WRIST) (see the effector table in [humanik.md](humanik.md)). `AddEffectorTargetPosition(effector, posModel, …)` with `m_TargetReachT[effector] = w` places a wrist on `PASS_MAIN` or `PASS_SECONDARY`. `PASS_SECONDARY` is the game's own hand and grip pass (`UpdateSecondaryHandIKPass`), which positions the wrists for the weapon grip.

The wielded weapon's animation set also poses the hand. The animation drives the fingers and forearm, and the weapon rides the attach bone (§1). A wrist effector target that disagrees with the animation's grip pulls the wrist away from the pose that the animation and the attach bone assume. The behaviour of a wrist effector on an arm that the animation set holds in a two-handed grip is not verified.

## 3. Character root motion and the collision proxy

### Where the world transform is authoritative

[`Character::m_WorldMatrixT0`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_WorldMatrixT0) and [`Character::m_WorldMatrixT1`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_WorldMatrixT1) are the authoritative pair; the aim IK reads `m_WorldMatrixT1`. `GetWorldMatrix` and `GetWorldMatrixRef` return `&m_WorldMatrixT1`. The render-facing `m_GraphicsWorldT0`/`T1` (`CTransform`) are derived from the world matrices (`SyncGraphicsMatricesToWorld` → `CTransform::FromMatrix4`), and the frame lerps T0 to T1 by `dtf`. Direct writers exist: `CCharacter::WriteWorldMatrix` (full matrix), `WriteWorldMatrixTranslation` (translation only), and [`Character::SetOrientation`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-SetOrientation) (rotation only, §4.3). `CCharacter::WriteWorldMatrixOrientation` is unconfirmed: the IDB function with that name writes an attachment proxy's rigid body, and the orientation write appears inlined into `SetOrientation`. A direct write to the world matrix is a teleport: it bypasses the collision solve.

### The displacement path

[`NStateTask_LocoUtil::EvaluateCharacterDisplacement`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/input::locomotion::NStateTask_LocoUtil##func-EvaluateCharacterDisplacement) is the per-tick movement producer, and it is a pure velocity function. Given the character, its new transform, and flags, it fills `wanted_velocity_ws` (world) and `wanted_velocity_ls` (local). It does not write the root. Its default path reads the animation's `GetRawRootVelocity` and rotates it into world space. Its code-driven path instead reads a target direction from the blackboard ([`ObjectBlackboard::MOVE_DIR_ID`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/blackboard::ObjectBlackboard::MOVE_DIR_ID), with the previous direction at [`PREVIOUS_TARGET_DIR_ID`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/blackboard::ObjectBlackboard::PREVIOUS_TARGET_DIR_ID) and the marker [`APPLY_TARGET_DIR_INSTANTLY_ID`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/blackboard::ObjectBlackboard::APPLY_TARGET_DIR_INSTANTLY_ID)). The `m_CodeDriven*` flags enable the code-driven path: `m_CodeDrivenDisplacement`, `m_AllowCodeDrivenDisplacementUntilTolerance`, `m_EnableCodeDrivenDisplacementDuringBlend`, and `m_AngleCorrectionEnabled` / `m_MoveActionParams.m_AngleCorrectionRequestedDir`. Its callers are [`NStateTask_MovementLocomotionTask::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/input::locomotion::NStateTask_MovementLocomotionTask##func-Update) (on foot), `NStateTask_MovementStuntingTask`, and `NPhysicalAnchorWarpTask`. §4.5 details how the two paths exclude each other.

The wanted velocity goes to the Havok character proxy. The physics step solves the proxy input against collision (stairs, slopes, and walls), and the character's `m_WorldMatrixT1` is written from the solved proxy position. The capsule follows because the proxy is the capsule. `CPfxCharacterInstance` is the character proxy wrapper: `m_Avatar` is the `CAvatar`, and `m_PendingProxyState` / `m_DefaultProxyState` select the capsule or quadruped shape.

The proxy has one input, [`PfxCharacterInstance::m_Input`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PfxCharacterInstance##field-m_Input), a [`CharacterInput`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::CharacterInput) (§4.1). The on-foot locomotion task writes its solved velocity, in the character's local frame, directly to [`CharacterInput::wantedVelocity`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::CharacterInput##field-wantedVelocity). The function the IDB labels `CPfxCharacterInstance::CCharacterInput::SetWantedVelocity` is [`Character::SetOrientation`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-SetOrientation), which sets the character's rotation and does not touch the proxy input.

### Vehicle seat attachment

In a vehicle the character is attached. `CCharacter::m_Attachable` (`CAttachable`), `m_attachType` (`CCharacter::AttachType`), and `m_attachedObject` hold the parent binding. The [`Character::AttachTo`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##vfunc-AttachTo) virtual, wrapped by [`Character::SetYAlignedAttachTo`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-SetYAlignedAttachTo), sets it. While the character is attached, its transform is parented to the vehicle seat rather than driven by the character proxy, and `m_attachType != NONE`. §4.4 gives the seat pose, and §5.2 and §5.3 give the in-vehicle predicates.

### Teleport and warp mechanisms

For discrete relocation, the engine uses the direct world-matrix writers above, its own `CTeleport` object ([`Teleport::SetTransform`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game_world::Teleport##func-SetTransform), `GetTransform`/`NeedsUpdate`, event-driven), the game world's teleport functions, and the animation warp tasks (`NPhysicalAnchorWarpTask`, `NStateTask_MovementHeightWarpTask`) for scripted warps. All of them bypass collision and move the character instantaneously. §4.3 lists the writers and the signals that detect them.

## 4. Proxy input, scene queries, teleports, seat pose, root motion, capsule, and pause

### 4.1 The locomotion task runs at idle and writes the proxy input directly

[`NStateTask_MovementLocomotionTask::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/input::locomotion::NStateTask_MovementLocomotionTask##func-Update) runs every on-foot sim tick, including standing idle with no input. It is not gated to an active move. The only callers of [`NStateTask_LocoUtil::EvaluateCharacterOrientation`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/input::locomotion::NStateTask_LocoUtil##func-EvaluateCharacterOrientation) are this task, [`NStateTask_MovementStuntingTask::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/input::locomotion::NStateTask_MovementStuntingTask##func-Update), and [`NPhysicalAnchorWarpTask::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/input::locomotion::NPhysicalAnchorWarpTask##func-Update). A call counter on `EvaluateCharacterOrientation` advances on every on-foot tick including idle. On-foot idle is neither stunting nor warping, so the advancing counter is the locomotion task ticking. The move and aim task counters stop at idle; those tasks are narrower, action-specific tasks, not the locomotion task.

At idle the task still runs the full pipeline: [`EvaluateCharacterSpeed`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/input::locomotion::NStateTask_LocoUtil##func-EvaluateCharacterSpeed) (returning about 0), `EvaluateCharacterOrientation`, and `EvaluateCharacterDisplacement`. It still writes a wanted velocity of about 0 to the character proxy every tick.

At its tail the locomotion task writes its solved velocity directly into the character proxy's input. The proxy is the [`PfxCharacterInstance`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PfxCharacterInstance) that the character holds in [`Character::m_PfxCharacter`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_PfxCharacter), and its input is [`PfxCharacterInstance::m_Input`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PfxCharacterInstance##field-m_Input), a [`CharacterInput`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::CharacterInput) (`CPfxCharacterInstance::CCharacterInput`). The velocity goes to [`CharacterInput::wantedVelocity`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::CharacterInput##field-wantedVelocity), a `CVector3f` in metres per second in the character's local frame, not world space: the task writes the normalized local move direction times the speed. The task returns without writing while the character is attached to a vehicle.

The speed is the animation's: the task normalizes the displacement direction and scales it by [`EvaluateCharacterSpeed`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/input::locomotion::NStateTask_LocoUtil##func-EvaluateCharacterSpeed), the horizontal magnitude of the clip's raw root velocity. So the starts' ramps, the stops' decay, the turning starts' swings, and a run's speed changing within each step are all in the velocity the proxy receives. The input tasks' target speed, the float at [`ObjectBlackboard::SPEED_ID`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/blackboard::ObjectBlackboard::SPEED_ID), does not set the speed: the input tasks branch on it (a value that is not positive routes them into the stop acts), and the movement task reads it for the player only to gate its angle correction. In the symbol dump, the task that writes it (`NStateTask_InputLocoSetTargetSpeedsTask::SetupTargetSpeeds`) picks it from the movement settings by the stick's magnitude and the character's state, as the walk, non-combat walk, run, or run backpedal speed in metres per second, and writes zero when the stick is below the walk threshold or when a predicted fall or a wall ahead should stop the character. That task has not been located in the IDB, so this is unverified for this build.

The character has a getter and a setter that convert the stored value to and from world space. [`Character::GetWantedWorldVelocity`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-GetWantedWorldVelocity) rotates the stored value into world space through [`Character::m_WorldMatrixT1`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_WorldMatrixT1). [`Character::SetWantedWorldVelocity`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-SetWantedWorldVelocity) converts a world velocity into the local frame through the inverse of the proxy's transform and stores it.

The task also writes [`CharacterInput::gameControledVelocity`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::CharacterInput##field-gameControledVelocity). It sets the flag while the proxy is supported on stairs ([`PfxCharacterInstance::m_IsSupportedOnStairs`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PfxCharacterInstance##field-m_IsSupportedOnStairs)) and the character's blackboard carries a slope direction, and clears it otherwise. The flag changes how the Havok proxy update reads the vector, not which vector it reads: while the flag is set, the update rotates `wantedVelocity` by the proxy's rotation, and while it is clear, the update hands the vector to the character state as it stands. Neither the update nor the physics step re-derives the velocity from the flag.

There is one proxy-input channel, not two. The function the IDB labels `CCharacterInput::SetWantedVelocity` is [`Character::SetOrientation`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-SetOrientation): it writes a quaternion's rotation into [`Character::m_WorldMatrixT1`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_WorldMatrixT1), keeping the translation, and stores the quaternion in [`Character::m_RotationGoal`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_RotationGoal). It is a direct world-matrix write and does not go through the physics proxy. The proxy-driven states that call it (ragdoll get-up, in-air grapple-fire, grappling-hang, stunting, jump, grapple-yank, and upright) therefore set the character's orientation through it. How those states feed `CharacterInput::wantedVelocity` is not established.

### 4.2 Raycast and scene-query API: `CPhysicsSystem::CastRay` and related functions

[`PlayerAimControl::UpdateDirectAim`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/aim::aim::PlayerAimControl##func-UpdateDirectAim) calls the engine's general scene query directly, with no wrapper: [`PhysicsSystem::CastRay`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PhysicsSystem##func-CastRay). The physics system is the [`PhysicsSystem`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PhysicsSystem) singleton.

```
bool CPhysicsSystem::CastRay(CPhysicsSystem*,
                             const CRay3&        ray,        // { CVector3f start; CVector3f direction; } WORLD space, direction normalized
                             float               minFraction,// 0.0 in the aim call
                             float               maxDistance,// world-space length along direction
                             CCastRayInfoBase*   outHit,     // nullptr = boolean-only
                             CRaycastFilter*     filter,     // nullptr = default filter
                             unsigned int        flags,      // 0 in the aim call
                             int                 layer);     // PhysicsSystem::QUERY_LAYER in the aim call
```

The coordinate space is world. The aim query passes the layer [`PhysicsSystem::QUERY_LAYER`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PhysicsSystem::QUERY_LAYER). `flags` is a collision-filter-info word (0 for a plain query). The backend is Havok [`hknpWorld::castRay`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::hknpWorld##func-castRay).

- Filter semantics. The `CRaycastFilter` constructor, bound as [`RaycastFilter::Construct`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::RaycastFilter##func-Construct), is `CRaycastFilter(ignoreMaterialMask, forceMaterialMask, IPfxInstance* ignoreInstance, const hknpWorld*)`. The first two parameters are material masks ([`MaterialPassFlags`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::MaterialPassFlags)), not layers: materials whose pass flags are in the ignore mask do not count as hits, and materials whose pass flags are in the force mask always count. The `ignoreInstance` argument excludes one instance, such as the player's own proxy. The aim path uses the subclass `CIgnoreMaterialFlagFilter` with [`SetIgnoreBulletPass`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::IgnoreMaterialFlagFilter##func-SetIgnoreBulletPass) / [`SetIgnoreRayPass`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::IgnoreMaterialFlagFilter##func-SetIgnoreRayPass) / [`SetIgnoreCameraPass`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::IgnoreMaterialFlagFilter##func-SetIgnoreCameraPass), each of which sets or clears one pass bit in the ignore mask. JC3 materials carry per-pass "holey" flags (foliage that a bullet passes through, glass, and similar), and the filter selects which passes count as a hit. `CPlayerAimControl` wraps this in `CPlayerAimRaycastFilterCacheFirstHoleyHitAndMinDistanceHit`, a caching collector that records both the first holey hit and the nearest solid hit.
- Result. `CCastRayInfo : CCastRayInfoBase` ([`CastRayInfoBase::Reset`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::CastRayInfoBase##func-Reset)) carries the hit position, normal, and fraction, the hit body and instance, [`CastRayInfo::GetHitMaterial`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::CastRayInfo##func-GetHitMaterial) → `EGameMaterialId`, and [`CastRayInfoBase::DidHitBulletPassMaterial`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::CastRayInfoBase##func-DidHitBulletPassMaterial). `GetHitNameHash` is not a result method: it is [`RagdollProxyPhantom::GetHitNameHash`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::RagdollProxyPhantom##func-GetHitNameHash), which takes a `CCastRayInfoBase` and returns the name hash of the ragdoll part the ray hit, or 0 when the hit is not on the ragdoll's proxy phantom.
- Thread and phase. These are sim-phase queries against the live Havok world. `UpdateDirectAim` runs inside the aim update on the sim thread ([`PlayerAimControl::UpdatePreSim`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/aim::aim::PlayerAimControl##func-UpdatePreSim) / [`UpdateAllTargets`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/aim::aim::PlayerAimControl##func-UpdateAllTargets)). The engine does not call them during the physics solve or from a render worker.

Simpler variants, all `CPhysicsSystem` members and all in world space:

- [`CastRaySimple`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PhysicsSystem##func-CastRaySimple): `bool CastRaySimple(const CVector3f& start, const CVector3f& end, unsigned int flags)`. It builds the ray from two points, takes no hit info and no filter, hardcodes `QUERY_LAYER`, and returns true when the segment is blocked. Without a filter it does not exclude the player's own bodies: a segment through the player misses the character proxy's capsule but can hit the player's own ragdoll and hit-proxy bodies. The player aim's filter ([`PlayerAimRaycastFilter`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/aim::aim::PlayerAimRaycastFilter)) rejects every physics instance of the objects it ignores, including those bodies.
- [`CastRayTerrain`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PhysicsSystem##func-CastRayTerrain): terrain only.
- [`CastRayWaterSurface`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PhysicsSystem##func-CastRayWaterSurface): the water plane.
- Shape casts. [`CastSphere`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PhysicsSystem##func-CastSphere) is `bool CastSphere(const CVector3f& start, const CVector3f& end, float radius, float, hknpCollisionQueryCollector&, unsigned int, float)`. [`CastShape`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PhysicsSystem##func-CastShape) casts an arbitrary `hknpShape*` with a rotation. The free function [`SweptSphereCast`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/physics##func-SweptSphereCast) fills a `CCastResult`. An engine consumer of the sphere cast, `CMagnetWeaponComponent::CastSphereAgainstStatic`, is not yet located: the IDB function with that name has a different body.

### 4.3 Teleport writers and teleport signals

The character teleport writers, all of which bypass the collision solve:

- Fast travel and mission warps. [`GameWorld::TeleportPlayer`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game_world::GameWorld##vfunc-TeleportPlayer) (implementation [`GameWorld::TeleportPlayerImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game_world::GameWorld##func-TeleportPlayerImpl)) queues a deferred request on `CGameWorld`, which the teleport state machine in [`UpdateTeleport`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/game_world##func-UpdateTeleport) applies over the following ticks; it never touches the character directly. [`GameWorld::TeleportPlayerInstant`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game_world::GameWorld##vfunc-TeleportPlayerInstant) (implementation [`GameWorld::TeleportPlayerInstantImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game_world::GameWorld##func-TeleportPlayerInstantImpl)) performs the move synchronously. It re-bases the character's world transform through `CGameObject::InitTransform`, the virtual at [`Character::GAME_OBJECT_INIT_TRANSFORM_SLOT`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character::GAME_OBJECT_INIT_TRANSFORM_SLOT) in the vtable of the character's `CGameObject` subobject at [`Character::GAME_OBJECT_BASE_OFFSET`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character::GAME_OBJECT_BASE_OFFSET). It then calls [`Character::ForceNeutralState`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-ForceNeutralState), sets [`AbilityFlags::m_IsStuntAutoExitEnabled`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::AbilityFlags##flag-m_IsStuntAutoExitEnabled) in [`Character::m_AbilityFlags`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_AbilityFlags), and re-bases the camera through [`GameCameraManager::ResetCamera`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/camera::game_camera_manager::GameCameraManager##func-ResetCamera). `NEvent::CPostEvent::PostMsg("game_teleporting_initiated" / "…_completed")` brackets the move.
- Scripted teleport objects: [`Teleport::Teleport`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game_world::Teleport##func-Teleport), which issues `GameWorld::TeleportPlayer` to the object's transform, `UpdateTeleport`, and [`NStateTask_InputVehicleExitTask_TeleportUpwards`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/vehicle::vehicle##func-NStateTask_InputVehicleExitTask_TeleportUpwards).
- Vehicle: [`Vehicle::TeleportVehicle`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/vehicle::vehicle::Vehicle##func-TeleportVehicle). The seated character moves with the vehicle through the attach (§4.4).
- Orientation-only and warp-task writers: [`Character::SetOrientation`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-SetOrientation), which writes the rotation of `m_WorldMatrixT1` directly (§4.1), and the animation warp tasks (`NPhysicalAnchorWarpTask`, `NStateTask_MovementHeightWarpTask`). The IDB also names `CCharacter::WriteWorldMatrixOrientation` and a second `SetOrientation(CQuaternion)`; neither is confirmed, because the functions carrying those names have unrelated bodies.

The `m_NumFramesSinceTeleport` counter does not detect teleports. `CCharacter::DebugVerifyCharacter`, which runs unconditionally, increments the field each tick, but no writer resets it. An apparent `= -1` is a local-variable fallback inside a warning-log call, not a field write. Without a reset, the field counts frames since spawn, and `== 0` never holds after a teleport.

The ability bit that `TeleportPlayerInstant` sets does not detect teleports either. `m_IsStuntAutoExitEnabled` controls whether the character leaves stunt positions automatically, and [`Character::SetStuntAutoExitEnabled`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-SetStuntAutoExitEnabled) also writes it, so a set bit does not identify a teleport.

The verified teleport signals are the following:

- The game world's teleport functions. [`GameWorld::IsTeleporting`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game_world::GameWorld##vfunc-IsTeleporting) reports whether a deferred `TeleportPlayer` request is still being serviced, which covers fast travel and the `CTeleport` objects. Fast travel, mission warps, and the `CTeleport` objects all enter through `TeleportPlayer` or `TeleportPlayerInstant`.
- The teleport events. The `game_teleporting_initiated` / `…_completed` `PostMsg` events bracket `TeleportPlayerInstant`, which gives a string-keyed choke point at the event level for the scripted warps.
- Position discontinuity. A per-tick translation delta, `length(T1.translation − prevT1.translation) > threshold` with the threshold well above wingsuit speed multiplied by the tick length, detects a discontinuity from any writer, including the vehicle teleport and the warp tasks, which do not go through the game world.

### 4.4 Seat pose: `m_AttachBone` and `m_AttachOffset` on the character

When the character is attached to a vehicle seat, the vehicle's `CSeat` does not store the pose. That struct is interaction-graph metadata only (`m_GraphNode`, `m_DoorSlot`, `m_WindowPartInstance`, and `m_PlayerUsable`) and has no transform. The character defines the pose, with an attach bone and an offset:

- `CCharacter::m_AttachBone` (`NBone::ESafeBoneIndex`) is a safe bone or socket on the parent (vehicle) model.
- `CCharacter::m_AttachOffset` (`CMatrix4f`) is the character's transform relative to that bone.
- `m_Attachable` (`CAttachable`), `m_attachType` (`AttachType`), and `m_attachedObject` hold the binding (§3). The Y-aligned attach entry is [`Character::SetYAlignedAttachTo`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-SetYAlignedAttachTo). It computes a yaw-only alignment from the target frame and calls the [`Character::AttachTo`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##vfunc-AttachTo) virtual. `AttachToWithCurrentOffset`, which preserves the live offset, is not yet located: the IDB function with that name has a different body.

While the character is attached, character world = vehicle.SafeBoneWorld(`m_AttachBone`) · `m_AttachOffset`. The whole skeleton rides the vehicle through the attach, so the character's own head and eye bones (`GetSafeBoneMatrix(HEAD)` and the eye bones) are already vehicle-relative and give the seated eye position. No vehicle-side seat transform exists.

The in-vehicle camera is a third-person chase rig (`SGenericVehicleCamera`: `m_CameraPosition`, `m_RotationPoint`, and `m_LookAtPoint` relative to the vehicle body, plus spring, lag, and FOV tuning). It has no seat-eye anchor. A vehicle-frame seat anchor that does not depend on the character skeleton is the composition of the `m_AttachBone` world transform (from the vehicle's animated model) with `m_AttachOffset`.

### 4.5 Root-motion summing: the two direction sources are exclusive

[`NStateTask_LocoUtil::EvaluateCharacterDisplacement`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/input::locomotion::NStateTask_LocoUtil##func-EvaluateCharacterDisplacement) selects one source; it does not sum. Its first branch is taken when the animation is not mid-blend, the code-driven marker [`ObjectBlackboard::APPLY_TARGET_DIR_INSTANTLY_ID`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/blackboard::ObjectBlackboard::APPLY_TARGET_DIR_INSTANTLY_ID) is not set, and the character is outside the special segments. That branch reads [`AnimationController::GetRawRootVelocity`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::AnimationController##func-GetRawRootVelocity) (`CAnimationControl::GetRawRootVelocity`), rotates it into world space, writes the wanted velocity, and returns immediately. Only when that branch is skipped does the function fall through to the code-driven path, which reads the target direction from the blackboard entry [`ObjectBlackboard::MOVE_DIR_ID`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/blackboard::ObjectBlackboard::MOVE_DIR_ID) (with the previous direction at [`PREVIOUS_TARGET_DIR_ID`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/blackboard::ObjectBlackboard::PREVIOUS_TARGET_DIR_ID) and the marker), builds a direction, and rotates it out. Animation root motion and the `MOVE_DIR_ID` direction never both contribute in one call. There is one source per tick.

The value the locomotion task writes to [`CharacterInput::wantedVelocity`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::CharacterInput##field-wantedVelocity) (§4.1) is the result of that single source, animation root motion or code-driven displacement. The proxy reads `wantedVelocity` after the task, so a velocity added there after the task runs is outside the displacement evaluator. While the player deflects the movement stick, the animation walk cycle produces root velocity, so `wantedVelocity` already carries the stick-driven walking speed.

### 4.6 Capsule shape and pause

#### 4.6a Capsule dimensions and runtime resize

The character proxy's capsule is a Havok `hknpShape` selected per proxy state. [`PfxCharacterInstance::SetProxyState`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PfxCharacterInstance##func-SetProxyState) performs the swap. It stores the new state in [`PfxCharacterInstance::m_ProxyState`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PfxCharacterInstance##field-m_ProxyState), fetches the shared character settings through the owner [`PfxCharacterInstance::m_Owner`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PfxCharacterInstance##field-m_Owner) (its `GetSharedPfxCharacterSettings` virtual), takes the per-state shape from the settings' shape table, and calls [`hknpWorld::setBodyShape`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::hknpWorld##func-setBodyShape)`(world, bodyId, shape)` to swap the shape on the live body. It also copies the state's per-shape byte into the rigid-body listener, [`PfxCharacterInstance::m_CharacterRBListener`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PfxCharacterInstance##field-m_CharacterRBListener). [`PfxCharacterInstance::GetCharacterRigidBodyId`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PfxCharacterInstance##func-GetCharacterRigidBodyId) returns the character's body id. [`PfxCharacterInstance::BuildDefaultCharacterContext`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PfxCharacterInstance##func-BuildDefaultCharacterContext) builds the Havok character-state machine (on-ground, in-air, and jumping) but not the capsule dimensions. Those live in the pre-built `hknpShape` objects in the shared settings' shape table, keyed by `EProxyState`. The engine resizes and swaps the capsule itself, through `m_PendingProxyState` / `m_DefaultProxyState`, on the sim thread. It swaps proxy state on swimming, vehicle, and ragdoll transitions, among others.

#### 4.6b What the game's pause freezes, and the clock split

A real pause (the pause menu is up) switches `CGameStateRun` into its paused update, which runs [`GameStateRun::UpdateRenderPaused`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::GameStateRun##func-UpdateRenderPaused). That path drives the render systems: landscape LOD, UI prerender, video, `WaitForCPUDrawToFinish`, and resource streaming. It reads the active camera's already-computed `m_TransformF`, but it does not call `GameCameraManager::UpdateRender` or `CameraTree::UpdateRenderContexts`. Under a real pause the camera transform is therefore not recomputed and stays frozen at its last value. Entering pause also sets `CPhysicsSystem::m_Pause = 1` and calls `CClock::Pause(true)`. Leaving it clears both (`CGameStateRun.cpp`: `m_Pause = 0; CClock::Pause(instance, 0)`).

[`Clock::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##func-Update) keeps two sets of accumulators, one that always advances and one that stops while the game-pause bool, [`Clock::m_Stop`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_Stop), is set. The fields of the [`Clock`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock) singleton that `Update` maintains:

| Field | Type | Behaviour in `Update` |
|---|---|---|
| [`m_FPS`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_FPS) | `f32` | `1 / m_SPF`, always updated |
| [`m_SPF`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_SPF) | `f32` | frame delta smoothed with a 1/5 exponential filter, times `m_UpdateSpeed`, always updated |
| [`m_RealFPS`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_RealFPS) | `f32` | `1 / m_RealSPF`, always updated |
| [`m_RealSPF`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_RealSPF) | `f32` | raw frame delta, always updated |
| [`m_UpdateSpeed`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_UpdateSpeed) | `f32` | timescale multiplier on `m_SPF` |
| `m_Stop` | `bool` | game-pause bool |
| [`m_Time`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_Time) | `u32` | milliseconds, always advances |
| [`m_RealTimeAtUpdate`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_RealTimeAtUpdate) | `u32` | milliseconds, always advances |
| [`m_PauseTime`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_PauseTime) | `u32` | milliseconds, stops while `m_Stop` is set |
| [`m_GameTimeMicro`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_GameTimeMicro) | `u64` | microseconds of `m_SPF`, always advances |
| [`m_GameRunTimeMicro`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_GameRunTimeMicro) | `u64` | microseconds of `m_SPF`, stops while `m_Stop` is set |
| [`m_CpuFrequency`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_CpuFrequency) | `u64` | performance-counter frequency, the divisor for all deltas |

[`Clock::Pause`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##func-Pause) writes `m_Stop`. On a transition from unpaused to paused it snapshots `m_RealTimeAtUpdate` into [`m_PauseTimeAtUpdate`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_PauseTimeAtUpdate) and [`m_RealTimeAtUpdateGame`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_RealTimeAtUpdateGame) into [`m_PauseTimeAtUpdateGame`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##field-m_PauseTimeAtUpdateGame). `Update` does not zero `m_SPF` during a pause. The pause shows in the getters instead: [`Clock::GetSPF`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock##func-GetSPF) returns [`Clock::PAUSED_SPF`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/clock::Clock::PAUSED_SPF) while `m_Stop` is set unless its `ignore_pause` argument is true.

The pyxis `Clock` binds the millisecond counters as the six `u32` fields the code accesses: `m_Time`, `m_RealTimeAtUpdate`, `m_RealTimeAtUpdateGame`, `m_PauseTimeAtUpdate`, `m_PauseTimeAtUpdateGame`, and `m_PauseTime`, the millisecond counter that stops during a pause. Because of this split, game time can stop while the real clock, and the render path of the unpaused `CGameStateRun` update that calls the camera update, keeps running.

## 5. Per-tick character state signals

The engine exposes per-tick signals, readable from the local `CCharacter` or a cheap singleton, that separate the player's modes: on foot, in a vehicle (and its class), wingsuit, parachute, grapple traversal, swimming, and game UI up.

### 5.1 The central mechanism: the character state-bitflag words

Almost every "what is the player doing" predicate the game ships (`CCharacter::IsUsingWingsuit`, `IsReelingIn`, `IsSwimming`, and the others below) is a one-bit read of a small array of 64-bit state-bitflag words owned by the character's control parameters. The words can be read directly without calling the predicates.

- [`Character::m_ControlParameters`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_ControlParameters) is a pointer to the character's [`ControlParameters`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::control_parameters::ControlParameters) (confirmed in the decompile of `IsInVehicleAttachState`).
- The state-bitflag array (`m_ControlParameters->m_UserVM.m_CurrentStateBitFlags`) is the run of `u64` words [`UserVM::m_CurrentStateBitFlags0`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::control_parameters::UserVM##field-m_CurrentStateBitFlags0), [`m_CurrentStateBitFlags1`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::control_parameters::UserVM##field-m_CurrentStateBitFlags1), and [`m_CurrentStateBitFlags2`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::control_parameters::UserVM##field-m_CurrentStateBitFlags2) in [`ControlParameters::m_UserVM`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::control_parameters::ControlParameters##field-m_UserVM). The bits are named by [`StateBitFlag`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/state::StateBitFlag): flag `n` lives in word `n / 64` at mask `1 << (n % 64)`. The whole read is `flags = character->m_ControlParameters->m_UserVM.m_CurrentStateBitFlags[n / 64]`.
- Some of the predicates also require [`AnimatedModel::m_InstanceData`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::AnimatedModel##field-m_InstanceData) (on [`Character::m_AnimatedModel`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_AnimatedModel)) to be non-null. The animation instance must exist for the bit to be meaningful, which matters only in the first frames after spawn or stream-in.

### 5.2 The state-machine-hash predicates (vehicle riding, reeled in, hang)

A second class of predicate is not a single bit. It walks the animation rule system (`m_AnimatedModel.m_RuleSystems[0]->m_StateMachineInstance->m_CurrentState->m_HashID.m_Hash`) and compares the current animation state hash against a set of known state ids, sometimes combined by OR with a state bit or the grapple-hook state. These cost a few pointer chases. They are the authoritative signal where a raw bit is ambiguous:

| Predicate | What it establishes |
|---|---|

`IsInVehicleAttachState` is the widest test for a body bound to a vehicle. It returns true through the whole enter and exit animation, not only once the character is settled, so the mount animation is inside its envelope.

### 5.3 Vehicle presence and class

The seated vehicle and its class come from the interaction graph, not from a flag:

- [`Character::GetVehicle`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-GetVehicle) fills a `boost::shared_ptr<CVehicle>`. It walks the interaction graph's top-root object and applies `rtti_cast<CVehicle>`. [`GetVehiclePtr`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-GetVehiclePtr) is the raw-pointer wrapper. Both take and release a shared-ptr refcount (an interlocked increment and decrement), so each call costs more than a field read.
- Class is decided by an RTTI `IsType` test against the vehicle's class-hierarchy `TYPE_ID`, exposed as character predicates:

| Class predicate | `TYPE_ID` tested |
|---|---|
| [`IsAttachedToVehicle`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-IsAttachedToVehicle) | any (has a `CVehicle` and is graph-attached) |
| [`IsAttachedToLandVehicle`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-IsAttachedToLandVehicle) | `CLandVehicle` (car and motorcycle) |
| [`IsAttachedToAirVehicle`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-IsAttachedToAirVehicle) | `CAirVehicle` (plane and helicopter) |
| [`IsAttachedToSeaVehicle`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-IsAttachedToSeaVehicle) | `CSeaVehicle` (boat and jetski) |
| [`IsAttachedToHelicopter`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-IsAttachedToHelicopter) | `CHelicopter` |
| [`IsAttachedToMech`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-IsAttachedToMech) | via [`Vehicle::IsMech`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/vehicle::vehicle::Vehicle##func-IsMech) |

The RTTI bases give the coarse split. The `CButtonMapping::EMapping` sections split more finely than the RTTI bases: car and motorcycle, boat and jetski, and plane and helicopter each have their own mapping. The predicates combine into the finer classes as follows:

- Helicopter: `IsAttachedToHelicopter`.
- Plane: `IsAttachedToAirVehicle && !IsAttachedToHelicopter`. Both derive from `CAirVehicle`.
- Motorcycle: `IsAttachedToLandVehicle && IsRidingMC` (`SB_IS_RIDING_MOTORBIKE`).
- Land car: `IsAttachedToLandVehicle && !IsRidingMC`.
- Boat or jetski: `IsAttachedToSeaVehicle`. The RTTI does not split boat from jetski at the `CSeaVehicle` base. The engine's vehicle-type enum is [`VehicleType`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/vehicle::vehicle::VehicleType) (`NVehicle::EVehicleType`: `ECAR`, `EHELICOPTER`, `EBOAT`, `EAIRPLANE`, `EMOTORCYCLE`, `ESUB`, and `ETRAIN`), stored on the vehicle as `CVehicle::m_VehicleType` and returned by `CVehicle::GetVehicleType`, which is inlined everywhere in this build. The field offset is not pinned. This enum also folds jetski into `EBOAT`; the game selects the jetski mapping band from a jetski-specific type elsewhere. TODO: pin the `m_VehicleType` offset and the jetski discriminator.
- Seat determines the input mapping, independent of class. [`Vehicle::m_LocalPlayerSeat`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/vehicle::vehicle::Vehicle##field-m_LocalPlayerSeat) (a [`Seat`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/vehicle::vehicle::Seat), `NVehicle::ESeat`, or `ENoSeatIdentifier` when the player has no seat) is what the game's own context predicates test (`m_LocalPlayerSeat == EDriverSeat`) to decide whether driver controls apply. A passenger or gunner gets a different mapping in the same vehicle. `CVehicle::GetSeat` is bound as [`Vehicle::GetSeat`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/vehicle::vehicle::Vehicle##func-GetSeat).

### 5.4 Grapple traversal states (`GHS_*`)

The grappling-hook state machine is the finest grapple-traversal signal, and it is independent of the character animation flags. [`Character::GetGrapplingHook`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##func-GetGrapplingHook) returns the hook shared-ptr. The raw hook pointer is cached in the character's inventory ([`Character::m_Inventory`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_Inventory), [`Inventory::m_GrapplingHook`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::inventory::Inventory##field-m_GrapplingHook)), and its state is [`GrapplingHook::m_State`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::grappling_hook::GrapplingHook##field-m_State), a [`GrapplingHookState`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/equipment::grappling_hook::GrapplingHookState) (`EGrapplingHookState`): `GHS_INITIALIZING`, `GHS_INACTIVE`, `GHS_REELING_IN`, `GHS_REELED_ATTACHED`, `GHS_REELED_HANG`, `GHS_REELED_UPSIDEDOWN`, `GHS_REELED_STUNT`, and `GHS_CUSTOM_ACTIVE_WIRE`.

A reeled state (`GHS_REELED_ATTACHED`, `GHS_REELED_HANG`, `GHS_REELED_UPSIDEDOWN`, or `GHS_REELED_STUNT`) means reeled onto something (the `IsReeledIn` predicate), `GHS_REELED_HANG` is hanging, and `GHS_REELING_IN` is mid-reel. The character-level `IsReelingIn`, `IsGrappleHanging`, and `IsReeledIn` above combine this hook state with the animation state. The raw `hook->m_State` remains readable when the hook pointer is present and the character predicate is ambiguous during a transition.

### 5.5 Game UI up and gameplay input suspended

The engine suspends gameplay input through three distinct mechanisms: the hard pause, the pause-until-action utility, and a switch of input focus to the UI action map.

1. Hard pause (pause menu). `CGameStateRun` propagates the update context's [`GameObjectUpdateContext::m_Paused`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::GameObjectUpdateContext##field-m_Paused) flag into `CPhysicsSystem::m_Pause` (`Base::CSingle<CPhysicsSystem>::Instance->m_Pause = m_Paused`) and calls `CClock::Pause(true)`, which sets the game-clock game-pause bool (§4.6b). The physics system is the [`PhysicsSystem`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/physics::PhysicsSystem) singleton (§4.2). Its `m_Pause` byte is nonzero for the whole real pause, so it is a per-tick read of whether the game's own pause is active. A real pause also freezes the camera update (§4.6b).
2. Pause until action. [`GamePauseUtility`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::game_pause_utility::GamePauseUtility), a `Base::CSingle` singleton, is the script facility that pauses the game until an action is pressed, used by tutorials. It is not a weapon selector; the game's weapon selection is a cross driven by the slot-select actions ([input.md, "Weapon selection, rebel drops, and gear mods"](../gameplay/input.md#weapon-selection-rebel-drops-and-gear-mods)). [`GamePauseUtility::m_state`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::game_pause_utility::GamePauseUtility##field-m_state) is its first field, and `m_state == `[`PauseState::E_STATE_PAUSED`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::game_pause_utility::PauseState##variant-E_STATE_PAUSED) means the pause is up. [`GamePauseUtility::SetState`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::game_pause_utility::GamePauseUtility##func-SetState) drives the state machine.
3. Input focus (map and commlink, with no physics pause). Opening the map or the commlink does not hard-pause the game. The game switches input focus to the UI action map instead. `CSteeringUI` holds a static UI action map (`CSteeringUI::GetActionMap` → `m_ActionMapUI`) that becomes the focused consumer while a UI screen is up, and the `CButtonMapping` band `FIRST_UI_MAPPING..END_UI_MAPPINGS` (bounded by the game's own `END_UI_MAPPINGS`) applies. Whether `CSteeringUI` is the active steering is the signal for these screens. No single per-tick "UI steering active" global is pinned. TODO: pin it, from `CSteeringUI::m_SteeringUI` presence plus a focus check. The pause flag does not cover the non-pausing screens.

### 5.6 State overlap and precedence

The states overlap. A reeled grapple is also airborne. A wingsuit dive is also falling, and wingsuit and parachute both count as falling. A vehicle-parachute is both an attach state and a parachute state. `IsInVehicleAttachState` spans the enter and exit animations. The pause and UI signals (§5.5) hold regardless of the character state beneath them.

A classification of the player's state resolves each overlap by testing the more specific signal first:

1. The UI and pause signals.
2. A teleport on this tick (§4.3).
3. Vehicle attach (`IsInVehicleAttachState`, with class from §5.3 tested helicopter, plane, motorcycle, car, then sea, and the seat from `m_LocalPlayerSeat`).
4. Grapple traversal: `IsReelingIn` (`SB_IN_REELING_IN`), `IsGrappleHanging`, `IsReeledIn`, `IsPreReelingIn` (`SB_IN_PRE_REEL`), and `IsPreHang` (`SB_IN_PRE_HANG`), with the `GHS_*` hook state in `GrapplingHook::m_State` as the fine discriminator.
5. Wingsuit (`IsUsingWingsuit`, `SB_IS_WINGSUIT`, gated on `m_InstanceData`).
6. Parachute (`IsUsingParachute`, `SB_IS_PARACHUTING`, or `IsInAttachedToParachute`, `SB_IN_ATTACHED_TO_PARACHUTE`, for the vehicle-parachute case).
7. Free fall (`IsFreefalling`, `IsFalling`, and `IsFastfalling`: `SB_IS_FREE_FALLING`, `SB_IS_FALLING`, and `SB_IS_FASTFALLING`).
8. Swimming (`IsSwimming` and `IsUnderwaterSwimming`: `SB_IS_SWIMMING` and `SB_IS_UW_SWIMMING`).
9. On foot when nothing else matches.

The `EvaluateCharacterOrientation` call count advances every on-foot tick including idle (§4.1), so it corroborates the on-foot case but does not separate the other states.

The full read is one pointer chase to `m_ControlParameters`, three word loads, a fixed set of bit tests, and a `GetVehiclePtr` only when a vehicle bit or state indicates a vehicle.

### 5.7 Edge cases

- Transitions. Vehicle enter and exit, grapple wind-up (`IsPreReelingIn`/`IsPreHang`), and reel release all pass through animation states where the coarse bit is not yet set but the body is already committed. `IsInVehicleAttachState` spans the vehicle transition, and the pre-* predicates cover the grapple wind-up. During a known transition, the state-machine-hash predicates (§5.2) track the state where the raw bit lags, and a blend frame can flip a predicate for a single tick.
- Overlapping states. See §5.6.
- Swimming. `IsSwimming` is set independently of the on-foot locomotion task. The `EvaluateCharacterOrientation` call count (§4.1) does not identify a swimmer as on foot or as swimming; only the swim bits do.
- Spawn and stream-in. The `m_InstanceData`-gated bits (wingsuit) read false until the animation instance exists, and `m_ControlParameters` or `m_InstanceData` can be null in the first frames.
- Teleports. On the tick a fast travel or mission warp re-bases the character (§4.3), the state signals can momentarily misclassify the frame.
