# FSR anti-aliasing and upscaling

The flat game's anti-aliasing is from 2015: SMAA, with an optional T2X temporal variant. The mod already disables T2X in stereo (its shared history ghosts across the two eye dispatches; see `anti_aliasing_apply` and rendering §5.7) and falls back to SMAA 1x, which is a passable edge filter but nothing more. AMD's FidelityFX Super Resolution (FSR) is the modern replacement: a temporal reconstruction pass that does substantially better anti-aliasing than SMAA, and — with one extra piece of plumbing — doubles as a resolution upscaler, which VR will want badly.

This document records how FSR is integrated: which version, where it dispatches, and the order it was built in. The concrete reverse-engineering it leans on lives in `rendering.md` (the post-effects chain, the buffers, the stereo double-dispatch) and the pyxis-defs.

## Why FSR, and which version

The alternatives are ruled out for a mod shipping into a third-party game on mixed GPUs. DLSS is NVIDIA-only and its license is hostile to this use case; XeSS's cross-vendor path is DX12-only (its DX11 backend is Intel-Arc-only). FSR 4 is disqualifying: it is an ML model gated to AMD RDNA4 (with later INT8 backports to RDNA3/RDNA2), so it never runs on NVIDIA or Intel — a non-starter for a mod that has to run on whatever GPU the player owns. FSR is MIT-licensed, runs on every vendor, and has a DirectX 11 path. That license and cross-vendor reach are the whole reason it wins.

**The mod ships FSR 2.2.1**, via the MIT community DX11 port (`optiscaler/FidelityFX-FSR2-DX11`), wrapped by the `fsr-sys` crate. FSR 3.1 is the newest version still on plain SM6.2 compute with no ML hardware gate, MIT, with an explicit native-AA mode and the newer `ffxapi` interface, but its DX11 backend is community-maintained, and the FSR 2.2.1 DX11 port is the one that is stable under Proton, so the mod uses 2.2.1. The 2.2 API is clunkier and its native-AA setup is manual, but the reconstruction quality at 1:1 is what matters here and the port loads and dispatches reliably.

## The engine already produces every input FSR needs

FSR's inputs all exist on the `GraphicsEngine` singleton and are valid at the start of the post-effects block (rendering §4):

- **HDR color** — `m_MainColorBuffer` (`MainColorBuffer`, R11G11B10F). Holds the clean HDR scene at the start of the post chain; the mod already captures it there (`capture_main_color`).
- **Depth** — `m_MainDepthTexture` (`MainDepthBuffer`, D32FS8, reverse-Z, near=1/far=0). FSR must be told the depth is inverted (and infinite-far) to match.
- **Motion vectors** — `m_VelocityBufferTexture` (`motion_blur_velocity_buffer`, ABGR32), per-object screen-space velocity written in `RP_Z_AND_VELOCITY_PASS`. These are the hardest input to synthesize, and the engine already produces them.
- **Exposure** — `CToneMappingEffect::m_ExposureBrightPoint` (the applied exposure), metered once per real frame. Only needed on the pre-tonemap (HDR) dispatch path; the post-tonemap path doesn't use it.

The one input the mod must build itself is a **per-eye previous-frame view-projection** for correct stereo motion vectors. The engine snapshots a single previous VP in the sim path (`Camera::UpdateRender`), not per dispatch, so each eye needs its own. This is the same per-eye-VP work already identified for the stereo render generally (rendering §5.7) — FSR inherits it, it is not new to FSR. The mod implements it as the stereo MV correction in the decode pass (see *Motion vectors* below): the mod snapshots per-eye view-projections in the `SetupRenderCamera` hook and re-anchors each eye's vectors at its own previous pose, without touching engine state.

## Where it dispatches: post-tonemap

The mod dispatches FSR post-tonemap, at the engine's anti-aliasing hook. There were two candidate dispatch points; this one is the SMAA drop-in.

**Post-tonemap, at the anti-aliasing hook (the shipped path).** SMAA already runs at step 9 of the post chain (rendering §3), after the HDR→LDR tonemap at step 7, on the LDR temp texture in the manager's three-slot ring. FSR drops in at the existing `anti_aliasing_apply` hook and is fed that same LDR image, in exactly the slot SMAA reads. No HDR flag, no exposure wiring — the image is already exposed. The mechanical cost is mimicking the slot-ring handoff (read slot N through the manager's texture array at [`PostEffectsManager::SRGB_RESULT_TEXTURE_SLOT_BASE`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::post_effects::PostEffectsManager::SRGB_RESULT_TEXTURE_SLOT_BASE) and [`PostEffectsManager::RESULT_TEXTURE_SLOT_BASE`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::post_effects::PostEffectsManager::RESULT_TEXTURE_SLOT_BASE), write the result into the next slot, advance the index — the engine AA does precisely this), and a modest quality cost: FSR reconstructs already-tonemapped color, so it can't recover highlight detail the tonemapper already compressed. Effects after step 9 (sun halo, fade) then render on top un-anti-aliased, but those are full-screen overlays (an additive bloom and a color multiply), so it doesn't matter.

**Pre-tonemap, at the post-chain entry (the deferred alternative).** FSR's canonical position is on HDR pre-tonemap color, where its highlight reconstruction has the full dynamic range to work with. Dispatching at the start of the post block (the `capture_main_color` seam, where MainColor still holds the clean HDR scene), resolving into MainColor in place, and letting the rest of the chain tonemap the cleaned image is the better-quality input, at the cost of wiring the HDR and auto-exposure flags and using a less conventional injection point. This path is not yet built (see order-of-work step 6).

Note that FSR's usual "before tonemap" placement is driven mostly by *upscaling*: an upscaler must run before resolution-dependent effects so they execute once at display resolution. That argument does not apply at native AA res, so it does not force the early position here; the remaining pre-tonemap argument is purely the highlight-quality one, which is modest.

The engine's own AA is suppressed wherever FSR is active: the same `anti_aliasing_apply` detour that forces SMAA 1x in stereo drops [`AntiAliasingEffect::m_Mode`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::post_effects::AntiAliasingEffect##field-m_Mode) to off ([`AAMode::AA_NONE`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::post_effects::AAMode##variant-AA_NONE) is the passthrough branch in `Apply`).

## Design for upscaling, build for AA

VR is the reason to care about upscaling. Stereo means rendering two eyes, each at the runtime's requested supersample (commonly 1.4–2.0× the panel) to counter lens-distortion sampling, at 90 Hz against a hard deadline — several times the pixel cost of a flat frame, on a deferred 2015 engine that isn't cheap. Missing the deadline in a headset means reprojection and judder, which is nauseating rather than merely ugly. Rendering the scene below panel resolution and upscaling is the standard lever, and FSR is one of the few cross-vendor ways to do it with temporal quality instead of a blurry stretch.

The crucial fact: **FSR's AA mode and upscaling mode are the same context, the same inputs, the same dispatch.** The only differences are that `renderSize < displaySize` instead of equal, and that the scene must actually be rendered at the lower per-eye resolution. So the integration built for AA *is* the upscaler, minus the resolution plumbing — there is no throwaway work. Accordingly:

1. The integration carries `renderSize` and `displaySize` as explicit parameters; they are not hardcoded equal. Native AA is just the first configuration of an upscaler.
2. Native AA (1:1) ships: testable on the desktop preview, no dependency on the resolution re-init, and it takes SMAA's place directly.
3. With the VR runtime and the per-eye resolution re-init (re-driving `CreateRenderSetups` / `Graphics::Reset` at a chosen per-eye resolution) in place, dropping `renderSize` below `displaySize` turns it into an upscaler with no FSR-side rework, just a render-scale slider. The slider is not built (order-of-work step 7).

This also de-risks in the right order. The per-eye motion-vector work is shared by both modes, but at native res a motion-vector bug is visible and forgiving, whereas at low render scale it is brutal smearing on every head turn. Proving the MVs at 1:1 first means the hard upscaling case inherits a known-good velocity path.

### VR-specific upscaling caveats (for when render scale drops below 1:1)

- **Disocclusion on head motion.** Fast head turns reveal large regions with no temporal history; temporal upscalers fall back to spatial reconstruction there, which is softest exactly when you are moving. Favor a conservative render scale (≈77–85%, "Quality"/"Ultra Quality") over aggressive (50%, "Performance").
- **Compositor reprojection interaction.** The OpenXR runtime may apply its own motion reprojection to hit framerate; stacking FSR temporal reconstruction under it can compound artifacts. Tunable, but only evaluable in-headset.
- **Motion vectors matter more.** An upscaler leans on MVs far harder than native AA; this is why the MV path must be solid before render scale drops.

## Motion vectors

FSR reprojects last frame's history through the current frame's motion vectors; a wrong MV path is the dominant source of ghosting and smearing, and it is what the whole temporal reconstruction leans on hardest under VR head motion.

**JC3's velocity encoding (RE'd from the shader bytecode).** The engine's `m_VelocityBufferTexture` (`"motion_blur_velocity_buffer"`, an 8-bit `ABGR8` target) does not store raw motion vectors. The velocity-write pixel shader (`rendervelocitybuffer` in `Shaders_F.shader_bundle`) computes, per pixel:

```
stored.xy = clamp((curUV - prevUV) * 8, -1, 1) * 0.5 + 0.5
```

where `curUV`/`prevUV` are the current/previous-frame screen positions in UV space (Y-down). So the buffer is **bias-encoded into [0, 1] with 0.5 = zero motion**, scaled ×8, and **clamped to ±0.125 UV per frame**. Two independent shaders confirm this: the motion-blur filter (`compositehighprecisionvelocityfilter`) decodes it with the exact inverse, `(stored*2 - 1) * 0.125`.

This is why FSR's `motionVectorScale` (a pure multiply) cannot consume the buffer directly: a multiply cannot subtract the 0.5 bias, so static geometry would read as constant motion. We decode it ourselves:

```
motion_uv = (stored.xy - 0.5) * 0.25     // = curUV - prevUV, UV space, Y-down
```

**The decode pass.** A compute shader reads `m_VelocityBufferTexture`, applies the decode above, converts to FSR's convention, and writes an `R16G16_FLOAT` buffer we hand to FSR with `motionVectorScale = (renderWidth, renderHeight)` (UV to pixels; FSR divides it by the render size, so the vectors stay in UV). FSR 2 reads a pixel's history at its current UV plus its motion vector, in Y-down UV (`ffx_fsr2_reproject.h`, `fReprojectedHrUv = fHrUv + fMotionVector`), so it wants the previous position less the current one; the engine stores the current less the previous, so the decode negates both axes (`MV_SIGN` in `payload/src/fsr/mod.rs`). The sign used to be negated in Y only, which the harness check below caught: every camera vector reached FSR with its horizontal component reversed, twice the camera's own motion in error.

One code of the encoding is a quarter of a 255th of the screen, 3.5 pixels at the headset's width, and zero motion falls between two codes, so a still pixel the velocity pass drew holds half a code of motion either way, and the clear value half a code too. The decode reads the clear value as no motion at all, and a drawn pixel whose motion is within one code of the camera's own (see the correction below) as the camera's alone.

**The stereo MV correction (issue #10's flicker).** The engine's velocity pass computes `curUV` with the *per-eye* current view-projection (the camera the mod offsets) but `prevUV` with the single sim-side *center* previous VP — so in stereo every static pixel carries a spurious lateral motion vector equal to the eye-vs-center parallax: depth-dependent (~20 px at 2 m at typical res, vanishing at infinity) and of **opposite sign per eye**. FSR then mis-reprojects each eye's temporal history by that amount, which shows as per-eye shimmer on high-contrast static edges — sun-shadow boundaries at grazing angles especially — worst under head motion. Confirmed by A/B: the flicker vanishes with FSR off. The fix lives in the decode pass: the `SetupRenderCamera` hook snapshots the center VP (pre-patch) and each eye's final VP (`stereo::VpHistory`), the CPU forms the two clip→previous-clip reprojection matrices in `f64` (`prevVP · inv(curVP)` — the world-scale translations only cancel at double precision), and the shader reconstructs each pixel from the raster depth, reprojects it with both, and adds `prevUV_center − prevUV_eye` to the decoded vector. Dynamic objects keep their object motion — only the camera term is swapped. The "centre" matrix is the previous view-projection the velocity pass actually encoded against when the payload can read it: the render camera's own `m_PreviousViewProjectionF` for an eye rendered whole, and that taken through the single-pass velocity rewrite's map into the eye's clip space for a half of the collapse (`encoded_previous_view_projection` in `fsr/mod.rs`). Under the harness's held camera the engine's previous camera is not the centre camera the mod snapshots, and the drawn pixels' motion, measured against the snapshot, was 70 to 90 pixels off at a still camera; against the engine's own matrix it is within the encoding's rounding under single-pass (a mean of 1.1 to 1.5 pixels) and 2.5 to 15 pixels off in multipass, whose velocity pass reads a previous camera that the render camera's at the post chain does not quite match (see "Verifying the motion vectors"). It runs while the stereo cameras are on (`payload/src/fsr/mod.rs`), and is a no-op without stereo disparity.

**No camera jitter.** FSR runs without a sub-pixel camera jitter: the camera is not jittered and the dispatch reports a zero offset. A jitter excited a blob-scale, both-eyes, scene-side (pre-FSR MainColor) shadow-term flicker whose mechanism survived a long bisection (issue #10): the stereo MV correction above, the eye-1 post-chain dedupe, a patch of the jitter-unstable vegetation LOD dissolve, and a series of shadow-pipeline interventions (fit unjitter, pristine-camera restore, atlas freeze) all left it tracking the jitter exactly, while exposure, the staged cascade constants, GI, SSAO, SSR, AO volumes, and occlusion queries were each ruled out empirically. FSR without jitter still resolves acceptably (no sub-pixel reconstruction, softer detail), so the mod trades sharpness for stability. The jitter, its motion-vector cancellation, and the LOD dissolve patch are deleted; the bisection record lives in issue #10.

**Why we decode the engine buffer rather than produce our own.** FSR needs *object* motion (vehicles, characters, vegetation), not just camera motion. Object motion requires each object's previous-frame world matrix — data the engine materializes per-draw across thousands of renderables and that has no central source we can read. The velocity buffer *is* that materialization (the engine walking every object and resolving current-vs-previous into one texture), so decoding it is the only way to get object motion short of re-running the velocity pass. A camera-only buffer we compute from depth + previous-VP would miss all object motion — the larger error. This is settled, not a compromise.

**Precision ceiling and follow-ups (deliberately deferred).** The decode recovers everything the buffer holds, but the buffer has an intrinsic ceiling: 8-bit quantization (the format) and the ±0.125 UV clamp (baked into the shader bytecode). The clamp is the dominant limit and saturates on fast head turns — exactly the VR case. Neither is removable cheaply:

- *Format tap* (hook `CreateRenderSetups` to make the velocity RT `R16G16F`): removes quantization only, not the clamp. Additive to the decode, low value on its own.
- *Shader replacement* (repack the bundle / hook shader creation to lift the clamp): removes both, but touches ~40 velocity variants and is disproportionate for a 2015 game's AA.
- *Hybrid (the real upgrade)*: keep JC3's decoded **object** velocity, but compute the **camera** component ourselves from depth + per-eye previous-VP at full precision, unclamped, and combine. This attacks the clamp precisely where it hurts in VR (head turns are camera motion) without touching shaders.

The hybrid is what ships; see "The hybrid decode" below.

**What the velocity buffer covers.** The velocity pass draws only what is enqueued on it: in the scenes the visual harness measured, the vegetation and a few hardware-instanced models (engine [`shaders.md`](../../engine/rendering/shaders.md#the-velocity-passs-motion-vectors)). Every other pixel keeps the cleared value, which decodes to zero motion. Without the hybrid decode below, FSR reprojects the static world's history as if the camera had not moved, whatever the head did; the correction leaves those pixels alone, since the engine encoded no camera motion there to re-anchor. The correction can be turned off (`fsr.stereo_mv_correction`, on by default; `fsr_mv_correction = "disabled"` in a visual experiment) to A/B that.

**The hybrid decode.** `fsr.hybrid_velocity` (on; `fsr_hybrid_velocity = "disabled"` in a visual experiment, and a switch beside the correction's in the debug UI's stereo section) gives the static world its real motion. Which pixels the velocity pass drew is read from the buffer itself: an undrawn pixel holds the target's clear value, which a dumped town eye showed at 12,687,814 of its 12,762,624 pixels, and which no velocity pixel shader writes except a pixel beyond about a hundred metres whose motion rounds to the same code, since every one of them writes its third channel from the clip `w` and saturates there (`rendervelocitybuffer` and `generalmkiiiprezvelocity` disassembled). For an undrawn pixel, and for a drawn one whose encoded motion saturated at the ±0.125 UV clamp, the decode reconstructs the pixel from its depth and reprojects it through the eye's own clip-to-previous-clip matrix (`prevVP_eye · inv(curVP_eye)`, formed in `f64` from the eye's own view-projections, so its real projection in both frames), and writes that motion, unclamped and at full precision. Every other pixel keeps the engine's motion with the correction above, so object motion survives where the engine wrote some. The same matrices serve multipass (the render camera's per-eye history) and single-pass (each eye's own matrices), canted and asymmetric eyes included, since nothing assumes the eyes parallel. The sky's depth is the infinite far plane, where the reprojection is the rotation alone. With no history (the first frame, a rebuilt context) the decode sends no motion and FSR resets; a camera cut, the view centre landing more than half the screen away in the previous frame at the far plane or at 2 m (`camera_cut` in `fsr/mod.rs`), resets that eye's history too. A far drawn pixel misread as undrawn gets the camera's motion instead of its own, and so does near geometry the velocity pass does not draw that moves with the head (the player's body and weapon, where they are not drawn there), which FSR's own disocclusion handling then has to catch.

With a still camera every pixel the hybrid decode gives the camera's motion decodes to exactly zero, and FSR keeps its history. That history takes about 64 frames to settle after a reset: in run 321, at the town in multipass with the camera still, the next frame differed from the last at 0.8 to 2.6 million pixels per eye after 2 to 16 frames of warm-up, 100,000 after 32, about 2,000 after 64, and 550 to 1,100 after 128 or 300. The thirty warm-up frames the coverage configs ask for leave it accumulating, which is most of why run 316's modes differed at 120,000 to 580,000 pixels with the hybrid on. Without the hybrid, the decode then read the clear value as half a code of motion and the correction added each eye's parallax to it, so FSR rejected most of its history each frame and every mode's output stayed close to its current frame, which is why they agreed at 11,000 to 66,000. Settled (120 warm-up frames, run 321) and with the decode fixed, the hybrid on and off give the same still image to within 1,000 to 8,000 pixels, and multipass and single-pass differ at 67,000 and 110,000 pixels per eye with FSR against 53,000 and 75,000 with the game's anti-aliasing: what remains is the single-pass render's own difference (the normals G-buffer differs at 22,000 and 190,000 pixels between the modes), which FSR's sharpening enlarges a little. It is accumulation state, not a per-mode error in the motion vectors, which decode to zero in both modes.

**Under single-pass stereo.** The collapse renders both eyes side by side into one double-wide target and runs the post chain once. `single_pass.fsr_per_eye` (on) resolves each half through its own eye's context: the decode reads the eye's window of the velocity and depth buffers and copies that window's depth into an eye-sized R32F texture (a depth-stencil resource cannot be copied by region), the eye's half of the colour is copied into an eye-sized input, and the result is copied back into the half. Each eye then has its own history at its own size, with no neighbourhood or history reaching across the seam, and the velocity pass's single-pass rewrite already writes each eye's motion in that eye's own screen space. The correction is taken from each eye's own matrices (the centre camera's view with the eye's projection, and the eye's view-projection, this frame's and last frame's), since the collapse keeps the render camera centred and the render camera's history holds the centred double-wide matrices. See "The shipped settings under single-pass" in [`single-pass-stereo.md`](../stereo/single-pass-stereo.md) for the measurement.

## Verifying the motion vectors

The harness saves what FSR is handed and checks it offline (`fsr_motion` and `fsr_depth` planes and the snapshots' FSR records, see "Snapshots" in [fast-comparison.md](../testing/fast-comparison.md); `python3 -m tools.rendering fsr-motion`). For every eye it reconstructs each pixel from the depth FSR read, reprojects it through the eye's recorded previous view-projection in double precision, and compares that camera motion, in FSR's convention and pixels, with the decoded vector times FSR's scale. Run 321 (`tools/rendering/suites/fsr.toml`, the town at 3584 by 3561 per eye) gives, for the pixels the hybrid decode gives the camera's motion (99.3 to 99.8% of each eye), the error's mean, 99th percentile, and largest value in pixels, against a camera motion of 22 to 26 pixels mean and up to 183:

| Scene | Multipass, each eye | Single-pass, each eye |
|---|---|---|
| Still | 0 / 0 / 0 | 0 / 0 / 0 |
| Rotating | 0.009 / 0.027 / 0.03 | 0.009 / 0.027 / 0.03 |
| Translating | 0.009 / 0.062 / 0.12 | 0.009 / 0.062 / 0.12 |
| Rotating, `index` rig (canted) | 0.008 / 0.027 / 0.04 | 0.008 / 0.027 / 0.04 |
| Rotating, shipped settings | 0.009 / 0.027 / 0.03 | 0.009 / 0.027 / 0.03 |

The residual is the reprojection in single precision and the 16-bit output. Before the fix (run 320) the same pixels were 50 pixels off on average while rotating, twice the camera's motion, because the horizontal sign was reversed; with the hybrid off they carry no camera motion at all (an error of the whole camera motion, 25 pixels mean and up to 183). The records are rounded back to single precision before the reconstruction: their shortest decimal form differs from the stored value enough that the near-plane division turned it into 3 pixels of apparent error at 0.2 m.

The pixels the velocity pass drew (0.2 to 0.7% of an eye, vegetation in these views) keep the engine's object motion on top of the camera's. Under single-pass they decode to within 0.03 pixels of the camera's motion, and to exactly zero with the camera still. In multipass they are 2.5 to 3.3 pixels off on average while still or rotating (largest 7.7 still, 9.4 rotating) and 8 to 15 while translating: the engine's encoding agrees with the render camera's previous view-projection only to within an eye-dependent parallax there, and the harness, whose held camera is not the camera the engine's simulation saw last frame, cannot say what the engine uses in a headset. The check of the engine's encoding against the recorded matrices (`engine vs encoded` in the tool's output) is independent of the decode, and is what confirmed the encoding's convention.

## Against the game's anti-aliasing

Run 321's quality scenes render, in one schedule at one clock and pose, FSR with and without the hybrid decode, the game's anti-aliasing (SMAA 1x, which changed 1.1 million pixels of an eye in this view), FSR at a reduced size, and a reference: the left eye at twice the pixels with the game's anti-aliasing, downsampled by area (`python3 -m tools.rendering fsr-quality`). Against the reference, the left eye (mean absolute difference in 8-bit codes, PSNR, edge sharpness relative to the reference's, and ghosting, the gradient added where the reference is flat):

| Scene | FSR | FSR, hybrid off | Game's AA | FSR at 0.85, scaled up |
|---|---|---|---|---|
| Still | 3.00, 30.9 dB, 1.18, 0.156 | 3.06, 30.9 dB, 1.18, 0.170 | 1.85, 33.7 dB, 0.93, 0.103 | 2.71, 32.4 dB, 0.97, 0.154 |
| Rotating | 2.23, 32.9 dB, 1.05, 0.109 | 2.77, 31.2 dB, 0.84, 0.134 | 1.91, 33.3 dB, 0.93, 0.086 | 2.50, 33.1 dB, 0.85, 0.116 |
| Translating | 2.36, 32.8 dB, 0.96, 0.165 | 3.02, 30.6 dB, 0.85, 0.241 | 2.05, 32.9 dB, 0.93, 0.121 | 2.84, 32.3 dB, 0.78, 0.166 |

Multipass and single-pass score within 0.1 dB of the left eye alone. With the camera still, the next frame changes at 500 to 1,100 pixels of an eye with FSR and 1,700 to 6,200 with the game's anti-aliasing (a mean change under a hundredth of a code in both). The game's anti-aliasing is the closest to the reference in every scene. FSR runs without a jitter (see *No camera jitter*), so it adds no sub-pixel samples: at 1:1 it is a temporal filter and the RCAS sharpening, which is what the sharpness above 1 and the extra ghosting measure; its one gain is the steadier still image. The hybrid decode is what keeps FSR usable in motion: without it FSR loses 1.7 to 2.1 dB, a fifth of its sharpness, and gains 25 to 45% more ghosting. The reference shares the game's anti-aliasing, which favours it; the margins at rest (2.8 dB) are larger than that bias explains, and in motion they are 0.1 to 0.4 dB.

## What it costs

Run 321's benchmark (`tools/rendering/suites/benchmark.toml` variants `fsr-off` and `fsr-hybrid-off`; single-pass, 72 Hz pacing, 3584 by 3561, three repeats; `target/harness-probe/benchmark/321-fsr`), medians in milliseconds:

| Scene | Mode | FSR (GPU) | GPU | Frame, median / 1% low |
|---|---|---|---|---|
| Capital | FSR | 2.11 | 13.55 | 13.90 / 26.96 |
| Capital | FSR, hybrid off | 2.11 | 13.58 | 13.93 / 27.45 |
| Capital | Game's AA | 0 | 13.54 | 13.90 / 17.77 |
| Capital | FSR at 0.85 | 1.52 | 13.62 | 13.93 / 26.29 |
| Capital | Game's AA at 0.85 | 0 | 13.27 | 13.88 / 16.63 |
| Town | FSR | 1.92 | 11.79 | 13.90 / 14.82 |
| Town | FSR, hybrid off | 1.92 | 11.77 | 13.90 / 14.79 |
| Town | Game's AA | 0 | 10.23 | 13.90 / 14.83 |
| Town | FSR at 0.85 | 1.38 | 10.28 | 13.90 / 14.82 |

The hybrid decode costs nothing measurable. FSR's seam is 1.9 to 2.1 ms at the headset's size and 1.4 to 1.5 ms at 0.85; at the town it adds 1.6 ms to the GPU's frame, and at the capital, where the GPU is already at the frame's length (its spans include its waits on the draw task), it turns the 1% low from 17.8 ms into 27 ms: one frame in a hundred misses a display period, which FSR off does not. The medians are the 72 Hz pace in every case. The mod cannot render below the headset's size and let FSR upscale (`renderSize` is always the display size, see *Design for upscaling, build for AA*); the cheaper configuration it can run is a smaller render with FSR at 1:1 and the compositor scaling it, which saves 0.6 ms of FSR and keeps the capital's misses, and loses 1 to 2 dB at rest against FSR at full size in exchange for 0.2 dB in rotation.

## Verdict

At 1:1 without a jitter, FSR costs 1.9 to 2.1 ms of GPU time and the capital's 1% low, and gives an image further from the supersampled reference than the game's SMAA in every measured scene: sharper (the RCAS pass), with more spurious gradient, and with a steadier still image. Turning it off saves that time and loses only the sharpening and the stillness at rest; rendering smaller with FSR saves less and is no closer to the reference. FSR earns its cost only with what it is built for, sub-pixel jitter or upscaling below the display size, neither of which the mod has. The recommendation is to turn FSR off by default until one of those exists, keeping it switchable. The hybrid decode should stay default-on: it costs nothing, and it is what gives FSR any camera motion at all; without it FSR in motion is 1.7 to 2.1 dB worse and ghosts more.

## Runtime toggle

FSR is switchable on and off at runtime (`config.fsr.enabled`, default on), so it can be A/B'd against the engine's SMAA live in the preview. The toggle drives two coupled things together: whether the FSR dispatch runs, and whether the engine's own `CAntiAliasingEffect` is suppressed. Off means engine AA runs as normal and FSR does nothing; on means FSR runs and engine AA is dropped to off. The render-scale parameter (1:1 for now) sits alongside it, ready for the upscaling slider later. It lives in the `FsrConfig` block with the sharpening switch and strength; the motion-vector sign convention is a constant in `payload/src/fsr/mod.rs`.

The velocity encoding above was recovered by extracting FSR's reference shaders and JC3's own velocity shaders from `Shaders_F.shader_bundle` (an ADF container; shaders are named DXBC blobs laid out as `<name>\0…pad…DXBC<bytecode>`). The extraction recipe — slice by the `DXBC` magic + the size field at `+0x18`, disassemble via `D3DDisassemble` from the native `d3dcompiler_47.dll` under Wine — is documented in `shaders.md`, should other shaders need reading later.

## Risk status

- **DX11 port maturity under Proton/Wine.** Resolved by shipping the FSR 2.2.1 DX11 port rather than the FSR 3.1 one. The FSR 3.1 native DX11 backend is community-maintained and newer; the FSR 2.2.1 port builds, unpacks its shader permutations, and dispatches reliably under Proton, which is why it is what ships (see *Why FSR, and which version*).
- **Motion-vector convention and scale.** Resolved and verified offline against the depth (see *Verifying the motion vectors*). The buffer is bias-encoded 8-bit (`(curUV-prevUV)*8`, clamped ±1, `*0.5+0.5`), so it needs a decode pass, not just a scale; FSR's sign convention comes from its reprojection shader (`MV_SIGN`).
- **Reverse-Z / infinite-far flags.** Depth is reverse-Z near=1/far=0; FSR is told the depth is inverted (and infinite-far where applicable) or reprojection breaks.
- **Jitter ownership.** The engine's TAA jitter, which alternates between the two offsets in [`jittered_samples`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::post_effects::jittered_samples), feeds only its own SMAA T2X and is dropped while FSR runs. FSR runs unjittered — see *No camera jitter*.
- **Reactive / transparency masks.** Still open. Water, particles, and muzzle flashes can ghost without a reactive mask; a second pass is planned if transparencies smear.
- **Per-eye FOV / asymmetric frusta (VR only).** FSR's dispatch takes a single `cameraFovAngleVertical` scalar to linearize depth for reprojection. On the flat desktop both eyes share one symmetric projection, so deriving the vertical FOV from the render camera's projection (`data[5] = 1/tan(fovV/2)` — invariant under our reverse-Z, and sidestepping the horizontal-vs-vertical question) is exact. In real VR each eye has its own field of view *and* an asymmetric off-axis frustum (left ≠ right, up ≠ down — the "wedge"), which a single vertical-FOV scalar cannot represent. The extraction already handles it: because we read FOV from the projection matrix rather than a constant, it yields a per-eye vertical FOV automatically from the per-eye projections VR injects — and a symmetric-equivalent vertical FOV is a good enough depth-linearization approximation for mild asymmetry. Revisit only if depth-reconstruction artifacts appear at the frustum edges under wide-FOV / strongly-canted HMD projections. Ties into the VR runtime's off-axis-projection work.
