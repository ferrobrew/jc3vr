# UI rendering

How Just Cause 3 renders its Scaleform UI each frame: the update and capture on the game thread, the draw on the UI render worker, the off-screen movies, the display-info writes that move a clip without running ActionScript, and how the UI's colour and alpha come out in its target. Where the UI sits in the frame and which surface it draws into is [rendering §10](rendering.md#10-ui--hud-pipeline). The screens, the root movie, and the traffic between ActionScript and native code are in [the pause-menu doc](../pause-menu.md#screens-and-the-root-movie); the Scaleform runtime, the loader, and standalone movies are in [scaleform.md](../scaleform.md). The addresses and layouts are in the pyxis modules [`ui::ui_manager`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/ui::ui_manager) and [`ui::scaleform`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/ui::scaleform).

## One movie

Every screen shares the root movie, [`UIManager::m_Movie`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_Movie), an instance of `ui/root.gfx` that loads `hud.gfx`, `pause.gfx`, and the rest as children. The whole UI is therefore one display tree, captured once and drawn once per frame into one target. The only movies outside it are the engine's render-to-texture UIs (see [Off-screen movies](#off-screen-movies)).

## The update side

`CUIManager::PreRender` runs on the game thread. It takes [`m_DeferredRenderLock`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_DeferredRenderLock) and is gated on four flags: a system-ready flag that pyxis does not bind, and the three render gates [`m_RenderReady`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_RenderReady), [`m_RenderActive`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_RenderActive), and [`m_RenderingEnabled`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_RenderingEnabled). In order, it:

1. claims the capture thread for itself ([`m_CurrentCaptureThread`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_CurrentCaptureThread) and the movie's own capture thread together);
2. flushes queued `root.OnVideoStop` invokes and calls [`UpdateCachedValues`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##func-UpdateCachedValues);
3. calls the `Update` virtual of every active registered screen, which includes [`HUDUI::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::HUDUI##func-Update) with its invokes and its per-frame marker writes;
4. ages the image delegates and advances and processes the dying-movie list;
5. calls `CRenderToTextureUI::Update` on every render-to-texture UI;
6. calls [`MovieImpl::Advance`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::MovieImpl##vfunc-Advance) and then [`MovieImpl::Capture`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::MovieImpl##vfunc-Capture) on the root movie;
7. updates the UI post effects.

So every screen's update, then the advance, then the capture. `Advance` is called with its own capture turned off, and `Capture` once after it, so each capture follows exactly one update of every screen. The capture's implementation, [`MovieImpl::CaptureImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::MovieImpl##func-CaptureImpl), is the last point at which a write to the display tree reaches this frame's snapshot.

`PreRender` runs once per render update. In gameplay, paused or not, the render update reaches it through `CUIManager::StartPrerender`, which queues it as a CPU fragment (`CUIManager_PrerenderProxy`) on the frame's fragment queue; the frontend and the other game states call it directly. Nothing in the frame's draw calls it.

## The capture and the snapshot

`Advance` runs ActionScript and mutates the display tree; `Capture` publishes the tree's changes as the pending snapshot for the renderer. The render side takes the latest captured snapshot with [`RTHandle::NextCapture`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::RTHandle##func-NextCapture) and draws it; it never sees the live tree.

`Render::Context::Capture` mutates the active snapshot, the same data every game-thread UI write touches, and nothing locks writers against it; the capture lock only orders `Capture` against `NextCapture`. The engine is safe because it captures only inside `PreRender`, on the game thread that also makes every UI write. A capture from any other thread races those writes. The constraints that follow for anything that captures or edits the tree are listed in [the issue #8 and #14 post-mortem](../../issues/08-14-hud-overlays-and-depth.md#constraints-established-the-important-part).

[`UIBase::InvokeImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_base::UIBase##func-InvokeImpl) runs ActionScript at once only when the calling thread is the capture thread in `m_CurrentCaptureThread`, and queues the call otherwise, so moving capture ownership off the game thread turns every screen invoke into a queued, delayed one.

## The render side

[`UIManager::StartRender`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##vfunc-StartRender) queues a CPU fragment on a worker whose body calls the [`Render`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##vfunc-Render) virtual. [`SyncRender`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##vfunc-SyncRender) waits for it, and [`Submit`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##vfunc-Submit) takes the master graphics context lock and flushes the HAL.

The render, [`UIManager::RenderImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##func-RenderImpl), takes the deferred render lock and checks the same three render gates. It stamps the render thread on the texture manager and on the UI command queue and executes the queue, binds [`m_RenderBuffer`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_RenderBuffer) with [`RenderHAL::SetRenderTarget`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::RenderHAL##vfunc-SetRenderTarget), and opens a frame and a scene ([`BeginFrame`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::RenderHAL##vfunc-BeginFrame), [`BeginScene`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::RenderHAL##vfunc-BeginScene)). It calls `NextCapture` on the movie's display handle and, when a snapshot was consumed, [`RenderHAL::Draw`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::RenderHAL##func-Draw) on its render entry. It then closes the scene and the frame and pops the render target. It never clears the target: the UI is drawn over whatever the target holds, which in the game is the finished frame.

The IDB labels this function `CRenderToTextureUI::Update`, and labels the real `CRenderToTextureUI::Update` (see [Off-screen movies](#off-screen-movies)) `CUIManager::DrawOcclusion`. The first body uses the manager's lock, HAL, movie, render buffer, and gates; the second advances one render-to-texture movie. pyxis binds the first under its correct name.

## Off-screen movies

The engine's render-to-texture UIs (`CRenderToTextureUI`, the in-world screens described in [scaleform.md](../scaleform.md#standalone-movies-crendertotextureui)) each own a separate movie. `PreRender` advances each of them through `CRenderToTextureUI::Update`, which, when the UI's code interface is active, calls that screen's `Update`, makes the game thread the movie's capture thread, and advances the movie.

[`UIManager::RenderOffScreenTexturesImpl`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##func-RenderOffScreenTexturesImpl) then draws them. For each one whose code interface is active, it sets the capture thread and captures that movie, builds a render target from the UI's colour and depth surfaces with [`RenderHAL::CreateRenderTarget`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::RenderHAL##func-CreateRenderTarget), pushes it with the movie's rectangle ([`PushRenderTarget`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::RenderHAL##vfunc-PushRenderTarget)), opens a scene, consumes the capture and draws it, closes the scene, calls the manager's `Submit`, pops the target ([`PopRenderTarget`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::RenderHAL##vfunc-PopRenderTarget)), and releases it. Every off-screen draw is flushed before its target is popped. Unlike the root movie, these movies are captured from the render side, which takes capture ownership from the game thread for the call.

`PreRender` also calls the per-movie update on an object the manager holds next to a render block, sets a flag on that block, and adds it to the render lists (`CRBILists::Add`). That looks like a path for drawing a UI movie into the world as a render block. It is not bound or investigated.

## Display-info writes

[`ValueObjectInterface::SetDisplayInfo`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::ValueObjectInterface##func-SetDisplayInfo) writes a display object's presentation state through a `GFx::Value` handle to it. [`DisplayInfo::VarsSet`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::DisplayInfo##field-VarsSet) selects which fields apply: x, y, rotation, x scale, y scale, alpha, and visibility. pyxis binds only the visibility bit, [`DisplayInfo::V_VISIBLE`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::DisplayInfo::V_VISIBLE); the others are verified in the IDB but not yet bound. A position is snapped to twips and applied through the display object's `SetMatrix`, which updates that object's own render node. No ActionScript runs and no AS3 property setter fires, so the write is node-local and cheap. Text fields take a separate text-rectangle path, and objects flagged as 3D take a different branch. `HUDUI::Update` places and shows its markers this way every frame ([`HUDUI::UpdatePOIs`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::HUDUI##func-UpdatePOIs), see [Points of interest](#points-of-interest)), and the weapon selection cross is placed the same way (see [weapon-selection.md](../gameplay/weapon-selection.md#placement)).

## Points of interest

Every world-anchored HUD marker is a point of interest ([`POI`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::poi::POI), `CPOI`, a game object): mission objectives, map waypoints, enemy and vehicle health markers, weapon pickup hints, active explosives, and the detector target. Mission objectives, game systems through `CHUDUI::RegisterPOI`, and the HUD's own pickup, explosive, and detector updates create them. Each registered POI has a record ([`POIRecord`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::POIRecord)) in the HUD's list ([`HUDUI::m_POIListHead`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::HUDUI##field-m_POIListHead)), guarded by [`m_POIListLock`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::HUDUI##field-m_POIListLock) because other systems register and unregister POIs from their own threads. A record holds a weak reference to the POI, an optional strong one that keeps it registered, the marker clip ([`m_Element`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::POIRecord##field-m_Element), a pooled `poi` clip taken on the record's first update), and whether the marker is shown ([`m_Visible`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::POIRecord##field-m_Visible)).

[`HUDUI::UpdatePOIs`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::HUDUI##func-UpdatePOIs) walks the list under the lock once per HUD update. It drops records whose POI is gone, skips invisible POIs, and for each live one calls [`POI::UpdatePOI`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::poi::POI##vfunc-UpdatePOI), which rebuilds [`m_Transform`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::poi::POI##field-m_Transform) from the attached object. The world point it then projects is that transform's translation, freshly updated. It projects through [`UIManager::Get2DInfo`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##func-Get2DInfo) with the active camera's view-projection, its orthonormalised transform and field of view, a fixed margin, the POI's clamp flag, and its 2D offset. The distance range, the behind-the-camera test, and the vehicle, settlement, mission, and ROM filters decide visibility, and a change invokes the movie's `ShowPoi` or `HidePoi`. A shown marker gets its icon scale and alpha, distance text, edge-arrow state, flash, label, and progress bar through the movie's `UpdatePoi`, then its x and y through a display-info write. The one on-screen POI nearest the stage centre whose label box contains the centre shows its label ([`m_ShowingLabelPOIId`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::HUDUI##field-m_ShowingLabelPOIId)). The `poi` clip lays its children out around its own origin and never reads its own position, so the clip renders the same wherever it is placed.

`Get2DInfo` calls [`Convert3DCoords`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##func-Convert3DCoords), which maps NDC into stage coordinates. When the cached viewport ratio differs from the stage's ([`m_CachedStageRatio`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_CachedStageRatio)), it stretches the longer axis so the stage keeps its shape, and the frame it maps into extends past the stage on that axis: the movie's show-all scaling, under which content outside the stage on that axis is still visible. A point inside the safe area ([`m_SafeArea`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_SafeArea)) shrunk by the margin is on screen. Otherwise an unclamped marker is off screen in front of or behind the camera, and a clamped one, after a point outside the camera's horizontal field of view is swung back toward the view, is clamped to the shrunk safe area with an edge code ([`ClampToScreen`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##func-ClampToScreen)).

[`ComputeSafeArea`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##func-ComputeSafeArea) derives the safe area from the stage, the safe-area setting ([`m_SafeAreaPercentage`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_SafeAreaPercentage)), and the cached viewport size, and pushes it to every screen, whose movies anchor their edge containers to it. Where the cached viewport is relatively longer than the stage on an axis, the safe area is widened on that axis by the extra extent the viewport shows at the stage's scale, so the edge containers move out into the visible frame beyond the stage. It reads the cached viewport size, not the movie viewport, so the layout input and the render viewport can differ.

Two related HUD state machines sit next to the markers. Health: [`HUDUI::UpdateHealth`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::HUDUI##func-UpdateHealth) pushes the character's health ([`Character::GetHealth`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##vfunc-GetHealth), on the scale of [`m_MaxHealth`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/character::character::Character##field-m_MaxHealth)) to the movie when it changes, and the movie shows it only as the full-screen damage vignette and the reticle's low-health outline. The weapon readout: [`HUDUI::UpdateShowWeaponsAndGrenadesUiTimer`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::HUDUI##func-UpdateShowWeaponsAndGrenadesUiTimer) holds [`m_ShowWeaponsUiTimer`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::hud_ui::HUDUI##field-m_ShowWeaponsUiTimer) full while the character should show its weapon, counts it down otherwise, zeroes it on holstering, and shows and hides the readout on its edges; the grenade readout has its own timer.

## Colour, alpha, masks, and filters

The blend states are verified in the IDB (`Scaleform::Render::D3D1x::HAL::createBlendStates`, not bound in pyxis). The rest of the section follows Scaleform's D3D1x HAL source (`applyBlendModeImpl`).

- The HAL builds two blend states per Scaleform blend mode and one more for mask submission, from a per-mode table of colour and alpha operations and factors. The ordinary set draws normal content with `SRC_ALPHA, INV_SRC_ALPHA` on colour and `ONE, INV_SRC_ALPHA` on alpha. The second set is the same table with a colour source factor of `SRC_ALPHA` replaced by `ONE`, for content that is already premultiplied: render-target layers, filter results, and cached bitmaps. The mask state writes no colour.
- Drawn this way over a target cleared to transparent black, ordinary content leaves `rgb = c * a` and `alpha = a`: the UI target holds premultiplied colour with coverage alpha, and premultiplied layers and filters compose the same way. A consumer that composites the target must blend it as premultiplied (`ONE, INV_SRC_ALPHA` on colour).
- Masks are stencil-based: a mask is submitted with colour writes off and its rectangles are cleared from the stencil afterwards (`PushMask_BeginSubmit`, `drawMaskClearRectangles`).
- A filtered subtree is drawn into a temporary target from the render buffer manager, the filter passes run on it, the result is cached while the subtree is unchanged, and it is drawn back with the premultiplied blend states. Filter output extends past the clip's geometric bounds by the filter radius. This is the usual Scaleform behaviour, consistent with the premultiplied states above, and not traced in the IDB.

## The HUD movie's layout

`ui/hud.gfx`'s main timeline places ten top-level clips, listed on [`ScaleformInfo`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::scaleform::ScaleformInfo): the six `MCI_safe_area_*` edge and corner groups; `MCI_safe_area_center`, which holds `MCI_reticles` (the weapon, grapple, and mech reticles), the pickups, the full-screen overlay clips, and the large button hint; `MCI_weapon_selection_wheel`; `MCI_hud`; and `MCI_poi_stage`. Everything else is created by ActionScript.

`MCI_safe_area_bottom_right` holds, among others, the weapon readout (`MCI_weapons_parent`), the grenade readout, the heat readout (`MCI_heat_container`), the notifications, the systemic button hints, the cutscene skip prompt, and the tether readout. The tether readout is `MCI_dual_tether`: the count of tethers in use out of the most the grapple holds, written as text by the movie's `UpdateTetherCount`, and a timeline of states for a new tether, a broken one, retracting, and release. `ShowDualTetherUi` shows it when a new tether appears in the movie's `UpdateWireData`, and it fades out when every tether is gone. The movie also builds a list of the attached tethers with their tension bars in `MCI_dualtether_stage`, but its constructor hides that stage and nothing shows it again.

The live marker pool is a set of anonymous clips directly under the HUD clip, not under `MCI_poi_stage`, as the live display tree shows in game.

Every mask placement in the movie is inside a widget (the circular meters, the life bar, the timers, the chaos award, the mission objective); the main timeline places none. Filters are common: hundreds of placements carry one, mostly glows, then blurs and drop shadows. A handful of placements use a non-normal blend mode, and one is cached as a bitmap.
