# VR runtime: OpenXR, per-eye projection, per-eye resolution

The OpenXR runtime is built. The mod brings up a real OpenXR session against the game's own D3D11 device, drives the render camera from the located HMD pose, builds a per-eye off-axis projection from the headset's field of view, renders each eye at the HMD-recommended resolution, blits the two eye captures into a stereo swapchain, and submits a projection layer to the compositor — while the game's own desktop present stays suppressed and one eye is mirrored back into the game window. This doc describes what runs, in the order it runs, and gathers the headset-only checks the desktop build could not settle into a single playtest checklist at the end.

The implementation lives in `crates/jc3vr-view/src/vr/` (`mod.rs` owns the session and the frame API; `frame.rs` bridges a frame to the render hooks; `projection.rs` builds the off-axis matrices; `blit.rs` copies the eyes into the swapchain; `resolution.rs` drives the per-eye resize; `mirror/` presents the desktop mirror; `config.rs` is the config surface) plus the frame-loop wiring in `payload/src/hooks/game.rs` and the VR headpose source in `crates/jc3vr-view/src/headpose/xr.rs`. It is the runtime half that turns the desktop stereo prototype (rendering §11) into something a headset displays; the head/body scheme, the HUD, and controllers hang off it.

## The runtime loop

The whole loop runs on the game's main thread, inside the `game_update_render` hook (`payload/src/hooks/game.rs`), in this order:

- `vr::update()` pumps the OpenXR event queue once, drives bring-up/retry/teardown per config, and returns whether a session is running. The headpose source is set to `Vr` while a session is running and `Sim` otherwise, so the flatscreen mouse-look sim yields to the HMD pose for the frame.
- `vr::apply_native_resolution()` populates the engine's deferred display-mode state so the first eye's `Draw` prologue resizes the scene targets to the per-eye resolution. This must sit before the eye loop.
- `vr::frame_wait()` runs `xrWaitFrame` → `xrLocateViews` and samples the controllers, returning a `WaitedFrame`. `xrWaitFrame` is what paces the app against the compositor, replacing vsync (which stays suppressed via `BLOCK_FLIP`, rendering §7).
- `vr::begin_render_frame` publishes the HMD headpose and the per-eye render parameters from the located views — but only when the runtime asked to render; otherwise the parameters are cleared and the camera hook falls back to flatscreen stereo for the non-submitted keep-alive draws. Then the original `UpdateRender` runs.
- `WaitedFrame::begin` runs `xrBeginFrame`, returning the `FrameContext` that holds the submit side (the frame stream and the swapchain) until the frame is submitted. It first waits for the previous frame's deferred tail to submit, so with `vr.overlap_render_update` on (the default) everything above runs alongside the previous frame's draw task and tail; with it off, the render update waits for the tail before `vr::update`, and the frame begins right after `frame_wait`. OpenXR allows a frame's `xrWaitFrame` once the previous frame has begun, from any thread, and requires only that the next `xrBeginFrame` follow the previous `xrEndFrame`; Monado's OpenXR state tracker blocks a second `xrWaitFrame` until the previous frame has begun and allows two waited frames in flight (read from its source, at a 2022 revision rather than the build the sessions run). [threading.md](threading.md#who-holds-what-across-a-frame) has what keeps the overlap safe.
- `vr::arm_direct` acquires the frame's swapchain image before the dispatches, so each eye's `RenderEngine::PostDraw` can blit it from `m_BackBufferLinear` straight into its slice. Under the single-pass collapse the one dispatch blits each eye from its half of the double-wide back buffer (`single_pass.collapse_direct_blit`), the blit's pixel shader mapping the slice's UV onto the half and clamping it to the half's outermost texel centres.
- The existing double-`Draw` stereo path renders both eyes. A running session forces the stereo double-`Draw` on regardless of the flatscreen stereo toggle (the swapchain has a slice per eye), and blocks the flip for both eyes. The `SetupRenderCamera` hook (hooks::camera, rendering §2) applies each eye's off-axis projection and world offset from the render parameters.
- `vr::present_and_submit()` blits each captured eye the post-draw did not already blit into its swapchain slice and ends the XR frame (a world projection layer when rendered, an empty frame otherwise), consuming the frame context and releasing the submit side. The swapchain acquire, release, and `xrEndFrame` run under the engine's immediate-context mutex, since the runtime's D3D11 client records on the game's immediate context.
- `vr::present_mirror()` draws one eye, or both side by side, into the game window, framed to the window aspect, and presents the game swapchain — the only present this frame.

The per-eye render parameters do not flow through the runtime's locks: the camera hook and the draw task read them from per-frame slots (`vr::render_params`, in `frame.rs`, each a `crate::render_frame::RenderFrameSlot`), so the draw task keeps reading the frame it records while the game thread prepares the next. Nothing on the game thread may block on the runtime's locks between `frame_wait` and the submit except the frame's own begin. With the frame tail deferred (`defer_tail` in `payload/src/hooks/game.rs`) the submit, the final drain, and the mirror run on a frame-tail worker that holds the submit side in the game thread's place; [threading.md](threading.md) has the thread model, the lock rules, and the guard that checks them.

## Session lifecycle, degradation, and retry

Bring-up is the full chain: load the OpenXR loader (dynamically, `openxr_loader.dll` beside the payload DLL or `vr.loader_path`; the static loader route does not cross-build under xwin), create the instance with `XR_KHR_D3D11_enable`, acquire the HMD system, create the session against the graphics engine's existing `ID3D11Device`, and create the LOCAL reference space. The stereo swapchain (a single 2-slice texture array) is created lazily on the first rendered frame.

Any failure at any stage logs on the `vr` target and leaves the mod in flatscreen stereo; `vr::update` retries the whole bring-up every `runtime.retry_interval_s` of the view tuning while `vr.enabled`. This is the graceful-degradation contract: with no runtime installed the mod plays normally in flatscreen and simply keeps retrying. Turning `vr.enabled` off, a session transition to `EXITING`/`LOSS_PENDING`, instance loss, or a lifecycle shutdown all tear the runtime down in order (swapchain → session → instance) so the OpenXR instance never outlives the DLL across an uninject → reinject cycle.

## The cockpit pose model

The runtime tracks a **recenter baseline** (`vr::Baseline`): a position and a yaw-only orientation, captured from the latest located head pose. `recenter()` asks for the current head pose to be snapshotted into the baseline at the top of the next frame, where the runtime lock may be taken (see [threading.md](threading.md#lock-rules)); F7 and the pause menu's RECENTER VIEW both route here (via `headpose::recenter`, which re-bases both the VR baseline and the mouse sim so one action recenters whichever source is live). The baseline is yaw-only on purpose — pitch and roll are the player's real head tilt and must not be zeroed, only the heading is re-based, matching the vehicle-recenter design in `docs/mod/body/head-and-body.md`.

Each frame, `frame_wait` locates the two eye views in LOCAL space and re-bases each into the baseline frame (`baseline⁻¹ · pose`, yaw-only inverse). `begin_render_frame` (`frame.rs`) then reduces the two eyes to a center pose (position averaged, the left eye's orientation), composes it into world space through `headpose::xr::compose` — the cockpit-frame pose is rotated by the body frame and placed on the animated head-bone anchor, scaled by `vr.world_scale` — and publishes it as the headpose. The per-eye world offset handed to the camera is the true per-eye delta from `locate_views`, rotated into world space by the body frame, replacing the flatscreen build's synthetic ±IPD/2 lateral offset.

Some of the frame's steps belong to modules above the VR runtime: the roomscale cockpit composition and its evidence, a recenter's observers (the roomscale and rig re-base), and the choice of a manual recenter's kind. The frame and the recenter reach them through one table of functions (`vr::FrameParticipants`) that the controllers register at install, so the frame keeps the order of its steps without naming their owners. The head pose has its own table (`headpose::HeadParticipants`) for the grapple's body-frame filter and telemetry, which the frame advances as well, and for the character state the body turn and the anchors read: the body follow, the on-foot and swim evaluator counts, swimming, a seat transition, a thrown body, and the UI mode.

The same goes for the runtime's teardown and its native-resolution driver. The teardown releases the flip block through `vr::TeardownParticipant`, which the graphics-engine hooks register; `vr::install` panics when it is missing, since a teardown that skipped it would leave the game's present blocked. The engine resizes the driver requests are observed through `vr::ResizeObserver`, which the texture census registers. The visual harness, also above the runtime, pushes whether it holds a configuration and the headset-like rig it substitutes for the located views into `vr::harness`, where the frame loop and the camera hooks read them.

The live tracking packet the frame publishes (`vr::live_tracking`, the head locate and the controller receipt of one frame) stays with the runtime; the head anchors read it to check the origin of the tracking they pair with the native pose.

The VR source publishes through `headpose::set_pose_no_interp`, writing the same pose to both sides of the engine's `T0 → T1` interpolation pair (**prev = cur**). The engine interpolates its camera by the sub-frame fraction `dtf` to smooth its fixed-rate sim tick; the VR source samples a fresh pose at the predicted display time every rendered frame, so there is no tick cadence to smooth and any residual interpolation would only lag the head behind the HMD (the "no smoothing on the HMD→camera path" pitfall in `docs/mod/body/head-and-body.md`).

## Per-eye camera and projection, and the two convention tweakables

`projection.rs` turns the four `XrFovf` half-angles into an off-axis (asymmetric-frustum) projection in the engine's row-major, row-vector layout (rendering §2.6), in two depth conventions, both host-unit-tested. The camera hook writes the projection into `m_Projection` on the render camera; the frame loop supplies the world-space eye offset alongside it.

The off-axis matrix is built element-for-element the way the engine's `CMatrix4f::PerspectiveOffCenter` builds `Camera::m_Projection` — verified (rendering §2.9) — and fed the engine's own default near and far planes ([`Camera::DEFAULT_NEAR_PLANE`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/camera::camera::Camera::DEFAULT_NEAR_PLANE) / [`Camera::DEFAULT_FAR_PLANE`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/camera::camera::Camera::DEFAULT_FAR_PLANE), the `Camera` constructor values). The far plane is the tell that matters: the game renders a finite-far reverse-Z frustum out to ~38 km, so a far plane of `4000` would clip the horizon at 4 km; the mod matches the engine's frustum.

The headset path writes a standard (non-reverse-Z) off-axis projection *before* `SetupRenderCamera`, so the engine applies its own reverse-Z remap and TAA jitter to it exactly once, and the blit linearizes the display-referred capture so the `_SRGB` swapchain's hardware encode reproduces the original bytes. Both used to be switchable as headset escape hatches and were never needed.

Before trusting a real HMD *rotation*, clear the coordinate-frame gate: every [render trace](rendering/render-trace.md) records the render camera's `m_TransformF` basis rows and the travel-direction dot products as `CoordFrame` events, so one trace captured while walking forward confirms JC3's world frame (almost certainly right-handed Y-up, but unverified). See `docs/mod/body/head-and-body.md`'s RE notes.

## Per-eye native resolution

While a session runs and `vr.native_resolution` is on (default), each eye renders at the runtime's recommended per-eye resolution × `vr.resolution_scale`, the same size the swapchain uses (one shared `scaled_eye_size`, so the blit is a straight scale-1 pass). The engine has no dynamic-resolution path (rendering §9): every render target is sized from `device->m_DeviceInfo.m_DisplayWidth`/`m_DisplayHeight` through `CreateRenderSetups`.

Rather than call `ApplyResize` directly, `resolution.rs` drives the engine's **own deferred display-mode state** — it writes the pending dimensions into `m_WindowWidth`/`m_WindowHeight` and sets `m_HasNewWindowSettings`, exactly as a windowed/settings resize does. The engine's `HandleModeChange`, serviced once per frame in the `Draw` prologue, then calls `ApplyResize` at the frame boundary the engine chose (previous dispatch drained, this frame not yet dispatched), so the idle-context assumption `ApplyResize` needs holds by construction (`docs/engine/rendering/render-setups-reinit.md` §2/§6). `ApplyResize` sets the camera aspect ratio and never touches the Win32 window (§4). It would also resize the DXGI swapchain buffers, but with `vr.own_back_buffer` on — the default — the mod substitutes that call so the swapchain stays at the window size while everything else follows the render size; see [`swapchain-ownership.md`](stereo/swapchain-ownership.md).

The pre-VR display size is captured before the first resize and restored both when the session ends and on uninject: a lifecycle cleanup requests the deferred restore while the hooks are still live, so the delayed hook uninstall (`lib.rs` `shutdown_startup`, which lets the engine run a few frames first; see [lifecycle.md](lifecycle.md#teardown-after-commit)) leaves the `Draw` prologue time to service it and the game is left exactly as found. Every serviced resize is verified (the device reports the requested size, and the Win32 window rect is unchanged); a timeout (`SERVICE_TIMEOUT_FRAMES`), a wrong size, or a changed window rect disables native resolution at runtime and restores the original size, and the mod continues at desktop resolution.

## The desktop mirror

While a session runs the compositor owns the HMD present and the engine's own present is blocked for both eyes, so the game window would freeze on a stale frame. `crates/jc3vr-view/src/vr/mirror/` presents the game's own swapchain itself, once per frame, unsynced (`SyncInterval = 0`): a vsynced mirror on a 60 Hz monitor would throttle the whole loop, including the 90 Hz HMD submit, down to the monitor's refresh. It draws the configured view (`vr.mirror_view`: `Left`, `Right`, or `StereoPair`) into the game back buffer, framed to the window aspect. With `vr.own_back_buffer` on the back buffer *is* the window client rect, so the present is 1:1 and the framing is simply a viewport. With it off the buffer is near-square at the per-eye resolution while the window keeps its 16:9 client rect, and the computed viewport pre-compensates DXGI's buffer→window stretch instead — the same computation, which degenerates to the identity when the two agree (unit-tested in `mirror/layout.rs`).

`mirror_layout` in `mirror/layout.rs` decides how the two aspects are reconciled per view. A single eye uses `Fill`: it scales the eye until it covers the window and crops the overflow, which is what other VR titles' desktop views do; the viewport it computes deliberately extends past the buffer edges, and since D3D11 rasterizes only within the render target, the crop falls out of the clip for free — no scissor, no extra copy, no UV-transform shader. The view tuning's `mirror.zoom` ([tuning.md](tuning.md)) magnifies a single eye about the centre, for tightening the desktop view onto the middle of the eye's much wider field of view. The stereo pair uses `Fit`: the two eyes are laid out as one image twice the eye's width and letterboxed whole, so neither is cropped (a crop would cut each eye's outer edge differently and spoil the fusion), then split down the middle in cross-eyed order, the right eye's image on the left and the left eye's on the right. Both eyes' captures are copied while the pair is up, as for any reader of an eye capture. F10 toggles the view between the stereo pair and the single eye it last left (the left eye before any toggle); it changes only `vr.mirror_view`. The egui panel composite always fits at 1:1 — a cropped UI panel would lose its edges. The egui debug overlay composites onto the mirror before the present so it stays visible on the desktop. That overlay is rendered into a **window-sized** offscreen texture (`crates/jc3vr-hud/src/hud/mirror_overlay.rs`) and composited across the whole back buffer, so it lands on the window at 1:1 whatever the render resolution is: the UI is measured in window pixels and is independent of the scene's. Sizing it to the back buffer instead couples it to the per-eye render resolution, which under `vr.own_back_buffer` off smears the UI horizontally as the near-square image is stretched onto a widescreen window, and under single-pass double-wide halves its relative width. Any draw/present fault disables `vr.mirror` at runtime and never wedges the loop; the window then holds its last frame. With the in-process capture off, the mirror window is also what a recording's video shows: the relay records the window's region on screen ([capture.md](capture.md)); by default a recording streams the eye views from inside the game instead.

## Recenter and the runtime controls

Recenter is bound to **F7** (`payload/src/hooks/wndproc.rs`), edge-detected like the other function keys (F1 session recording and F2 take marker ([capture.md](capture.md#session-recording)), F4 clean view, F5 uninject, F6 egui capture, F8 the floating panel, F9 a profiler capture, F10 mirror stereo pair, and F12 a screenshot). The same action is the pause menu's RECENTER VIEW. The debug UI's Rendering page has the runtime controls (`crates/jc3vr-ui/src/ui/vr.rs`): `vr.enabled`, `vr.native_resolution`, `vr.mirror` with its view, `vr.own_back_buffer`, `vr.direct_eye_blit`, and `vr.overlap_render_update`, and a status readout with the runtime name, the effective per-eye resolution, the live headpose source, and the hidden-area mask (below); the session state is the Status page's VR SESSION row.

## Config reference

All under `vr.*` (`crates/jc3vr-view/src/vr/config.rs`):

- `enabled` — master switch; off tears any live runtime down and stays in flatscreen stereo.
- `resolution_scale` — per-eye render resolution scale on the runtime's recommendation (`1.0` = recommended).
- `world_scale` — metres of head/IPD motion per engine unit (`1.0` = 1:1).
- `loader_path` — override for the OpenXR loader DLL.
- `native_resolution` — render each eye at the HMD-recommended resolution (default on; auto-disables on a resize fault).
- `own_back_buffer` — substitute a mod-owned render target for the engine's swapchain-derived back buffer, so the DXGI swapchain stays at the window size instead of following the per-eye render resolution (default on; see [`swapchain-ownership.md`](stereo/swapchain-ownership.md)). The mirror's present becomes 1:1, and single-pass double-wide stops forcing a 2x-width swapchain.
- `overlap_render_update` — run the next frame's `xrWaitFrame`, view location, and render update alongside the previous frame's draw task and deferred tail, waiting for the tail only at `xrBeginFrame` (default on). Off restores the serial ordering, which waits for the tail before the render update. The cost and the gain are in [frame-budget.md](performance/frame-budget.md#overlapping-the-render-update).
- `mirror` / `mirror_view` — desktop mirror on/off and what it shows: `Left`, `Right`, or `StereoPair` (default on, `Left`). The framing against the window aspect and the centre magnification are constants in `crates/jc3vr-view/src/vr/mirror/layout.rs`.

## Playtest checklist

Everything below needs a headset in the loop; the desktop build could not settle these, and each maps to a runtime knob or a diagnostic so a wrong guess is recoverable without a rebuild. Consolidated from the module doc comments and the branch's commit notes.

**Bring-up and lifecycle.**

- With a runtime present and a headset connected, confirm the `vr` log shows the loader loading, the runtime name and version, the D3D11 graphics requirements, the negotiated swapchain format, the swapchain creation line, and the `session state -> READY` transition, then a steady `VR frame-loop health` line every ~5 s.
- Confirm graceful degradation with no runtime available: the mod plays in flatscreen, logs the bring-up failure, and retries at the tuning's interval (no panics, no crash).
- Toggle `vr.enabled` off and on in the debug UI mid-session: the runtime tears down cleanly (flatscreen resumes, resolution restores) and brings back up on re-enable.
- Uninject (F5) and reinject: the game stays running and stable, the display resolution is restored to the pre-VR size, and a fresh inject brings the runtime back up cleanly.

**Coordinate frame and pose.**

- Capture a render trace while walking forward and read its `CoordFrame` summary (`tools/analysis/analyze_trace_frames.py`, or the `coord_frame` log line at the trace's end) to confirm the world frame before trusting HMD rotation (blocker 3, `docs/mod/body/head-and-body.md`).
- Confirm head rotation and roomscale translation track 1:1 with no perceptible lag or smoothing.
- Confirm Recenter (F7 or the pause menu's RECENTER VIEW) re-bases heading only, leaving pitch and roll (real head tilt) intact.
- Confirm the stereo separation reads as depth (not a flat or hyperstereo image) and that near/far objects fuse — the true per-eye `locate_views` delta, not the synthetic IPD.

**Projection and color.**

- Confirm the world fills the frustum with no §2.7 depth wedge (a thin valid band with black elsewhere).
- Confirm colors and gamma look correct in the headset.
- Under single-pass stereo with the collapse, confirm water surfaces and their reflections line up in both eyes: the WaveWorks ocean sits at its depth with parallax rather than flat at the centre view (`single_pass.nvwater_per_eye`), and at a lower water-quality setting the legacy water's reflections stay on the water instead of sliding across it (`single_pass.water_uv_per_eye`). Each flag toggles in the debug UI for an A/B ([single-pass-stereo.md](stereo/single-pass-stereo.md)).

**Resolution and mirror.**

- Confirm each eye renders sharp at the recommended resolution and that the `native resolution: engine resize serviced` line reports the expected per-eye size and a sane aspect ratio, with no runtime auto-disable.
- Confirm the desktop mirror fills the window with the configured eye at the correct aspect (no stretch, no bars under the default `Fill`), that `Fit` and the zoom slider behave, that the egui overlay is visible on it, and that the mirror present never throttles the HMD frame rate.

**Body IK.**

- Confirm the spine and neck bend toward where the player looks without fighting the head-bone override or the game's aim IK (`docs/engine/character/humanik.md` open risks); the reach weights are the `body_ik` section of the character hooks' tuning (`crates/jc3vr-body/tuning/character.toml`).

## The hidden-area mask

`XR_KHR_visibility_mask` is enabled whenever the runtime offers it (`crates/jc3vr-view/src/vr/state.rs`). `crates/jc3vr-view/src/vr/visibility_mask.rs` fetches each eye's hidden triangle mesh on the first located frame of a session and again after the runtime's visibility-changed event, logs each eye's vertex and triangle counts and the hidden share of its field of view once per fetch, and the VR status readout lists the same and draws each eye's field-of-view rectangle with the hidden triangles outlined in it. Nothing is masked yet. The spec places the vertices in the view's space on the plane `z = -1`, so they are tangents of the view angles, the space the tangents of the located `XrFovf` angles bound; the hidden share is the triangles' area over that rectangle's. A persisted instance keeps the extensions it was created with, so a payload re-injected into a session launched before this sees the extension as missing until the game restarts.

Monado's null compositor, which the capture harness runs, returns 12 vertices and 4 triangles per eye, 3.1% of each eye's field of view (session 339).
