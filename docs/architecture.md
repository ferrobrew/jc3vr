# Architecture

jc3vr is a VR mod for Just Cause 3. A DLL, the payload, is injected into the running game. Inside the process it detours the engine's frame, camera, rendering, input, character, and UI functions, drives an OpenXR session against the game's own Direct3D 11 device, renders the scene once per eye or once for both eyes at the headset's per-eye resolution, and submits the result to the OpenXR compositor. The game never sees the headset: it renders as it normally would, while the mod substitutes the camera, the targets, and the present.

Each section below links to the document that owns its detail. [CONTRIBUTING.md](../CONTRIBUTING.md) holds the conventions and the development workflow, and [README.md](README.md) indexes every document.

## Payload lifecycle

The injector calls the payload's `run` export, or `run_source_tuning` when a development launcher asks for the tuning from the source tree. It resolves the session output folder ([mod/sessions.md](mod/sessions.md)), installs logging, loads the tuning ([mod/tuning.md](mod/tuning.md)), stopping and unloading itself when a tuning file is missing or invalid, installs the crash handler, loads the settings ([mod/settings.md](mod/settings.md)), and installs the hooks (`composition::install`, which registers each module's shutdown participants and hook steps and composes the hook libraries for the core crate's `hooks::install`). The rest of the initialization runs on the game thread at the first [`Game::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::Game##func-Update): the debug UI's egui state, the HUD redirect, and the OpenXR runtime. An eject (F5, or the injector's `--eject`) prepares every subsystem for shutdown on the game thread, tears down in a fixed order, removes the hooks, and unmaps the module ([mod/lifecycle.md](mod/lifecycle.md)).

## Path of a frame

The engine runs one frame on the game thread as an update, a render update, and one or more draws. The draws are recorded by the engine's draw task on a CPU fragment worker. The mod's hooks sit at each stage. [mod/threading.md](mod/threading.md) owns the thread model, the two locks of the VR runtime, and the rules for which thread may take them; [mod/vr-runtime.md](mod/vr-runtime.md) owns the OpenXR loop step by step. The steps below follow one frame with a VR session running.

### Update and simulation

1. The [`Game::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::Game##func-Update) detour (`hooks::game`) runs `crate::update` before the original: the directing tools, the tracking recorder's frame tick, the capture harness's requests, the hand bodies' frame tick, and the debug UI.
2. The original update runs the simulation tick. The engine's input job polls the devices; the mod's [`InputDeviceManager::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/input::input_device_manager::InputDeviceManager##func-Update) detour consumes the look and move input and lands the controller bindings' writes ([mod/input/input.md](mod/input/input.md)). The input tick's game stage, in the world's pre-simulation queue, makes the bindings' decisions and every act that changes the world ([mod/input/controllers.md](mod/input/controllers.md#bindings-and-injection)).
3. The character hooks (`hooks::character`) run inside the pose-finalization pass: the procedural torso and the wrist targets before the HumanIK solve, then the head override and the finger curls after it ([mod/body/procedural-body.md](mod/body/procedural-body.md), [mod/body/head-and-body.md](mod/body/head-and-body.md)). The rig moves Rico through the game's own character movement ([mod/body/rig.md](mod/body/rig.md)).

### Render update and the OpenXR frame

4. The [`Game::UpdateRender`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::Game##func-UpdateRender) detour opens the frame's generation of the per-frame slots (`crate::render_frame`), which keep the values of the frame being prepared apart from those of the frame the draw task is still recording.
5. `vr::update` pumps OpenXR events and brings the session up, retries it, or tears it down. Without a runtime, the mod plays in flatscreen stereo and keeps retrying. `vr::apply_native_resolution` sizes the scene targets to the headset's per-eye resolution; while a session runs, the engine renders into a back buffer the mod owns rather than the DXGI swapchain ([mod/stereo/swapchain-ownership.md](mod/stereo/swapchain-ownership.md)).
6. `vr::frame_wait` calls `xrWaitFrame`, which paces the game against the compositor in place of vsync, locates the eye views, and samples the controllers. `vr::input` publishes the controller snapshot (`ControllerFrame`) that everything in `controllers` reads.
7. `vr::begin_render_frame` composes the head pose into the world (`headpose::xr`) and publishes it with the per-eye off-axis projections. The original render update runs. At render time, the controllers' late update and the presentation layer re-pose the held weapon, the hands, and the upper body on the skinning palette from the latest tracking, so nothing attached to the player is drawn a simulation tick behind ([mod/rendering/presentation-layer.md](mod/rendering/presentation-layer.md), [mod/rendering/render-time-anchoring.md](mod/rendering/render-time-anchoring.md)).
8. `WaitedFrame::begin` calls `xrBeginFrame` once the previous frame's tail has submitted. With the direct eye blit, `vr::arm_direct` acquires the swapchain image so each eye can be blitted into its slice from the draw task.

### Draws

9. `hooks::game` builds a dispatch plan (`stereo::dispatch::DispatchPlan`) and calls [`Game::Draw`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::Game##func-Draw) once per dispatch. Between dispatches it restores the engine state that advances once per draw (frame counters, constant-buffer rings, temporal history indices, draw-list parity), so each dispatch sees the same frame. [engine/rendering/rendering.md](engine/rendering/rendering.md) sections 5 and 11 to 13 describe that state.
10. Each draw runs on the draw task ([`GraphicsEngine::HandleDrawThreadTask`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::graphics_engine::GraphicsEngine##func-HandleDrawThreadTask)). The [`Camera::SetupRenderCamera`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/camera::camera::Camera##func-SetupRenderCamera) detour (`hooks::camera`) applies the eye's projection and offset. The render-pass, scene, screen-space, and post-effect hooks (`hooks::graphics_engine`) correct what does not survive per-eye rendering: culling widened to both eyes ([mod/stereo/culling.md](mod/stereo/culling.md)), lighting and shadow state ([mod/stereo/lighting-shadow-vr-interactions.md](mod/stereo/lighting-shadow-vr-interactions.md)), and FSR or the mod's TAA in place of the engine's SMAA ([mod/rendering/fsr.md](mod/rendering/fsr.md), [mod/rendering/taa.md](mod/rendering/taa.md)). Game shaders are patched in memory when the engine creates them ([mod/rendering/shader-patching.md](mod/rendering/shader-patching.md)).
11. The [`RenderEngine::PostDraw`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine::RenderEngine##func-PostDraw) detour draws the world-space overlay, the scope lens, the floating HUD panel, the egui debug panel, the controls summary, and the desktop mirror overlay into each eye's back buffer, then blits the eye into its swapchain slice or copies it into its capture texture. Each of those passes is registered by the module that owns it, in the order `hooks::graphics_engine::post_draw` fixes, so the render hooks name none of the layers above them.

### Submit and mirror

12. `vr::present_and_submit` blits any eye the draw did not, and ends the frame with one projection layer. `vr::present_mirror` draws one or both eyes into the game window and presents the game's swapchain, the only present of the frame. With a VR frame to submit and no render trace running, these run on the frame-tail worker (`vr::tail`), so the game thread starts the next frame's update while the last draw and the GPU finish.

### Stereo rendering paths

Multipass stereo dispatches `Game::Draw` once per eye. Single-pass stereo, the default while a session runs, dispatches once into a double-wide target: the game's vertex shaders are rewritten so one instanced draw emits both eyes through viewport routing, and the content that reads a single camera is corrected per eye ([mod/stereo/single-pass-stereo.md](mod/stereo/single-pass-stereo.md), [mod/stereo/single-pass-render-blocks.md](mod/stereo/single-pass-render-blocks.md)). Where the frame time goes in each path is in [mod/performance/performance.md](mod/performance/performance.md) and [mod/performance/frame-budget.md](mod/performance/frame-budget.md).

### The floating panel

The game's Scaleform UI is redirected into a texture the mod owns by rebinding [`UIManager::m_RenderBuffer`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_RenderBuffer). That texture is drawn as a quad in each eye's scene at `RenderEngine::PostDraw`, so it reaches the compositor inside the projection layer rather than as a separate composition layer. World-anchored markers are reprojected into the world rather than drawn on the panel ([mod/hud.md](mod/hud.md), [engine/rendering/ui-rendering.md](engine/rendering/ui-rendering.md)). The VR settings are pages in the game's own pause menu ([mod/pause-menu.md](mod/pause-menu.md)); everything else is in the debug UI ([mod/debug-ui.md](mod/debug-ui.md)).

## Crate layering

The payload is built from layer crates, each of which may depend only on the crates below it, except that crates side by side may not depend on each other. From the bottom:

1. `jc3vr-core`: the lifecycle, the configuration engine, the tuning loader, the hook plumbing, the frame slots, timing, and the profiler core.
2. `jc3vr-input`: the pure controller frame types, motion, the scheme, the haptic mix, and the input-capture policy. It depends on no layer crate at all, so it builds and tests natively with `cargo test -p jc3vr-input --target x86_64-unknown-linux-gnu`.
3. `jc3vr-view`: the OpenXR runtime, the head pose, the camera and window-focus detours, the frame state the render hooks read per draw (the stereo state, the dispatch, the layout, the per-eye render parameters, and the stereo and FSR settings), the tracking recorder, and the dependency-free registries and cells the render hooks share with the layers above (the post-draw's registrations, the eye captures, the palette edit, the player's draw inputs, the overlay's inputs, and the scope's lens frame).
4. `jc3vr-render` beside `jc3vr-body`, `jc3vr-weapons`, `jc3vr-physical`, `jc3vr-vehicles`, `jc3vr-grapple`, and `jc3vr-gameplay`, on the view crate: the render crate and those six may not depend on each other. The render crate holds stereo, FSR, the engine-pipeline hooks, the overlay and scope passes, and the render diagnostics. The body crate holds the body-bound controller subsystems, the vocabulary, facts, and physics substrate they share with the subsystems above, and the character, animation, and input detours. The weapons crate and the physical crate sit side by side on the body crate, and neither may depend on the other: the weapons crate holds the weapon handling and the loadout table, the physical crate the physical hands and the glass, and what one knows about the other (a held weapon, a reached weapon, the held guns' bodies) crosses through the body crate's held-item facts and registrations. The vehicles crate and the grapple crate sit side by side on the weapons and physical crates, and neither may depend on the other: what the grapple tells the vehicles (the airframe a door-side arrival reached) crosses as a body fact. The vehicles crate holds the vehicle handling: the mounted guns reach the weapon handling's delivery and recoil, and the rail and the mounted handles the climb and the hand bodies, and it fills the registrations below it (the take-off's tick, the rail's step and auto-attach blocker, the mounted-shot observer, the vehicle targets, and the mounted-gun fact) from its own register files, which the gameplay crate's install calls. The grapple crate holds the grapple and the snatch, which pulls weapons from their sources and the steal and reaches the physical hands' remote holds, doors, and ragdolls; the bindings run its ticks in their game stage. The gameplay crate sits on the body, weapons, physical, vehicles, and grapple crates and holds the bindings, the summary model, and the look, equipment, and sim detours; it fills the body's registrations (the hands' stage table and observers, the aim's weapon hooks, the climb's readers, and the character hooks' blockers and consumers) at install, connects the physical hands with the weapon handling above both, and composes the body's, the weapons crate's, the physical crate's, the vehicles crate's, and the grapple crate's hook libraries with its own in their established order. Body, weapons, physical, vehicles, grapple, and gameplay reach the render passes only through the view crate's registries and cells, so an edit to the render crate rebuilds none of them, an edit to the weapons crate rebuilds neither the body nor the physical crate, an edit to the vehicles or the grapple crate rebuilds neither the other nor the crates below it, and an edit to the gameplay crate rebuilds none of the five below it.
5. `jc3vr-capture`, on the render crate and beside body, weapons, physical, vehicles, grapple, and gameplay: the screenshot harness, the visual stage's controls, and the benchmark samplers. It defines no detours. The render hooks reach it only through the probe tables the render crate keeps (`stereo::single_pass::probes` and `hooks::graphics_engine::probes`), which the capture crate fills at install and which the hooks call only once a capture or benchmark request has raised the flags in `capture_arming`. Nothing below tooling may depend on it, so an edit to it rebuilds only the tooling, UI, and payload crates.
6. `jc3vr-hud` and `jc3vr-tooling`, side by side: neither may depend on the other. Tooling may depend on the capture crate; the HUD may not.
7. `jc3vr-ui`: the debug UI, the status rows, and the pause menu.
8. `jc3vr_payload`, the only `cdylib`, which may depend on every layer crate: the entry points, the composition, the frame driver, the window procedure, and the settings aggregate.

A lower crate reaches a higher one through a registration the higher one makes rather than by naming it: the passes the render crate's post-draw runs, for example, are registered in the view crate's `hooks::graphics_engine::post_draw` by the render, gameplay, HUD, and tooling crates. `composition::install` in the payload runs every registration, in an order that is load-bearing, before it composes the hook libraries. A subsystem reads its settings through the slot it declares beside their type, so no layer names the aggregate, which only the payload sees.

Cargo forbids cycles between the crates; `crates/layering-guard` checks what it cannot. It is a host-native test crate, so it runs under `cargo test -p layering-guard --target x86_64-unknown-linux-gnu` as well as under `scripts/xwin_test.sh`. It reads the payload's manifest and every `crates/jc3vr-*/Cargo.toml`, and checks that every layer has its crate, named for its layer, and that every dependency of each, in the normal, dev, build, and per-target sections, points down the order. A dependency is read by its package name and by the directory its path points at, so an alias cannot hide one. That catches an acyclic but wrong edge: HUD on tooling, gameplay, vehicles, grapple, physical, weapons, or body on render, body on weapons, physical, vehicles, grapple, or gameplay, weapons on physical or physical on weapons, either on vehicles, grapple, or gameplay, vehicles on grapple or grapple on vehicles, either on gameplay, view on render, render or the HUD on capture, or any layer crate on the payload. It also checks that every layer crate is a workspace member, that only the payload is a `cdylib` among the workspace's members, and that the view and render crates' `hooks` modules never name the body, weapons, physical, vehicles, grapple, gameplay, or HUD crates. Each failure says how to fix it. When an edge is refused, move the code down to the crate that owns it, or invert the edge with a registration; do not move the layer.

## Where new findings go

A finding about the game goes into the pyxis defs as a typed binding with its doc comment, and its explanation goes into `docs/engine/<subject>/`. A design or implementation of the mod goes into `docs/mod/<subject>/`, under the subject directory that matches the payload module. An investigation that answers one issue's question goes into `docs/issues/`. A doc that would mix engine and mod material is split along that line. Every new doc gets an entry in [README.md](README.md). Docs and comments name pyxis symbols and carry no addresses, offsets, or other game-owned constants (CONTRIBUTING.md has the full rule).
