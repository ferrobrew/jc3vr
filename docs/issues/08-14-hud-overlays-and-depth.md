# HUD overlays and depth (issues #8 and #14)

Resolved: both issues are closed. The full-screen overlays are suppressed and the HUD's depth comes from the atlas, as [hud.md, "HUD depth"](../mod/hud.md#hud-depth) describes. This page keeps the post-mortem of the per-element depth split, whose constraints still bind any design that captures the HUD movie or edits its render tree. How the engine updates, captures, and draws the UI is in [ui-rendering.md](../engine/rendering/ui-rendering.md).

## The split post-mortem

Three mechanisms were built to render groups of HUD elements into separate textures, so each group could be drawn at its own depth. All three are deleted. Their failures established the constraints below.

### Constraints established

1. One safe capture per frame. `Render::Context::Capture` mutates the active snapshot, the same data every game-thread UI write touches, with no writer lock; the capture lock only orders `Capture` against `NextCapture`. The engine is safe only because it captures inside `CUIManager::PreRender` on the game thread, which makes every other UI write. A design that needs more than one distinct visibility configuration per frame cannot get it from captures.
2. The display side owns child indices. `GFx::DisplayList` addresses each child's render node by a cached numeric `TreeIndex`, so a structural edit the display list does not know about shifts its siblings' indices and corrupts later operations. Swapping a moved node for an empty "tombstone" container at the same index holds: only structural operations are index-based, and matrix, visibility, and alpha writes are node-local and follow the node.
3. The renderer's cache reconciliation requires unique parentage. `TreeCacheContainer::HandleChanges` walks the child array and the cache list in lockstep and converges only when every node is in exactly one child array. A node with two parents (a display-side re-insert of a held node, or a stale registry after the game re-attaches the HUD around the frontend-to-gameplay transition) hangs the render thread inside the deferred render lock, which deadlocks the game.
4. The render-buffer manager is not built for churn. `RBGenericImpl::RenderBufferManager` allocates and links a cache-list record for every `CreateRenderTarget` and charges its budget, so creating and releasing a full-resolution target per draw degrades every later call until the UI worker is slow enough that the engine visibly skips UI updates. Wrap targets once and reuse them.
5. Content projected from the world needs full-rate sampling. A layer refreshed below the frame rate shows it at once under camera motion: elements in different layers are projected with different frames' matrices, and they strobe at refresh boundaries. Freezing a layer's quad pose compensates camera rotation only.

### The mechanisms

Multi-pass visibility rendering drew the movie three times per render call, toggling clip visibility and calling `Movie::Capture` between passes, with capture-thread ownership borrowed as `RenderOffScreenTextures` does. It failed on constraint 1: the worker-side captures raced the game thread's UI writes, which showed as flicker in every layer, updates arriving seconds late (the ownership claim also diverted every `CUIBase::Invoke` into the queued path), and a crash in `PrimitiveBundle::InsertEntry`.

The time-multiplexed layer refresh applied one visibility mask per frame at the capture seam (a detour on `MovieImpl::Capture`, under the deferred render lock), so the engine's own capture carried it, and redirected one layer's texture per frame in turn. It was stable and cost no more than the stock HUD, but failed visually on constraint 5. It also showed that releasing the clip-handle registry while the mask held clips hidden lets the fresh handles read the mask back as the game's intent, which blanks the HUD cumulatively; the game's intent has to be restored before any release.

The render-root partition came closest. It moved the layer containers' render nodes behind tombstones (constraint 2) into two extra `TreeRoot`s created in the movie's own render context, and a `CUIManager::Render` detour that reimplemented the original drew each root into its own texture from the frame's single capture: full rate, no extra captures, and no change on the display side. It reconciled the pool's spawns and despawns and the display side's re-inserts at the seam every frame, with a check for double parenting (constraint 3), cached its wrapping render targets (constraint 4), and built only from a registry resolved during gameplay whose containers reached the live render root. With all of that, gameplay was healthy. But the first pause permanently stopped the UI update pump: `MovieImpl::Capture` was never called again, the pause menu never drew, and unpausing left the UI dead, while every lock, gate, and render-tree structure checked in the wedged process was healthy. The cause was not found, and the partition was deleted with it.
