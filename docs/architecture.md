# Architecture

jc3vr is a VR mod for Just Cause 3. A DLL, the payload, is injected into the running game. It detours the engine's frame, camera, rendering, input, character, and UI functions, drives an OpenXR session against the game's own Direct3D 11 device, renders the scene for each eye at the headset's resolution, and submits the result to the compositor. The game never sees the headset: it renders as it normally would while the mod substitutes the camera, the targets, and the present.

[CONTRIBUTING.md](../CONTRIBUTING.md) lists the workspace's crates and tools and holds the conventions and the workflow; [README.md](README.md) indexes every document. This page shows how a frame flows through the mod and how the layer crates may depend on each other.

## Payload lifecycle

The injector calls the payload's `run` export (or `run_source_tuning`, [mod/tuning.md](mod/tuning.md)). Startup loads the tuning and the settings and installs the hooks through `composition::install`; a failure there unloads the payload. The rest of the initialization, the OpenXR runtime among it, runs on the game thread at the first [`Game::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::Game##func-Update). An eject (F5, or the injector's `--eject`) prepares every subsystem on the game thread, tears down in a fixed order, removes the hooks, and unmaps the module. [mod/lifecycle.md](mod/lifecycle.md) owns the order.

## Path of a frame

The engine runs a frame on the game thread as an update, a render update, and one or more draws, which its draw task records on a CPU fragment worker. [mod/threading.md](mod/threading.md) owns the thread model and lock rules, and [mod/vr-runtime.md](mod/vr-runtime.md) the OpenXR loop.

1. The `Game::Update` detour (the payload's `hooks::game`) runs the payload's `update` first: the tuning reload, the tools, the hand bodies' tick, and the debug UI. The simulation then runs. The [`InputDeviceManager::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/input::input_device_manager::InputDeviceManager##func-Update) detour consumes the look and move input, and the input tick's game stage at the top of the pre-simulation queue makes the bindings' decisions and every act that changes the world ([mod/input/bindings.md](mod/input/bindings.md#injection-timing)).
2. The [`Game::UpdateRender`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::Game##func-UpdateRender) detour opens the frame's generation of the per-frame slots (`jc3vr_core::render_frame`), which keep the frame being prepared apart from the one the draw task is still recording. It pumps OpenXR (`vr::update`; without a runtime the mod plays in flatscreen stereo), waits on the compositor in place of vsync (`vr::frame_wait`), samples the controllers, and publishes the head pose with the per-eye projections. While a session runs the engine renders into a back buffer the mod owns ([mod/stereo/swapchain-ownership.md](mod/stereo/swapchain-ownership.md)).
3. `hooks::game` builds a `stereo::dispatch::DispatchPlan` and calls [`Game::Draw`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::Game##func-Draw) once per dispatch, restoring between dispatches the engine state that advances once per draw so each sees the same frame ([engine/rendering/rendering.md](engine/rendering/rendering.md)). Multipass stereo dispatches once per eye; single-pass, the default in a session, dispatches once into a double-wide target with rewritten vertex shaders ([mod/stereo/single-pass-stereo.md](mod/stereo/single-pass-stereo.md)).
4. On the draw task, the [`Camera::SetupRenderCamera`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/camera::camera::Camera##func-SetupRenderCamera) detour applies the eye's projection, and the render crate's `hooks::graphics_engine` corrects what per-eye rendering breaks: culling ([mod/stereo/culling.md](mod/stereo/culling.md)), lighting and shadows ([mod/stereo/lighting-shadow-vr-interactions.md](mod/stereo/lighting-shadow-vr-interactions.md)), anti-aliasing ([mod/rendering/fsr.md](mod/rendering/fsr.md)), and the game's shaders ([mod/rendering/shader-patching.md](mod/rendering/shader-patching.md)).
5. The [`RenderEngine::PostDraw`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine::RenderEngine##func-PostDraw) detour draws the world overlay, the scope lens, the floating panel, the debug UI, and the controls summary into each eye, then blits the eye into its swapchain slice. The passes of the layers above are registered in the view crate's `hooks::graphics_engine::post_draw` as ordered tables, so the render hooks name none of them.
6. `vr::present_and_submit` ends the OpenXR frame and `vr::present_mirror` presents the desktop window, normally on the frame-tail worker (`vr::tail`) so the game thread starts the next update while the GPU finishes.

The game's Scaleform UI is redirected into a texture the mod owns and drawn as a quad in each eye's scene, so it reaches the compositor inside the projection layer ([mod/hud.md](mod/hud.md)). The VR settings are pages in the game's pause menu ([mod/pause-menu.md](mod/pause-menu.md)); everything else is in the debug UI ([mod/debug-ui.md](mod/debug-ui.md)).

## Modules by crate

Detours live in each crate's `hooks/`, which mirrors the pyxis hierarchy. Where a domain spans layers, each crate holds its layer's part under the same module path: `controllers::overlay` is the overlay's data model in the view crate, its draw pass in the render crate, and its placement in the body crate. Each crate's `lib.rs` documentation lists the modules it owns, and a crate that owns tuning reads it through its `tuning` module ([mod/tuning.md](mod/tuning.md)).

## Crate layering

Each layer crate may depend only on the crates below it, and crates side by side may not depend on each other. From the bottom:

1. `jc3vr-core`: the lifecycle, the configuration engine, the tuning loader, the hook plumbing, the frame slots, timing, and the profiler core.
2. `jc3vr-input`: the pure controller frame, motion, scheme, haptic mix, and input-capture policy. It depends on no layer crate, so it builds and tests natively.
3. `jc3vr-view`: the OpenXR runtime, the head pose, the camera and window-focus detours, the frame state the render hooks read, the tracking recorder, and the registries the render hooks share with the layers above.
4. `jc3vr-render` beside the gameplay stack, both on the view crate, with no edge between them. The stack is `jc3vr-body` (the body-bound controllers, the shared vocabulary, held-item facts, and physics substrate, and the character, animation, and input detours); `jc3vr-weapons` and `jc3vr-physical` side by side on it; `jc3vr-vehicles` and `jc3vr-grapple` side by side on those two; and `jc3vr-gameplay` on all of them, which holds the bindings and fills and orders the tables of the body's contributions record (`jc3vr_body::contributions::BodyContributions`), since it is the lowest crate that sees every subsystem in them. Siblings learn about each other through the body crate's facts and registrations.
5. `jc3vr-capture`, on the render crate: the screenshot harness, the visual stage, and the benchmark samplers. It defines no detours; the render hooks reach it only through the probe table (`probes`) it fills at install, armed only by a capture or benchmark request.
6. `jc3vr-hud` and `jc3vr-tooling`, side by side. Tooling may depend on the capture crate; the HUD may not.
7. `jc3vr-ui`: the debug UI, the status rows, and the pause menu.
8. `jc3vr_payload`, the only `cdylib`, which may depend on every layer crate.

Because the gameplay stack and the capture crate reach the render passes only through the view crate's registries, an edit to the render crate rebuilds none of them, and an edit to a crate of the stack rebuilds neither its siblings nor the crates below.

A lower crate reaches a higher one through a registration the higher one makes. A crate declares what it reads from above in one `Contributions` struct with a field per contribution and takes it through one `register` call, so a registrant that leaves one out fails to compile. Names a lower crate keeps for bookkeeping are opaque values the registrant supplies (a shutdown participant's `ParticipantId`), and ordered tables take their order from the registrant. A subsystem reads its settings through a slot declared beside their type, so only the payload sees the settings aggregate ([mod/settings.md](mod/settings.md)).

`composition::install` in the payload calls every crate's `register` in one place. The order is free but for three constraints, stated with their reasons in [mod/lifecycle.md](mod/lifecycle.md#hook-installation-and-removal) and in `payload/src/composition.rs`: every registration precedes `jc3vr_core::hooks::install`; stereo's hook-removal step registers before the texture census's; and the magazine executor's admission closes before the native-callback check. The vehicles crate's `register` returns the equipment detours, so they enable only once vehicle handling has registered. The hook libraries enable in the order `composition::libraries` lists, under one thread suspension; no two detour the same function, and a unit test pins the order so a change is deliberate.

Every registration reports what it finds missing to one `RegistrationCheck` (`jc3vr_core::registration`), which the composition finishes before any hook is installed. A missing contribution is a broken build, not a game state, so the payload logs every missing one, stops startup, and unloads itself.

Cargo forbids cycles; `crates/layering-guard` checks the rest. It reads every layer crate's manifest and the payload's, and fails on a dependency in any section that points up the order or across between siblings (read by package name and path, so an alias cannot hide one), on a layer crate that depends on the payload or is not a workspace member, on a second `cdylib`, and on the view or render crates' `hooks` naming the gameplay stack or the HUD. When an edge is refused, move the code down or invert the edge with a registration; do not move the layer.
