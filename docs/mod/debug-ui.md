# Debug UI

## Navigation

The debug window opens on Status. The nine pages are Status, Body/tracking, Hands/interaction, Weapons, Movement/vehicles, Rendering, Input/bindings, Tools, and Experimental. A wide window keeps the page list and feature list beside the selected feature. A narrow window uses page and feature selectors. Feature labels remain outside the content scroll area.

The Status page has one feature, Status (`payload/src/ui/overview.rs`). It lists the rows that need attention first (failures, active captures, and waiting or unavailable snapshots), then everything else under a collapsible header, each group ranked failures first. The rows are the session rows (the OpenXR input, the session focus and controllers, and the debug panel ownership), the capture and tool rows (video, tracking, the profiler trace, the performance monitor, and the world overlay), and every status row ([status.md](status.md)). Its buttons open the performance, tracking capture, and video features, and log the status summary.

Each feature renders its controls followed by a collapsible Live status readout, open by default. A feature without controls shows only its readout, and a feature without a readout shows no Live status header. Readouts run after the controls return, so they hold no configuration edit guard. Content scroll state uses the stable feature key rather than a displayed label or list position. Diagnostics groups are closed by default where a feature has one. Visualization switches and the shared overlay settings live only in the global drawer described below. Existing configuration fields, actions, and defaults remain the domain modules' responsibility.

`payload/src/ui/dispatch.rs` routes every catalog feature (`payload/src/ui/catalog.rs`) to its renderer. The route match is exhaustive, so a new feature does not compile until it has a route. The controller, game, and render modules hand out each feature's controls and readout as plain functions, which lets a renderer-free test check that every feature renders something without drawing it.

Tools holds Tracking capture, Controller capture, Render capture, Replay, Director (the cinematic mode, time, safety, heat, teleport, spawn, including the exploding barrel preset, and the keyboard shortcuts), Environment (time of day and weather), Video (the video recorder and take markers), and Presets (the `Controllers` and `Gamepad baseline` switch presets). Recordings are always lossless chunked version 4. Input/bindings holds Devices and thresholds (hand tracking, binding injection, and the trigger, squeeze, grip force, and trackpad press and release thresholds, with the scheme, OpenXR device, recovery, mode, binding, and menu map readouts), Wrist summary (the summary switch, show on glance, and hiding the game's button hints), and Self-check. The pause menu retains calibration and the existing comfort, display, and core control settings, including the motion controllers switch, the dominant hand, and the move deadzone. A setting the pause menu exposes has no copy in the debug UI.

Rendering holds Runtime, Stereo, Foveation, HUD, and Previews and performance. Tools > Render capture dumps the render trace, with its frame count and per-eye screenshots, and holds the live log filter. Experimental holds the single-pass stereo, far field, and post-FX skip controls, and a button that opens the render RE window.

## Render RE window

The render RE window is a separate egui window (`payload/src/ui/diagnostics.rs`) for single-pass stereo and render reverse-engineering. It holds the render-block type registry toggles, the per-eye skip toggles and the skip-pass range, the eye-1 gates, the exposure A/B, the render trace's options (the MainColor means at the stage brackets and per pass, the render-target hashes, the global constants, the per-eye draw diff, and the brightness-step auto-capture), the terrain and flicker diagnostics, and the per-eye render camera readout. The Experimental page's button opens it and its close button closes it. Its open state lives in the UI and is not persisted. It follows the main window's read-only boundary: while gameplay input owns the controls, its contents are disabled.

## Input ownership

The header remains outside the feature body. Allow gameplay input requests a read-only overlay. The body, navigation, detached feature controls, and layout actions are disabled when editing capture is unavailable. Readouts still execute. The header reports requested and effective ownership separately. Hiding and reopening through the existing panel route returns to editing. The navigation does not introduce an input binding or change the capture policy.

The read-only boundary is only the UI side of input ownership. The input adapter remains responsible for clearing pending events, consuming held inputs through release, restoring the previous game-device state, and admitting events only with effective capture.

## Visualizations

The global Visualizations button opens a persistent drawer without changing the selected feature. Its bounded inventory edits the existing body mirror, controller gizmo, ghost hand, grip marker, grapple highlight, grapple beam, grab view, grab view contents, collider view, palm box, and wrist detonator button configuration fields in place. Requested switches appear first, grouped as Debug geometry or Gameplay cues. The filter matches view names, group names, and owning feature names. The shared settings group retains the overlay master switch, gun readout selector, mirror distance, and depth policy. Changing pages or input mode does not rewrite saved switches.

The header counts requested Boolean switches in this inventory, including grab view contents. It does not count every visualization in the mod or treat the gun readout selector as a Boolean switch. Each row distinguishes a saved request from a known blocker. Controller and overlay master switches, the grab view parent, temporary output suppression, cinematic suppression, and applicable producer scheme/gameplay gates have explicit explanations. Parent controls can be enabled in place. A request without a known blocker reports draw unverified because source, pose, camera, and depth availability are not sampled here. The active count remains unknown unless every registered request is blocked or off. Retained primitive counters do not establish a current draw. The shared settings report last-snapshot retained primitives, collected primitives after suppression and the cap, suppressed primitives, and uploaded primitives per eye separately. These are primitive counts, not active-view counts.

The drawer takes a configuration and runtime snapshot before editing. It acquires a configuration edit guard only to apply changed fields after rendering the controls. It uses the existing read-only boundary, so status remains visible while switches, filtering, settings, and temporary output actions are disabled without editing capture. The filter also matches each switch's owning feature: Body fit owns the body mirror and controller gizmos; Physical hands owns ghost hands, the palm boxes, the grab view and its contents, and the collider view; Grapple owns the target highlight and beam; Explosives owns the wrist detonator button. Besides the switches, the drawer holds the shared overlay settings (including hiding the game's reticles while the hands aim), the collider view's contents (its boxes, shapes, static bodies, contacts, joints, and gaze switches), the overlay, grab view, and collider view readouts, and Hide/Restore. The collider view's contents are edited on a copy and only those fields are written back, so the view's own switch edited in the same frame keeps its value.

Hide registered views suppresses the rendered output of all registered switches, including Gameplay cues. The inventory maps to the retained sources `BodyMirror`, `BodyMirrorPouches`, `DebugGizmos`, `GhostHands`, `GrabMarkers`, `GrappleHighlight`, `GrappleBeam`, `GrabView`, `ColliderView`, `PhysicalHands` (the palm boxes), and `WristDetonator`. The grab view parent and its content switches share `GrabView`. The collector filters these sources before the primitive cap, beginning with the next first-eye snapshot so both eyes keep the same geometry. The visualization controls are the sole runtime writer of the mask and apply it without a configuration lock. Producers continue to submit, refresh, clear, and expire their slots normally. Grip, grapple, and other gameplay behavior remain unchanged. `GunReadout`, `SightTuning`, `MagazinePips`, and all other non-inventory sources remain unchanged.

The temporary mask also covers registered switches enabled while hidden. A typed snapshot records the switches requested at Hide for a diagnostic count; it is not a configuration backup or a draw count. Restore registered views clears only the temporary mask and diagnostic snapshot. It preserves configuration edits made while hidden. Neither action writes saved configuration. The in-memory state lasts until explicit Restore or payload teardown. Closing and reopening the drawer does not restore output, and the state is not persisted across payload sessions.

Sight/scope, preview, HUD, and performance tools remain in their existing feature editors. Opening the drawer does not call a preview renderer, mark previews visible, or activate capture or scan work. Existing preview routes retain their DX11-renderer availability check.

Renderer-free tests cover the concrete configuration fields, edit isolation, filtering, requested-first ordering, parent blockers, and requested-versus-unverified counts. Added tests cover the registered source mapping, Hide/edit/Restore configuration isolation, every retained source's output under suppression, cap ordering, refreshes, clears, expiry, and restoration. The full Wine workspace suite passes with these tests, and the all-target, all-feature Windows clippy check passes with warnings denied. A retained last pipeline error is diagnostic history, not proof of a current blocker or zero activity. No live desktop, DX11, or headset validation is recorded for the drawer.

## Layout persistence and recovery

The workspace and detached feature views use `ui_layout_v2.json`. Feature views store stable catalog keys. Detach this view opens the selected feature in a dock window. Dragging its tab back to the main dock re-docks it. Closing a detached view does not remove its feature from navigation. Recover detached views gathers saved views into the main dock. Restore default layout returns to one workspace on Status.

Layout edits submit a serialized snapshot every sixty editing frames to one owned writer. It keeps one in-flight replacement and only the newest pending snapshot. Atomic durable replacement runs outside the layout and egui locks. The saved snapshot cache advances only after a successful generation acknowledgement; a failed latest snapshot can retry on the next submission. Shutdown closes admission and drains the worker, and an unfinished worker keeps the payload mapped.

A layout saved when features had separate sections still loads: the section names are ignored, a feature detached more than once keeps one view, and an unknown feature key is dropped or falls back to the default selection. The older `ui_layout.json` from before the feature navigation is not read. An invalid or unsupported layout reports a notice and blocks automatic persistence until recovery or reset.

## Verification

The frozen workspace passes Windows all-target, all-feature clippy and the Wine suite, including 2,678 payload tests. Renderer-free tests cover feature selectors, route categories and route coverage, distinct scroll keys, the Runtime feature's controls-then-readout order, unavailable previews, per-section views collapsing on load, normalized active/focus indices, malformed layouts, read errors, and failed atomic replacement. The actual production DockArea test renders main and detached controls through an injected callback without a fake DX11 renderer. It verifies disabled editing, preserved frame time and scale, visible detached content, neutral input on resume, and an unchanged authoritative layout. These callback tests do not prove that every domain feature body exposes all required widgets.

Read-only enforcement occurs inside each fresh dock body, with separate dock-interaction gates and a copied layout. Input neutralization preserves viewport, timing, scale, and other frame metadata rather than replacing the whole input state. Layout reads treat only missing files as absent. Atomic sibling-file replacement preserves the previous saved arrangement on failure.

No live DX11, desktop, or headset validation is recorded. Detached-view geometry, narrow readability, pointer hit regions, scroll restoration, and read-only behavior still require runtime acceptance. A successful renderer-free test does not establish these runtime properties.
