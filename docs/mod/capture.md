# In-process capture

The recorder streams one eye's rendered frames out of the game process at the render resolution and the headset's refresh rate, with a per-frame pose sidecar, so a trailer can be cut from footage that is neither a window capture nor limited to the desktop mirror's framing. The code is `payload/src/recorder/`, the host side is `scripts/capture_host.sh` and the relay it runs, `tools/capture/relay.py`, and the post-processing tool is `tools/capture/reframe.py`.

## Pipeline

The render thread does the minimum that needs the immediate context. In `render_engine_post_draw`, after the per-eye capture textures are copied for the frame, the recorder draws a fullscreen pass with `i420_pack_ps` that converts the chosen eye's display-referred RGBA into planar 4:2:0 YUV (BT.709, limited range) packed into a single `R8` texture of `width x height * 3 / 2`. That texture is copied into a ring of three staging textures, and the staging texture written two frames earlier is mapped with the no-wait flag. By then its copy has completed, so the map costs no GPU stall; if it has not, the map refuses and the frame is repeated. The mapped rows are copied into a pooled buffer and handed to the writer thread. The pass is skipped during the far-field phase and, in two-pass stereo, runs only on the dispatch that refreshed the chosen eye; under single-pass collapse both eyes are fresh on the one dispatch.

The writer thread owns a TCP connection to the host and the sidecar files. It connects with retries every half second, so the recording can be started before the host listener is up, and frames that arrive before the connection exists are dropped and counted. The stream is `yuv4mpegpipe`: a one-line header with the size, rate, and chroma layout, then `FRAME` followed by the planar bytes for each frame. It is self-describing and every frame is the same size, so the host side needs nothing configured and a dropped or repeated frame cannot desynchronise the parser. Frame rate is not measured; the header carries the value from the recorder config, which should be the headset's refresh rate. When the recording folder's host path is known ([sessions.md](sessions.md#the-sessions-root)), the header ends with an `XJC3VR_DIR=<path>` parameter naming it, percent-encoded so the path stays one space-free token. y4m allows `X` parameters and ffmpeg's demuxer skips ones it does not know, but it refuses a header longer than about a hundred bytes, which a path easily makes it, so the relay removes the parameter before ffmpeg sees the header.

Every captured display frame produces exactly one stream frame. A readback that is not ready re-sends the previous frame's bytes and is counted as a duplicate; a writer queue that is full drops the frame and is counted as a drop. The sidecar records which frames are duplicates, so the video's timing can be trusted frame by frame and corrected where it is not.

## The host

`scripts/capture_host.sh` picks the encoder (the first hardware H.264 encoder ffmpeg reports, NVENC, VAAPI, QSV, or AMF, else libx264), the quality, the colour tags, the ten-minute segmenting, and the audio source (the default sink's monitor), and hands that ffmpeg command line to the relay. The relay listens on the port, and for each connection reads the stream header, takes the recording folder from its `XJC3VR_DIR` parameter, starts ffmpeg reading the stream from its standard input, and forwards the header (without the parameter) and the rest of the stream. ffmpeg writes `video_NNN.mkv` segments into the folder, numbered on from any segments already there. When the stream ends ffmpeg finalizes the last segment and the relay listens again, so one host serves every recording of a session. A header without the parameter (the payload on native Windows) sends the segments to a stamped folder under the script's argument, `captures/` by default. Ctrl+C stops the relay: it closes ffmpeg's input, which finalizes the segment in progress; ffmpeg runs in its own process group so the interrupt does not cut it off first.

Video and audio both take wall-clock timestamps as ffmpeg reads them, which is what lines them up; the take markers give a second reference. ffmpeg starts when the recording connects, so the first few frames queue while it starts and are read in a burst: their timestamps bunch up over the first fraction of a second, and ffmpeg nudges them apart (it warns about non-monotonic timestamps). Every frame is kept, so frame numbers still match the sidecar's `stream_frame`.

The environment overrides are `JC3VR_CAPTURE_PORT` (default 47172, the payload's default), `JC3VR_CAPTURE_ENCODER`, `JC3VR_CAPTURE_QUALITY` (default 18), `JC3VR_CAPTURE_AUDIO` (a PulseAudio or PipeWire source, or `none`), `JC3VR_SEGMENT_SECONDS` (default 600), and `JC3VR_VAAPI_DEVICE`.

## Files

A recording's files share its folder, `recordings/<stamp>/` in the session folder ([sessions.md](sessions.md)): the host's `video_NNN.mkv` segments and the game's sidecar:

- `stream.json`: the stream size, rate, eye, pixel format, colour space and range, the host target, and the start wall clock.
- `frames.jsonl`: one line per stream frame, and one per take marker, in file order. A frame line has `stream_frame` (the frame number in the video), `capture_frame` (the render thread's ordinal), `duplicate`, `unix_ms`, `game_run_time_us`, `eye`, `predicted_display_time_ns`, and `views`: both eyes' raw located pose (position, orientation as `x, y, z, w`) in the runtime's LOCAL space and field of view as `left, right, up, down` angles in radians.

The capture ordinal, timestamps, and views describe the source pixels copied into the staging ring, rather than the later map or delivery attempt. A no-wait map that is not ready repeats both the previous pixels and their source metadata. `stream_frame` still advances for each delivered frame, and `duplicate` identifies that repeated source. Priming emits no video frame until a source is available. There is no separate delivery timestamp.

A take marker made while the recording runs (F2, the director's hotkey, or Mark in Tools > Video) is a line with two fields: `stream_frame`, the frame it falls at, and `marker`, holding its session ordinal `index`, the local `stamp`, `unix_ms`, `game_run_time_us`, and `label`. A frame line never has a `marker` field, which is how a reader tells them apart. Markers travel to the writer on their own unbounded channel, so a full frame queue cannot drop one, tagged with the capture ordinal the render thread is about to assign; the writer puts each before the first fresh frame whose `capture_frame` reaches it, so its `stream_frame` is the first video frame captured after the press, however far the writer lags. A repeated frame does not place a marker, which therefore lands on the next fresh one. Markers made after the last frame the writer receives fall at the end of the stream. With no recording running, markers go to `markers.jsonl` in the session root instead, one JSON object per line with the same fields, where the wall clock is what lines one up against a host recording. Either way, while a tracking recording or its lookback collects, the same marker is also written to the tracking timeline as a `take_marker` event with the same fields ([testing/recorder.md](testing/recorder.md)), so the copies join by `index` and `stamp`.

## Post

`tools/capture/reframe.py` turns a segment plus its sidecar into a flat video. The eye render is off-axis and wide; the tool builds the eye's pinhole matrix from the sidecar's field of view, a symmetric output camera from the requested horizontal field of view and aspect, and warps each frame by the homography between them, so the crop is centred on the optical axis rather than the texture centre. With `--smooth` above zero the output camera follows a Gaussian-smoothed head orientation instead of the recorded one, which is a rotation-only stabilisation from ground truth: a homography, no depth, nothing estimated. The margin outside the crop is what the stabilised view pans into. `--dry-run` prints the framing and the first frame's corner mapping without decoding. Both modes list the take markers from the segment's start on, with their frame and time in the output; the tool reads marker lines apart from frame lines, so they do not shift the frame indexing.

Segments after the first need `--offset`, the stream frame index the segment starts at, since the sidecar covers the whole recording.

## Session recording

F1 starts a session recording: the video recorder and a tracking recording ([testing/recorder.md](testing/recorder.md)) started together under one stamp, so both halves land in one `recordings/<stamp>/` folder in the session folder ([sessions.md](sessions.md)), the tracking recording as `tracking.jc3trk` beside the video's sidecar and segments. F1 again stops both, as it does when either one runs on its own. Tools > Video has the same button and a "Session recording" line saying which halves run and under which stamp, with the tracking recording's error if it did not start (it needs `testing.enabled` and a player character). Neither recording has a length limit: video frames stream to the host, and tracking batches are appended to the file by a writer thread, so an hour-long session holds no more in memory than a short one.

The two halves line up by the OpenXR predicted display time, which the video sidecar's `predicted_display_time_ns` and the tracking frames' `display_time_ns` share; `tracking-synth dump --from xr:<ns>` prints the tracking around a video frame.

F2 is the take-marker action: an unlabelled marker into whatever records (above); in the headset the left stick click and then right A does the same ([input/controllers.md](input/controllers.md)). With no tracking recording running it also saves the tracking lookback, the last ten seconds, to `recordings/<stamp>/lookback.jc3trk`, so a moment is kept even when no session recording was started.

## Operating it

1. Start `scripts/capture_host.sh [fallback output dir]` on the host and leave it running for the session. It listens on port 47172 unless `JC3VR_CAPTURE_PORT` says otherwise.
2. In the headset, start the recording with F1 (a session recording), or the video alone from Tools > Video in the debug UI or its hotkey (Numpad / by default). Tools > Video shows the stream size, the frames sent, repeated, and dropped, and whether the host is connected.
3. Stop the recording the same way: the stream closes, the host finalises the last segment into the recording's folder and waits for the next one. Ctrl+C on the host script stops it, finalising the segment in progress.

The recorder config (eye, scale, header frame rate, host, port) is in the same section and applies to the next recording. Scale below one shrinks the stream in the pack pass, which is the lever if the readback or the loopback cannot keep up at full eye resolution.
