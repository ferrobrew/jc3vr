# Threading and the VR runtime's locks

The mod runs code on threads it does not own: the game thread, the engine's draw task and CPU fragment workers, the input job, and the UI capture and render workers, as well as a frame-tail worker of its own. The VR runtime has two locks. The runtime state (`VR_STATE` in `crates/jc3vr-view/src/vr/state.rs`) is taken briefly by the game thread. The submit side (`SUBMIT` in `crates/jc3vr-view/src/vr/submit.rs`: the frame stream and the swapchain) is held for most of a frame while its holder waits on the draw task and the fragment workers. A thread those waits depend on that blocks on either lock deadlocks the game, so which threads may take them, and where in the frame, is a correctness rule. The UI capture thread asking whether a session runs while the frame holds the lock and waits for that thread is the typical case.

This page has the thread model, who holds what across a frame, the lock rules, the guard that checks them, and the game tick that the handles to game objects borrow. The OpenXR frame loop step by step is in [vr-runtime.md](vr-runtime.md#the-frame-loop).

## Threads

| Thread | Mod code that runs on it | Role |
| --- | --- | --- |
| Game thread | The [`Game::Update`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::Game##func-Update) hook (`crate::update` in the payload: the tuning reload, the directing and test tools, the hand bodies' frame tick, and the debug UI); the simulation's hooks, among them the input tick's game stage at the top of the world's pre-simulation queue ([input/controllers.md](input/controllers.md#bindings-and-injection)) and the hand bodies' pre-simulation callback; and the [`Game::UpdateRender`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::Game##func-UpdateRender) hook (the palms' tick, the VR runtime pump, the frame begin, the engine's render update, the eye dispatches, and the inline frame tail) | `Game`, narrowed to `GameDebugUi` and `GameFrame` |
| Frame tail (`jc3vr-frame-tail`) | The deferred frame tail (`vr::tail`): the final drain, the mirror, the blit, and the submit | `FrameTail` |
| Draw task | [`GraphicsEngine::HandleDrawThreadTask`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::graphics_engine::GraphicsEngine##func-HandleDrawThreadTask) and everything under it: the render-pass, camera, and shader hooks and `RenderEngine::PostDraw` (the HUD quad, the egui panel, the mirror overlay). It runs on a CPU fragment worker, or inline on the game thread when [`CpuPrimaryCount`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/cpu_fragment##func-CpuPrimaryCount) is at most one | `Unmarked`, or `GameFrame` when inline |
| CPU fragment workers | Engine jobs and any hook they reach. The game thread runs queued fragments itself while it waits in [`CpuFragmentWaitUntilSignalIsNonZero`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/cpu_fragment##func-CpuFragmentWaitUntilSignalIsNonZero) | `Unmarked`, or the game thread's role for a fragment it runs |
| Input job | The input update ([`RunInputThread_Proxy`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/game##func-RunInputThread_Proxy)) on whichever worker takes it, concurrently with part of the game thread's update ([engine/gameplay/input.md](../engine/gameplay/input.md#where-the-device-poll-runs)): the input tick's poll stage (the `InputDeviceManager::Update` detour), the head pose simulation's tick, and the UI's input hooks. It may touch only input, UI, and the mod's own state. In the load state and the frontend's loading it runs inline on the game thread, with the game stage right after it | `InputJob`, which narrows `Game` on a run the game thread steals |
| UI capture thread | The thread [`UIManager::m_CurrentCaptureThread`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##field-m_CurrentCaptureThread) names: the pause-menu hooks and the capture seam (`hooks::ui::movie_capture`). The frame waits on it while it holds the submit side | `Unmarked`, or `GameFrame` |
| UI render worker | The fragment [`UIManager::StartRender`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/ui::ui_manager::UIManager##vfunc-StartRender) queues: the partitioned HUD render (`hooks::ui::ui_render`) | `Unmarked` |
| Mod writer threads and the shutdown thread | The image writer, the video recorder, the tracking recorder, the settings, inventory sidecar, diagnostics, and profiler writers, and `shutdown_startup` | `Unmarked`; none locks the runtime |

The role column is the thread's role in `jc3vr_core::thread_role` ([the guard](#the-guard)). Engine threads keep the default `Unmarked`, so a hook that runs on an unexpected thread is caught without having been marked.

## Who holds what across a frame

A frame runs in this order on the game thread, with the render update overlapped (`vr.overlap_render_update`, on by default):

1. `Game::Update` calls `crate::update`, which runs the debug UI holding the egui state lock (`EguiState::get`) for the whole egui pass.
2. The simulation runs. The previous frame's draw task and deferred tail may still be running.
3. The `Game::UpdateRender` hook opens the frame's generation of the per-frame slots (`render_frame::begin_preparing`), then calls `vr::update`, `vr::auto_recenter_tick`, and `vr::apply_native_resolution`, each of which locks the runtime state briefly.
4. `vr::frame_wait` locks the runtime state for `xrWaitFrame`, the view location, and the controllers, and releases it. The head pose and the per-eye render parameters are published, and the engine's render update runs, while the previous frame's draw task and tail may still be running.
5. `WaitedFrame::begin` takes the submit side, which blocks until the previous frame's tail has submitted, and calls `xrBeginFrame`. A frame with no XR frame to begin waits for the tail the same way. `vr::arm_direct` then acquires the swapchain image and publishes it in the direct-blit slot, which the draw task's `PostDraw` reads.
6. The eye dispatches run with the submit side held. The game thread waits on the fragment workers, running stolen fragments meanwhile, and on the draw task between dispatches ([`GraphicsEngine::WaitForCPUDrawToFinish`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::graphics_engine::GraphicsEngine##func-WaitForCPUDrawToFinish)).
7. With the tail inline, the game thread drains the last dispatch, submits, and releases the submit side. With the tail deferred, the `FrameContext` and its guard move to the tail worker, which polls the last dispatch's completion signals, records the mirror and the blit under the engine's immediate-context critical section, and submits, while the game thread returns to the next frame's `Game::Update`.

In the serial ordering (`vr.overlap_render_update` off) the game thread waits for the tail (`vr::wait_for_frame_tail`) before step 3 and begins the frame right after `vr::frame_wait`.

The overlap follows the engine's own frame. `Game::UpdateRender` does not wait for the previous draw task: its wait is gated on [`Game_EnableOldSyncPoint`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::Game_EnableOldSyncPoint), which nothing sets, and the engine's fence is the wait at the top of [`Game::Draw`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/game::Game##func-Draw). OpenXR allows a frame's `xrWaitFrame` once the previous frame has begun, from any thread, and requires only that the next `xrBeginFrame` follow the previous `xrEndFrame`. What the mod adds needs three things to stay safe:

- The draw task reads values the render update writes: the per-eye render parameters, the cull and shadow-fit projections, and the capture views (`vr::frame`), the camera hook's interpolation fraction and planes, the hands' late update, the presentation layer, and the guns as the render update placed them. Each is a `RenderFrameSlot` (`jc3vr_core::render_frame`), which keeps the frame being prepared apart from the frame being drawn. The engine's `Draw` prologue records which frame a dispatch draws (`render_frame::note_dispatch`), the draw-task detour pins that frame on its thread (`render_frame::pin_dispatch`), and every read there answers with the dispatched frame's value. Every other reader reads the frame being prepared.
- The runtime's D3D11 client records on the game's immediate context when it acquires, releases, and submits swapchain images, and the tail makes those calls while the render update may be issuing the engine's own context work, so they run under the engine's context mutex, which the engine's `Graphics::` wrappers take call by call.
- Everything from the begin on (the dispatch state, the between-eye snapshots, the swapchain acquire, the dispatches) waits for the tail, which drained the previous dispatch. So do a desktop swapchain resize (`vr::sync_swapchain_to_window`), which the tail's mirror presents into, a queued visual-harness transition at the top of the render update, a session stop, and the teardown.

Under the two runtime locks the holders take the config lock, the controller frame slot, the stage information, the render-parameter slots, the input status and the haptics mixer, the capture-texture state, the direct-blit slot, the blit and mirror pipelines, the egui panel state, the replay's staged step, the tracking recorder's state, and the engine's immediate-context critical section. Each is taken briefly, and nothing takes the runtime's locks under them.

The render-time seams that place what the player holds and pose the body (the late update's frame, the presentation layer's records and draw cache, the held explosives' registrations, the overlay's store, and the debug panel's placement) are leaf slots: the input tick or the simulation writes them, the render update reads them, and neither side takes another lock under them ([rendering/render-time-anchoring.md](rendering/render-time-anchoring.md)).

The egui state lock is the other long one. The game thread holds it across the debug UI, and the draw task takes it in `PostDraw`: at eye 0's to render the floating panel, and at the frame's last near dispatch's to render the mirror overlay. With the tail deferred, that last walk can overlap the next frame's debug UI, so the draw task can wait there for the game thread's egui pass; the game thread never waits on that walk while it holds the egui state lock (rule 6).

## Lock rules

1. Block on the runtime's locks only on the game thread at the top of the render update or at the overlapped frame's begin, holding no other lock. The functions that do (`vr::update`, `vr::is_running`, `vr::auto_recenter_tick`, `vr::native_eye_resolution` and `vr::engine_render_resolution`, `vr::frame_wait`, `WaitedFrame::begin`, `vr::uninstall`, and `vr::wait_for_frame_tail`) are for those points and for the shutdown path in rule 6. Take the runtime state before the submit side, never the other way round.
2. Everywhere else, read a published slot. `vr::render_params` says whether a VR frame is rendering and carries the per-eye parameters, `vr::is_running_published` whether a session ran at the last `vr::update`, and `vr::stage::stage`, `jc3vr_input::frame::latest`, `vr::recenter_count`, and `vr::published_status` publish the rest. The debug UI's runtime readout uses `vr::status`, which try-locks and reports nothing rather than waiting.
3. Ask for runtime work by request. `vr::recenter`, `vr::request_recenter`, and `vr::request_seat_recenter` set atomic bits that `vr::auto_recenter_tick` services at the top of the next frame, so the window procedure, the UI capture thread, the input tick, and the roomscale update may call them under any lock. `vr::recenter` also defers choosing the recenter kind, since choosing it takes the config lock.
4. Take the runtime's locks outermost. A thread holding any other lock, the config lock included, must not take them, since the holders take those locks under them.
5. Keep published slots as leaves: hold them briefly, take no other lock under them, and do not wait while holding them. Where a reader must touch an engine lock, it try-enters it, as the controls summary does with the HUD's hint queue.
6. Do not wait on the draw task while holding the egui state lock. The shutdown path tears the runtime down from the lifecycle cleanups, which run under that lock, so `shutdown_from_game` first calls `vr::wait_for_frame_tail`: with the tail submitted, the draw task it waited on no longer needs the egui state lock.
7. Take the eye blit's locks inside the engine's immediate-context critical section, in one order: the section, then the direct-blit slot (`DIRECT`), then the blit pipeline (`VR_BLIT`), both in `crates/jc3vr-view/src/vr/blit.rs`. The draw task's direct route reaches them from `PostDraw` with the section already held; the submit enters the section before it takes the pipeline, and takes the direct-blit slot only on its own, before either. A holder of `VR_BLIT` outside the section (the end of the frame's view over the back buffer, the teardown) must not enter the section under it.

## The guard

`jc3vr_core::thread_role` gives each thread a role in a thread-local cell. `mark_thread` sets a thread's base role once: the game thread marks itself `Game` at the top of `Game::Update` and of the render update, and the tail worker marks itself `FrameTail`. A `RoleScope` from `enter` narrows the role for a dynamic extent and restores the previous one when dropped: `crate::update` holds `GameDebugUi` for the egui pass; the render update holds `GameFrame` from just after `vr::frame_wait` to its end, lifted only around the overlapped frame's `WaitedFrame::begin`, and in flatscreen frames too, so a violation shows without a headset; and the input job's detour holds `InputJob`, so a check that admits only `Game` does not admit a stolen run of the job. The draw task and the fragments the game thread runs itself take its role.

Every blocking lock of the runtime state goes through `lock_state` (`vr/state.rs`), and of the submit side through `lock_submit` (`vr/submit.rs`). Each reads the caller's role, and any role other than `Game` (`ThreadRole::may_block_on_vr_state`) is a violation. A debug build logs it with the caller's location (`#[track_caller]`) and panics before it blocks, so the log names the site instead of the process wedging. A release build logs the first violation and goes on to lock. The only other access to the state's mutex is the `try_lock` in `vr::status`.

The guard checks the thread, not the locks it holds, so rule 4 is not enforced: a call from the top of the render update while holding another lock is not caught.

## The game tick

Most of the mod's game-object code needs one guarantee that a thread role does not give: that it runs on the game thread at a point where no other engine thread mutates the world's game objects, so that a character, weapon, or vehicle that is live when the code reaches it stays live until the code returns. `jc3vr_core::game_tick` carries that guarantee as a token, `GameTick`, and the handles to game objects borrow it, starting with `LocalPlayer` (`crates/jc3vr-body/src/controllers/physics/local_player.rs`), the local player reached once per tick with its null check.

A tick exists only inside `GameTick::enter`, which hands its closure a borrow with a fresh lifetime, so neither the tick nor a handle borrowed from it outlives the call, and the token is neither `Send` nor `Sync`. Code that needs the guarantee takes `&GameTick<'_>` (by convention the parameter `game`) instead of stating it in a `# Safety` section. Opening a tick is `unsafe`: the caller asserts the serial point, and a debug build checks the role as a backstop, admitting only `Game` and `GameDebugUi`. The input job, the frame tail, the render update's `GameFrame` scope, and every `Unmarked` thread (the draw task, the fragment workers, and with them the character manager's parallel pose pass) cannot open one.

The serial points that open a tick:

| Entry point | Where in the frame |
| --- | --- |
| The input tick's game stage (`controllers::bindings::stage`, gameplay crate) | The top of the world's pre-simulation queue, after its update-queue commit and before any character, weapon, or vehicle update and the physics step; after a pre-simulation update that skipped its queue; or inline after the device poll in the load state |
| The hand bodies' frame tick (`physical_hands::physics::frame_tick`, from the payload's `crate::update`) | The top of the `Game::Update` hook, before the game's update starts |
| The palms' tick (`physical_hands::main_thread_tick`, from `hooks::game::game_update_render`) | The top of the render update hook, before the frame scope: the simulation is done and the engine's render update has not started |

A tick does not cover the engine calls made inside it. An engine method can free, reallocate, or reparent the object it is called on or others (dropping a weapon may destroy it; an act can retire a proxy), and it can reenter the mod's detours, which may reach the same object again. Code that keeps an object across such a call re-resolves it afterwards, through a weak reference or a fresh `LocalPlayer::get`. Nor does a tick make an object exclusive: two handles reached in the same tick name the same engine object, so a handle lends `&mut` only through `&mut self` and is neither `Clone` nor `Copy`.

Code that runs in a detour on an engine thread, in the parallel pose pass, in the physics step's callbacks, or at render time has no tick and keeps its own `# Safety` contract, fetching the local player itself. So do helpers both kinds of caller share, such as the loadout's store projection. `tools/analysis/unsafe_counts.py` counts the unsafe blocks and the local player fetches per crate.
