# Static foveated rendering (issue #29)

The mod shades every pixel of both eyes at full rate, including the periphery, where the lenses and human vision resolve little detail. Static (fixed-centre) foveation reduces the peripheral shading cost. The only cross-vendor path on Direct3D 11 is Valve-style radial density masking through the stencil buffer, which is what the mod implements; issue #29 has the survey of the alternatives (compositor foveation, NVAPI variable-rate shading, and quad views).

Before the scene passes, a full-screen pass writes a radial, dithered mask into a stencil bit of the main depth-stencil surface, so the dropped peripheral pixels carry the bit. The expensive scene passes then run with a stencil test that rejects those pixels before the pixel shader runs. A fill-in pass afterwards reconstructs the dropped pixels from their kept neighbours. The main depth surface has an 8-bit stencil, so this works on any GPU.

## The engine's depth-stencil path

The engine binds depth-stencil state in one place. Render blocks stage a packed depth-stencil state index and a stencil reference on the context through setters such as [`SetStencilTestEnable`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/graphics_engine::draw##func-SetStencilTestEnable), [`SetStencilFunc`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/graphics_engine::draw##func-SetStencilFunc), [`SetStencilOp`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/graphics_engine::draw##func-SetStencilOp), and [`SetStencilMask`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/graphics_engine::draw##func-SetStencilMask), which write context fields and make no Direct3D call. [`SetupRenderStates`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/graphics_engine::graphics_engine##func-SetupRenderStates), the state flush at the top of every draw wrapper, looks the staged index ([`HContext_t::m_DepthStencilStateIndex`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::graphics_engine::HContext_t##field-m_DepthStencilStateIndex)) up in a per-context cache, creates the state lazily through [`CreateDepthStencilState`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/graphics_engine::graphics_engine##func-CreateDepthStencilState), and issues the only `OMSetDepthStencilState` with [`HContext_t::m_StencilRef`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::graphics_engine::HContext_t##field-m_StencilRef), rebinding only when the index or reference changed. The doc comment on `m_DepthStencilStateIndex` gives the index's bit layout.

A detour on `SetupRenderStates` can therefore rewrite the staged index just before the flush, and the engine's cache creates and keeps the extra state object.

The engine uses stencil itself on the main surface, staged per pass from the [`RenderPass`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_pass::RenderPass) stencil fields by [`RenderPass::PreDraw`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_pass::RenderPass##func-PreDraw): the SMAA edge mask ([`edge_stencil_bit_mask`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::post_effects::edge_stencil_bit_mask)), character skin and subsurface scattering, the outline blur, and the road and decal masks ([`RenderPassId::RP_ROAD_STENCIL`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine::RenderPassId##variant-RP_ROAD_STENCIL) and [`RenderPassId::RP_CLEAR_STENCIL`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine::RenderPassId##variant-RP_CLEAR_STENCIL)). The skin and outline bits are not confirmed. No engine code path found references the top stencil bit, so the mod uses it as the mask bit (`MASK_BIT` in `foveation.rs`); the shipped per-pass write masks have not been audited, so a collision is possible and would show as corruption in one effect. Direct3D 11 has one stencil test per draw, so the forced test skips draws that already enable stencil, and those draws render unmasked.

The main depth and stencil are cleared per pass through [`Clear`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/module/graphics_engine::draw##func-Clear), early in the G-buffer range around [`RenderPassId::RP_Z_OCCLUDERS`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine::RenderPassId##variant-RP_Z_OCCLUDERS), so the mask is written after that clear.

## Implementation

- `crates/jc3vr-view/shaders/foveation_mask_ps.hlsl` writes the radial dithered mask, using interleaved-gradient noise decided per drop cell, and `foveation_fill_ps.hlsl` reconstructs dropped pixels from their kept neighbours. Both take the same constant buffer (the eyes' centres, the radii, the drop, the seam column, and the cell size), and the two must keep their noise and drop decision identical so the fill reproduces the mask's choice.
- `crates/jc3vr-view/src/vr/foveation.rs` holds the two full-screen passes, which run on the immediate context under `Context::m_Mutex` as `vr::blit` does, the force-test index rewrite (`apply_force_test`), the packed-index bit math (`packed_stencil_test`), and the foveated pass set (`FoveatedPasses`).
- `crates/jc3vr-render/src/hooks/graphics_engine/render_pass.rs` holds the `SetupRenderStates` detour and the `DrawRenderPassRange` bracketing (`run_scene_range`): the mask-write runs before the first foveated pass, the stencil test is forced through each run of foveated passes, and the fill-in runs before the pass named by `FoveatedPasses::fill_before`, or at the start of the post effects in the `DrawPosteffects` hook. The mask-write runs in the call whose range holds the first foveated pass, so it runs once even when the scene range is split across calls. The foveal centre is each eye's projection's principal point (`foveal_center_uv`), so off-axis eyes fovea about their optical centre rather than the screen centre.
- `foveation.enabled` (on) is the pause menu's `FOVEATED RENDERING`, and `foveation.debug_show_mask` paints the dropped pixels magenta from the debug UI's Foveation feature. The rings are the view tuning's `foveation.inner_fraction`, `outer_fraction`, and `max_drop` ([tuning.md](../tuning.md)).
- Three switches, all on, sit with the single-pass switches so the harness can compare them within one schedule, but they gate multipass as well: `single_pass.foveation_gbuffer`, `foveation_lighting`, and `foveation_quads`.

## Which passes skip the dropped pixels

A pass belongs in `FoveatedPasses` only if dropping its pixels leaves every kept pixel unchanged. Two questions decide that: whether the pass writes anything a later pass reads at a neighbouring pixel before the fill-in runs, and whether it writes depth the prepasses have not already written. A dropped pixel keeps the depth it had when the forced test began, and the SSAO, the depth downsample, the fog volumes, the water's depth test, and FSR all read depth at and around it.

- Always: the models, the vegetation, and the creatures ([`RenderPassId::RP_MODELS_DYNAMIC`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine::RenderPassId##variant-RP_MODELS_DYNAMIC) through [`RenderPassId::RP_CREATURES`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine::RenderPassId##variant-RP_CREATURES)).
- `single_pass.foveation_gbuffer`: the terrain's apply passes ([`RenderPassId::RP_TERRAIN_APPLY_NEAR_DETAILED`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine::RenderPassId##variant-RP_TERRAIN_APPLY_NEAR_DETAILED) through `RP_TERRAIN_APPLY_FAR`), the road junctions and road layers (`RP_ROAD_JUNCTION` through `RP_ROAD_JUNCTION_OPAQUE`), and the decals (`RP_DECALS` through `RP_SCREEN_SPACE_ROAD_DECALS`).
- `single_pass.foveation_lighting`: the deferred lights ([`RenderPassId::RP_DEFERRED_LIGHTS`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine::RenderPassId##variant-RP_DEFERRED_LIGHTS)), the light billboards (`RP_BILLBOARD`), the stars, sun, moon, skybox, and sky gradient (`RP_STARS` through `RP_SKY_GRADIENT`), and the fog gradient (`RP_FOG_GRADIENT`). Each writes the lit colour at its own pixel from that pixel's inputs. The fill-in then runs right after the fog gradient, under a stencil test that passes only the dropped pixels, instead of at the start of the post effects. Moving the fill-in is what makes the lighting safe to drop: from the scene-colour copy the water and the refraction read onward, every pass sees a reconstructed neighbourhood, and the passes after the fill-in (the water, the clouds, the fog volumes, the particles, and the transparents) shade the dropped pixels as they shade every other pixel. The occlusion queries ([`RenderPassId::RP_OCCLUSION_QUERY`](https://ferrobrew.github.io/pyxis/#/JustCause3_Steam_20206564/item/graphics_engine::render_engine::RenderPassId##variant-RP_OCCLUSION_QUERY)) between them stay out, since a dropped pixel would stop counting towards a query.

The passes left out were measured at the town by masking each group alone and comparing the G-buffer's depth and the final image against the variant without it (run 333):

- The depth prepasses give the dropped pixels their depth.
- The terrain's detail passes (`RP_TERRAINPATCH_DETAIL_MID` and `_LOW`, the largest terrain cost) write depth the prepasses do not. Masked, 2.9 and 2.0 million dropped pixels per eye lost their depth, and 0.8 and 0.6 million kept pixels changed in the final image, against a repeat floor of about 3,000. The base-mesh passes (`RP_TERRAINPATCH_BASEMESH_TESSELLATE_NEAR` through `RP_TERRAINPATCH_BASEMESH_COLOR`) do the same over a smaller area: 136,000 dropped pixels' depth and 12,600 kept pixels. The apply passes, the roads, and the decals changed neither.
- Forcing the test on draws that write stencil without testing it, while keeping their writes, changed 190,000 and 700,000 kept pixels, so draws that use stencil stay unmasked.
- The SSAO and its blur, the reflections, the global illumination, the subsurface skin, and the depth downsample read neighbours. The post effects and FSR run after the fill-in.

The detail passes could be made skippable only by writing their depth in a prepass, the engine's or a mod-side depth-only draw of the same patches, which would cost part of what masking them saves.

### Dropping whole quads

A pixel shader runs per 2x2 quad, and a quad with one live pixel runs all four lanes. With the drop decided per pixel, only 15% of an eye's quads lose all four pixels at the shipped radii, against 54% of the pixels dropped, so the stencil test saves little shading: the deferred lights go from 0.64 to 0.57 ms. `single_pass.foveation_quads` decides the drop per 2x2 cell aligned to the quads, so a dropped cell runs nothing, and the same lights take 0.36 ms. The fill-in then reconstructs a dropped cell from the nearest pixel of each of the 8 neighbouring kept cells, weighted by inverse squared distance. The far periphery is blockier than with the per-pixel dither at 1:1, at edges especially: a pole against the sky shows a 2-pixel stair.

### Cost and image differences

At the town, foveation saves about 0.1 ms of GPU time per frame against none, and 0.33 ms against the models-only, per-pixel version. "The foveation's net value" in [frame-budget.md](../performance/frame-budget.md) has the per-pass figures.

The kept pixels were compared in single-pass with the shipped settings, the G-buffer and lighting switches on against off (quads in both, so the two drop the same pixels), inside the kept set read from the stencil mask bit (run 333, saved planes). The scene colour at the start of the post chain differed by more than 2% at 7,400 and 14,800 kept pixels per eye at the town, against 10,200 and 15,100 for the repeat; at 45 and 33 at the capital at night; at 116 and 118 in the tunnel (14 for the repeat); and at 3,400 in the meadow, against 52,000 for its repeat, whose trees move between snapshots. The final image differs at more kept pixels than the scene colour (11,300 and 6,700 at the town against 4,300 and 3,700), because the dropped pixels hold a different reconstruction and the post effects that read neighbours (the glare and the engine's anti-aliasing) carry it into kept pixels next to them. The G-buffer's depth at the dropped pixels is unchanged.

With the fill-in before the water, the clouds, and the transparents, those render at the dropped pixels instead of being averaged from neighbours, so the sea at the horizon, the clouds' edges, and thin wires are sharper in the periphery. A few light specks can show on characters in the far periphery, probably dropped cells with no kept neighbour, which keep their unshaded value. None of these differences has been judged in a headset.

## Under single-pass stereo

The single-pass collapse renders both eyes into one double-wide target in one dispatch, so the mask and the fill-in run once. Laid out as for one eye, they would put a single fovea on the seam with a radius sized for the double-wide target. `single_pass.foveation_per_eye` (on) hands both passes both eyes' centres, each as a UV of its own half, an eye-sized half-diagonal, and the first column of eye 1's half. Each pixel takes its eye from the half it lies in and measures its radius, its dither, and its fill-in neighbourhood in pixels from that half's left edge; a neighbour across the seam reads as zero, as one past the edge of an eye-sized target does. Each pass stays one draw. "The shipped settings under single-pass" in [single-pass-collapse-defects.md](single-pass-collapse-defects.md) has the measurement.

## The fill-in's pipeline state

The fill-in draw runs on the immediate context with the pipeline state it binds itself, so `bind_fullscreen` binds every stage it depends on, including an explicit opaque blend; the state backup restores the engine's state afterwards. A stage left unbound inherits what the engine's last scene block left on the context. An inherited additive blend, for example, makes the fill add its reconstruction over the whole shaded frame, which doubles the brightness and flips with head pose. A raw pass on the engine's context must bind every state stage it depends on.

## Unverified

- The forced test relies on `SetupRenderStates` rebinding because the rewritten index differs from the last one flushed. Whether the first foveated draw rebinds, so the mask-write's own state does not leak into a scene pass, and whether the first draw after the range restores the normal state, is not confirmed.
- `packed_stencil_test` sets one set of stencil operations. If `CreateDepthStencilState` leaves the back face at `ALWAYS`, back-facing peripheral geometry still shades.
- The ring radii, the drop, and the fill neighbourhood have not been judged through the lenses.
